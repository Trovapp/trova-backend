# 일정 초안 접수와 다시 짜기

인증된 사용자가 `POST /api/trip-drafts`에 영상 목록과 조건을 보내면 서버가 비동기 생성 작업을 접수한다. 기존 초안에서 다시 짜기를 시작할 때는 `replacesDraftId`에 원본 초안 번호를 넣는다.

```http
POST /api/trip-drafts
Content-Type: application/json
Idempotency-Key: 93242a57-f1b4-40bc-9f28-514f1ae595c6

{"jobIds":[17],"message":"당일치기 오전 위주","replacesDraftId":41}
```

앱은 사용자가 새 작업을 시작할 때 UUID 하나를 발급한다. 수동 생성과 다시 짜기 모두 계정·원본·입력별로 키를 공유한다. 한 탭에서 202를 확인한 뒤에도 최초 확인부터 24시간 동안 키와 초안 번호를 보관해 다른 탭과 앱 재실행에서 다시 쓴다. 401 후 같은 계정으로 다시 로그인해도 미확정 요청에는 같은 키를 보낸다. 키는 선택 사항이며 UUID 형식이 잘못되면 400이다.

| 상황 | HTTP | 응답과 앱 동작 |
|---|---|---|
| 새 작업 접수 | 202 | `{"draftId":42,"status":"PENDING"}` |
| 같은 사용자가 최초 접수 후 24시간 안에 같은 키를 재전송 | 202 | 본문 조건·원본·작업의 현재 상태와 관계없이 최초 접수 응답을 재생한다. `GET /api/trip-drafts/42`에서 현재 상태를 확인한다. |
| 같은 사용자가 최초 접수 후 24시간 미만에 같은 원본·본문을 재전송(원본 생략, 키 생략·변경 포함) | 202 | 폐기되지 않은 PENDING·PROCESSING·NEEDS_INPUT·READY 초안의 최초 ID와 `PENDING`을 반환한다. 예를 들어 다른 탭이 202를 확인하고 대체 초안이 READY가 된 뒤 11분째에 재시도해도 큐 등록은 최초 1회다. |
| 같은 원본에 PENDING·PROCESSING 작업이 있고 요청을 재생할 수 없는 경우 | 409 | `activeDraftId`로 진행 중인 초안을 조회한다. 최초 접수 후 24시간 미만이고 정규화한 본문이 같으면 이 요청의 키도 해당 작업에 연결한다. 다른 본문의 키는 이후 새 접수에 쓸 수 있다. |
| 같은 원본의 대체 초안이 NEEDS_INPUT이고 키·본문 재생 조건에 해당하지 않는 유효한 요청 | 202 | 이전 질문을 종료하고 새 초안을 접수한다. 이전 질문에 뒤늦게 답하면 답변 API가 409를 반환한다. |
| 배포 전 원본 번호를 기록하지 않은 진행 작업이 이 사용자의 비노출 원본에서 시작됐을 가능성이 있는 경우 | 503 | `DRAFT_LEGACY_JOB_IN_PROGRESS`와 `Retry-After: 30`을 반환한다. 서버가 키와 정규화 본문을 기록한다. 30초 뒤 앱이 재생 조회로 확인한다. |
| 원본의 작업이 READY·APPROVED·FAILED이고 키·본문 재생 조건에 해당하지 않는 요청 | 202 | 새 초안을 접수한다. 완료 후에도 24시간 내 기존 키로는 최초 응답을 받는다. |

본문을 비교할 때 영상 번호 목록은 순서와 중복을 무시한다. 날짜와 조건은 `message`에 담기며, 메시지의 앞뒤 공백과 연속 공백 차이는 무시한다. `replacesDraftId`가 다르면 별도 요청이다. 서버는 접수된 키를 먼저 조회한다. 본문으로 재생할 때 받은 새 키도 최초 접수의 24시간 만료 시각까지 같은 작업을 가리킨다. 재생으로 본문이나 키의 만료 시각이 연장되지 않는다. 최초 접수부터 정확히 24시간이면 키와 본문 재생이 만료되고, 원본의 진행 작업 유무에 따라 새로 접수하거나 409를 반환한다. 같은 원본에 다른 조건의 진행 작업이 있어도 재생할 초안이 있으면 그 최초 ID를 반환한다. 다른 작업의 상태와 질문을 보존한다. 본문 재생은 해시 저장을 시작한 버전에서 접수한 작업부터 적용한다.

키가 없는 생성 POST는 최초 접수 후 24시간 미만인 승인된 동일 본문도 재생한다. 승인 뒤 같은 입력으로 다시 만들려는 사용자는 새 UUID로 명시적으로 접수한다.

### 자동 재시도 전 조회

앱은 503 자동 재전송 직전에 `POST /api/trip-drafts/replay`로 생성과 같은 본문과 선택 헤더 `Idempotency-Key`를 보낸다. 서버는 계정별로 연결된 키를 먼저 찾고, 없으면 같은 원본과 정규화 본문의 최근 접수를 찾는다. 유효한 대기 키가 있으면 대기를 시작한 뒤의 결과만 대상이다. 조회는 초안이나 큐 항목을 만들지 않는다.

| HTTP | 앱 동작 |
|---|---|
| 200 · `{"draftId":42,"status":"APPROVED"}` | 해당 초안의 현재 상태를 열고 자동 재전송을 종료한다. |
| 204 | 같은 키로 생성 POST를 재시도한다. 조회 직후 다른 기기가 승인해도 서버가 기존 ID를 반환한다. |
| 조회 오류 | 자동 재전송을 보류한다. |

상세 조회 `GET /api/trip-drafts/{draftId}`는 폐기 여부를 불리언 `dismissed`에 담는다. 닫힌 초안은 `true`, 나머지는 `false`다. 앱은 구버전 서버와 호환되도록 필드를 선택적으로 읽는다. 다른 기기에서 폐기했거나 상태가 APPROVED·FAILED가 됐다면, 같은 입력으로 새 수동 생성이나 다시 짜기를 시작할 때 새 키를 사용한다.

배포 전에는 비노출 원본과 다시 짠 초안의 관계를 저장하지 않았다. 같은 사용자가 원본보다 나중에 만든 미추적 수동 초안 중 두 원본 번호가 모두 비어 있는 행이 후보가 된다. 영상 선택은 다시 짤 때 바꿀 수 있어 영상 목록만으로 원본을 확정할 수 없다.

후보에 PENDING·PROCESSING 작업이나 마지막 갱신 후 24시간이 지나지 않은 NEEDS_INPUT 질문이 하나라도 있으면 503을 반환한다. 질문은 그대로 두므로 사용자가 답할 수 있다. 503 때 받은 UUID는 최초 대기 시각부터 24시간 동안 같은 입력의 다음 접수를 기다린다. 서버는 그 초안을 저장하는 트랜잭션에서 대기 키들을 모두 초안에 연결한다. 다른 기기가 곧바로 승인해도 대기 키의 재접수는 같은 202와 ID를 반환한다. 후보가 모두 마지막 갱신 후 24시간 이상 지난 질문이면 유효한 새 요청을 202로 접수하면서 그 질문들을 만료 처리한다. 만료된 질문에 뒤늦게 답하면 409다.

409 응답 예시

```json
{
  "code": "DRAFT_REPLACEMENT_IN_PROGRESS",
  "message": "이 일정을 이미 다시 짜고 있어요.",
  "status": 409,
  "traceId": "d41ffc4d-3767-4c19-bcfa-f082c9de8821",
  "activeDraftId": 42
}
```

`activeDraftId`는 진행 중인 대체 초안의 숫자 ID다. `traceId`는 응답 헤더 `X-Trace-Id`와 같다.
