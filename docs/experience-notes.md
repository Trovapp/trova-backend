# 작업 경험 기록

판단이 필요했던 작업마다 문제, 고른 방법과 이유, 확인한 범위를 남긴다.
"이유"는 작업 중 사용자와 나눈 대화에서 사용자가 말한 내용을 근거로 쓴다.

---

## 2026-09-30 AI 대화가 끊기고, 찾지도 않은 장소를 찾았다고 답함 (#69, PR #70)

### 문제와 조건
- 권한 경계 QA(다른 사용자 데이터 접근 시도, 31개 API 모두 404로 통과) 중에 AI 대화 이상을 발견했다.
- 운영 서버(Oracle)에서 대화 5번: 2번은 정확히 5초에 `Read timed out`으로 끊겨 "지금 답변을 가져오지 못했어요", 3번은 "카드로 보여드릴게요"라고 답했지만 후보 0개.
- 같은 시각 외부 호출 기록(`api_call_logs`)에 장소 검색(google-places) 0건 → Gemini가 찾기 도구를 부르지 않고 말만 했다.
- 조건: 무료 Gemini(`gemini-3.5-flash-lite`), 도구 호출 모드 AUTO, 앱은 AI 응답을 60초까지 기다림, 대화 호출은 공용 HTTP 설정(읽기 대기 5초)을 그대로 씀.

### 범위
- A(5초 시간 초과), B(찾지 않고 찾았다고 말함), C(도구가 불리면 느려지는 응답 속도) 중 **A + B**. 사용자가 "2번으로 진행해줘"로 선택했다. C는 이번 범위에서 뺐다.

### 선택한 방법과 이유 (비교한 대안 포함)
- A: **대화 호출만 읽기 대기 20초**(A1)를 골랐다.
  - 비교한 대안: 공용 설정을 20초로(A2, 다른 API도 장애 때 20초씩 붙잡힘), 5초 유지 + 재시도 1번(A3, 느린 상태가 이어지면 둘 다 실패하고 무료 한도를 더 씀).
- B: **지시문 수정**(B1)을 골랐다.
  - 비교한 대안: 도구 호출 강제 ANY(B2, 실측에서 "고마워"에도 장소 검색을 함), 지시문 + 서버 단어 검사(B3, 정상 답변을 잘못 바꿀 수 있음).
- 이유: 비교표와 함께 A1 + B1을 두 단계로 나눠 진행하자고 제안했고, 사용자가 "응 그렇게 진행해줘"라고 승인했다. 사용자가 따로 밝힌 이유는 없다.

### 확인한 것
- A: 6초 뒤 응답하는 실제 HTTP 서버로 테스트했다. 공용 5초 설정은 끊기는 것(재현)과 대화 클라이언트는 받는 것(수정)을 확인했다. 대기를 5초로 되돌리면 테스트가 실패하는 것도 확인했다. MockRestServiceServer는 네트워크를 타지 않아 대기 시간을 검사할 수 없어서 실제 서버를 썼다.
- B: 로컬(Mac)에서 Gemini를 직접 호출해 지시문마다 54번 측정했다(`docs/benchmarks/2026-09-30-chat-tool-calling.md`).
  - 장소 찾기 도구 호출: #54 이전 46% → 수정 전 21% → 수정 후 100%(24/24).
  - 찾지 않고 찾았다고 한 답: 19번 → 0번.
  - 일반 대화 18/18 정상.
- 원인 추적: 운영 기록상 9/15~9/18에는 도구가 불렸고 9/30에는 0번이었다. 그 사이 변경은 기호 금지 규칙(#54) 하나였고, #54 전후 지시문을 같은 조건으로 재서 호출률 하락(46% → 21%)을 확인했다.
- 도구 흐름 첫 실동작: 이 흐름은 수정 전에는 운영에서 사실상 돌지 않았다.
  - 로컬 서버(개발 DB): 찾기 요청 3개 모두 후보 7개.
  - 운영 서버(Oracle, 배포 후): 찾기 요청 3개 모두 후보 7개(10.3~18.1초). "고마워"는 도구 없이 1.1초.
- 측정 기준 수정: 처음 판정식은 "찾아드릴까요" 같은 제안도 거짓 카드로 잡았다. "이미 찾았다" 표현만 잡도록 좁히고, 세 지시문을 같은 기준으로 다시 집계했다.

### 확인하지 않은 것
- 두 번째 메시지 이후 대화와 note_preference("그거 좋다") 호출.
- AUTO 모드는 확률적이라 54회 표본의 100%가 항상 보장되지는 않는다.
- Gemini가 20초보다 느린 경우(측정 중 40.9초 1번)는 여전히 끊긴다. 느린 상황은 가짜 서버로만 재현했다.
- 빈 시간 추천은 로컬, 운영 모두 도구는 불렸지만 후보 0개. 데이터 문제인지 기능 문제인지 확인하지 않았다.
- 응답 속도(C): 도구가 불리면서 1초 → 10~18초. 운영 기록으로 나눠 보면 대부분 장소 임베딩을 하나씩 만드는 시간이다(19개 × 약 0.4초 = 약 9초).

## 2026-09-30 처음 보는 지역의 첫 AI 대화가 느림 (#73, PR #74)

### 문제와 조건
- #69로 AI 대화가 실제로 장소 찾기 도구를 부르게 되면서 응답이 1초에서 10~18초로 늘었다.
- 운영 기록으로 나눠 보니 가장 큰 부분이 새 장소 임베딩을 하나씩 만드는 시간이었다(김해 19개 약 9.2초, 전주 16개 약 8.4초).
- 한 번 만든 임베딩은 DB에 저장돼 다시 만들지 않으므로, 느린 건 처음 보는 지역의 첫 검색이다.
- 조건: 무료 Gemini `gemini-embedding-001`(분당 100, 하루 1,000, 문장 수로 셈), 운영 서버는 Oracle E2.1.Micro, DB는 Supabase.

### 범위
- 임베딩만(태그 붙이기 약 4초는 제외). 사용자가 "1번이랑 C1으로 진행해줘"로 선택했다.
- 이에 앞서 사용자는 "대화가 느려지면 그록으로 대체해야하는거 아니야?"라고 물었다. 시간 분해 결과 Gemini 대화 호출은 약 2초(11%)였고, 가장 큰 병목인 임베딩은 Groq에 API가 없어 대체로 해결되지 않는다고 답했다. 그 뒤 C 작업이 결정됐다.

### 선택한 방법과 이유 (비교한 대안 포함)
- **C1. `batchEmbedContents`로 한 번에 묶어 요청.**
  - 비교한 대안: C2 동시 요청(예상 2~3초, 작은 서버에 동시 연결 부담), C3 응답 뒤 백그라운드로 미루기(첫 검색의 정렬 품질이 떨어짐).
- 이유: 비교표에서 C1을 추천했고, 사용자가 "1번이랑 C1으로 진행해줘"로 골랐다. 사용자가 따로 밝힌 이유는 없다.

### 확인한 것
- 로컬(Mac) 직접 호출: 19개를 하나씩 9.92초, 묶음 1.34초. 결과 벡터가 같다(코사인 1.0).
- 테스트:
  - 새 장소 N개면 묶음 요청 1번(하나씩 요청 0번), 장소마다 맞는 벡터 저장.
  - 기존 임베딩은 제외, 101개는 100+1로 나눠 요청.
  - 묶음 실패 시 저장하지 않고 실패도 문장 수만큼 기록, 한 장소 저장 실패는 나머지에 영향 없음.
  - 요청 본문 형태 확인.
- 운영 서버(Oracle):
  - 수정 전(전주) 첫 대화 16.9초, 임베딩 약 8.4초.
  - 수정 후(강릉) 첫 대화 13.9초, 임베딩 묶음 1.23초.
  - 새 임베딩 수는 둘 다 16개.

### 확인하지 않은 것
- 임베딩 생성은 7초 넘게 줄었지만 첫 대화는 3초만 줄었다. 묶음 요청 뒤 약 4.3초 구간(장소마다 DB에 한 번씩 저장하는 시간으로 추정)은 측정으로 확인하지 않았다.
- 수정 전후 지역이 다르다(같은 지역은 이미 임베딩이 생겨 다시 잴 수 없음).
- 하루 한도 소진 때 묶음 요청의 실제 실패 형태, 100개 가까운 묶음의 응답 시간(공용 대기 5초).

## 2026-10-01 임베딩 묶음 요청 뒤에도 남은 4.3초 찾기와 DB 묶음 전송 (#77 PR #78, #79 PR #80)

### 문제와 조건
- #73(임베딩 묶음 요청) 뒤 운영 첫 대화가 16.9초 → 13.9초로 3초만 줄었다. 임베딩 요청 뒤 약 4.3초 구간의 원인을 몰랐다.
- 처음엔 "장소마다 DB에 저장하는 시간"으로 추정했지만, 운영 서버 안에서 잰 DB 읽기 왕복이 약 30ms라 저장 16번+조회 19번으로는 약 1초밖에 설명되지 않았다. 추정이 틀렸다.

### 범위
- 원인 확인: 사용자가 "1번 진행해줘"(구간별 시간을 서버 로그에 남겨 확인)로 골랐다.
- 고칠 범위: 로그 결과로 후보 A~E(호출 기록, 임베딩 UPDATE, 개인화 조회, 카탈로그 저장, 실내 태그)를 보여줬고, 사용자가 "A + B로 진행해줘"로 골랐다.

### 선택한 방법과 이유 (비교한 대안 포함)
- 원인 확인: 요청마다 구간별 시간을 로그 한 줄로 남겼다(동작 변경 없음).
  - 운영 결과: 임베딩 구간 4288ms = 요청 1501 + 저장 1263 + 나머지 약 1.5초(호출 기록 18줄을 JPA로 한 줄씩 저장).
  - 내가 #73에서 만든 "문장마다 한 줄" 기록 방식이 원인 중 하나였다.
- A(호출 기록): **A1. 문장마다 한 줄 유지 + JdbcTemplate.batchUpdate**.
  - 비교한 대안: A2 묶음당 한 줄 + 문장 수 칸 추가(줄 수와 한도 사용량이 달라져 통계를 바꿔야 함), A3 비동기 기록(서버가 죽으면 기록 유실).
  - id가 IDENTITY라 Hibernate가 INSERT를 묶지 못해서 JPA 대신 JDBC로 보냈다.
- B(임베딩 UPDATE): **B1. batchUpdate**.
  - 비교한 대안: B2 한 문장 VALUES(15ms 더 빠르지만 SQL 조립이 복잡), B3 트랜잭션 하나로만 감싸기(실측 297 → 220ms로 효과 작음).
- 이유: 개발 DB 실측표와 함께 A1 + B1을 추천했고, 사용자가 "A1 + B1으로 진행해줘"로 골랐다. 사용자가 따로 밝힌 이유는 없다.

### 확인한 것
- 개발 DB 실측(로컬 Mac, 18건): UPDATE 297 → 54ms, INSERT 209 → 31ms. 커밋 횟수가 아니라 왕복 횟수가 시간을 좌우했다.
- 로컬 서버(개발 DB) 강릉: 임베딩 저장 558 → 27ms. 새 장소 16곳 모두 실제 Postgres에 저장되고, 기록 16줄이 같은 시각에 들어갔다.
- 운영 서버(Oracle) 부산, 새 장소 20곳:
  - 임베딩 저장 1263 → 202ms, 임베딩 구간 4288 → 1498ms.
  - 첫 대화 13.8초(제주, 이전) → 9.9초.
- 테스트:
  - 묶음 전송 1번(개별 UPDATE 0번), 101곳은 100+1로 분할.
  - 묶음 저장 실패 시 예외 없음.
  - 묶음 INSERT 줄이 JPA 엔티티로 그대로 읽힘(H2 통합 테스트).

### 확인하지 않은 것
- 벡터 UPDATE SQL은 H2에서 돌릴 수 없어서 개발 DB와 운영으로만 확인했다.
- 묶음 저장 중 한 건 실패 시 전체 실패(받아들인 트레이드오프)는 테스트로만 확인했다.
- 운영 측정은 지역이 다르다(제주 → 부산).
- 남은 구간(실내 태그 약 2.3~2.9초, 카탈로그 저장 약 1.5초, 개인화 조회 약 1.5초)은 이번 범위 밖이다.

## 2026-10-02 영상 기록에 이미 다시 시도된 영상의 실패 카드가 계속 남음 (#83, PR #84)

### 문제와 조건
- 디자인 작업 중 캡처에서 발견했다. 운영 사용자 계정의 영상 기록 맨 위에 "처리에 실패했어요" 카드 4장(작업 17, 18, 25, 26)이 계속 보였다.
- 운영 DB(읽기 전용)로 확인한 것:
  - 모두 9/5와 9/17의 실패이고, 세 영상 모두 나중에 다시 분석돼 성공했다.
  - CXdphBD0I_k는 30초 간격으로 두 번 실패해 카드가 두 장이었다.
  - `?si=`가 붙은 예전 주소도 저장돼 있다.
- 원인: `/api/places/pending`이 FAILED를 전부 내려주고, 같은 영상의 이후 작업과 비교하지 않았다.

### 범위
- S1(나중에 성공한 영상의 실패 숨김) + S2(같은 영상 실패는 최신 하나). 사용자가 "S1 + S2 + M1로 진행해줘"로 골랐다.
- S3(오래된 실패 자동 정리), S4(실패 이유 문구), S5(데이터 삭제)는 뺐다.

### 선택한 방법과 이유 (비교한 대안 포함)
- **M1. 서버 처리 목록 API에서 거르기.** 규칙은 "실패 카드는 그 영상의 가장 최근 작업이 실패일 때만"이다.
  - 같은 영상은 정식 주소(ShareUrl)로 비교한다.
  - 실패가 없으면 추가 조회를 하지 않는다(분석 중 몇 초마다 폴링되는 API).
  - 비교한 대안: M2 앱에서 거르기(웹은 그대로, 규칙이 두 곳), M3 성공하면 실패 작업 DB 삭제(실패 기록이 사라짐).
- 이유: 데이터를 지우지 않고 보이는 것만 정리하는 안을 추천했고, 사용자가 그대로 골랐다. 사용자가 따로 밝힌 이유는 없다.

### 확인한 것
- 테스트 5개(4개는 구현 전 실패 확인):
  - 나중에 성공 → 빠짐, 여러 번 실패 → 최신만, 다시 시도 중 → 처리 중만
  - 주소 형식이 달라도 같은 영상, 다른 영상의 성공은 영향 없음(대조군)
- 운영 서버(Oracle) 반영 뒤 사용자 계정 영상 기록 캡처: 실패 카드 4장이 모두 사라졌다.
- 처음엔 "2장 남는다"고 예측했는데, 운영 DB를 다시 보니 세 영상 모두 이후 성공해 4장 모두 사라지는 게 맞았다. 예측을 고쳐 보고했다.

### 확인하지 않은 것
- 사용자가 성공 결과를 지운 영상의 예전 실패도 계속 숨겨진다(의도로 판단, 사용자 확인 전).

## 2026-10-02 같은 영상을 다시 넣으면 성공 결과가 또 생겨 영상 기록에 여러 번 보임 (#87, PR #88, 앱 bdd4228)

### 문제와 조건
- Q1 확인 캡처에서 발견했다. 영상 기록에 "만남의 장소 1순위 사당에서 노는법"이 3줄로 보였다.
- 운영 DB(읽기 전용)로 확인한 것:
  - 같은 영상의 성공 결과가 여럿이었다: 김해 5번, 사당 3번, 안산 3번, 김포·제주·청라 각 2번(청라는 주소 형식이 다름).
  - 결과마다 장소 묶음이 따로 있다.
- 원인: 공유 API는 처리 중인 같은 영상만 막고, 이미 성공한 영상은 새로 분석해 장소를 또 저장했다.

### 범위
- S1(앞으로 중복 막기) + S2(영상 기록에 같은 영상은 하나만). 사용자가 "S1 + S2, R1, 서버 처리로 진행해줘"로 골랐다.
- S3(기존 중복 데이터 정리)는 사용자 데이터 삭제라 뺐다.

### 선택한 방법과 이유 (비교한 대안 포함)
- 대표 결과는 **R1. 장소가 남아 있는 결과 중 가장 최근.**
  - 비교한 대안: R2 일정이 있는 결과 우선(오래된 분석이 대표가 될 수 있음), R3 장소가 가장 많은 결과(오탐이 많은 예전 결과가 뽑힐 수 있음).
- 서버 처리:
  - 공유 API는 이미 분석한 영상이면 `200 {jobId, DONE, alreadyAnalyzed}`를 준다. `reanalyze: true`면 새로 분석하고, 장소를 모두 지운 영상도 새로 분석한다.
  - 장소 목록 API는 대표 결과의 장소만 내려준다.
  - 같은 영상 판단은 `ShareUrl.videoKey`(정식 주소)로 하고, Q1의 처리 목록 거르기와 공유한다.
- 이유: 비교표와 함께 추천했고, 사용자가 그대로 골랐다. 사용자가 따로 밝힌 이유는 없다.
- **진행 중 발견:** 앱에는 이미 "이미 저장한 영상이에요 → 새로 분석 / 보러 가기" 확인이 있었다.
  - 서버만 바꾸면 사용자가 고른 "새로 분석"이 무시되는 문제가 생긴다.
  - 그래서 앱에서 새로 분석과 실패 영상 다시 시도를 `reanalyze: true`로 바꾸고, "이미 분석함" 응답이면 결과 화면으로 바로 가게 했다.
  - 서버와 앱을 같이 배포했다(사용자: "앱 단계 진행하고 머지 후 배포해줘").

### 확인한 것
- 서버 테스트 5개(4개는 구현 전 실패 확인):
  - 이미 분석 → 기존 결과, 여러 결과 → 장소 있는 최신, reanalyze → 새로 분석, 장소 모두 지움 → 새로 분석(대조군)
  - 목록 API: 주소 형식이 달라도 같은 영상의 최신 결과만
- 운영 서버(Oracle) 반영 뒤 사용자 계정 영상 기록: 사당 3줄 → 1줄, 김포 2줄 → 1줄.
  - 운영 DB 계산으로 장소 있는 결과 20개가 영상 10개로 묶이는 것과 대조했다.

### 확인하지 않은 것
- 앱의 "새로 분석"과 "이미 분석함" 이동을 실제로 눌러 보지 않았다. 새로 분석은 사용자 계정에 새 결과를 만들기 때문이다.
- 화면 아래쪽(청라, 제주)은 스크롤이 필요해 캡처하지 못했다(DB 계산으로 대신).
- 숨겨진 예전 결과의 장소는 DB에 남아 있다(S3 미진행).
- 예전 결과로 만든 여행은 그대로 있다.

  - 고친 뒤: 3번 모두 통과(작업 1개, 5개 응답 모두 같은 jobId).
- 기존 공유 테스트 18개 통과, `./gradlew build` 통과.

- 앱의 빠른 두 번 누르기는 탭 자동화로 재현할 수 없어 코드로만 확인했다.

## 2026-10-03 장소 상세에 전화번호 (#99)

### 문제와 조건
- 찜한 장소 상세는 장소 카탈로그(Google 장소) 정보라 전화번호가 없어 전화 버튼을 둘 수 없었다(영상 속 장소 상세에는 있음).
- Google 장소 상세(리뷰)는 장소마다 처음 한 번만 받고 요약을 저장해 다시 쓴다. 운영 707곳 중 35곳이 이미 요약됐다(찜한 장소 4곳 포함).
- 비용(공식 문서·가격표, 2026-10-03 확인)
  - 요청 하나는 그 안의 가장 높은 티어 하나로 과금된다.
  - 리뷰는 Enterprise + Atmosphere, 전화번호는 Enterprise 티어다. 둘 다 월 1,000건 무료다.
  - 이번 달 운영 place-details 호출은 1건이었다.

### 선택한 방법과 이유
- 사용자가 "P3로 진행해줘"로 골랐다(P1 + 기존 장소 채우기).
  - 비교한 대안: P1만(기존 35곳은 번호 없음), P2 카카오에서 이름·좌표로 찾기(다른 지점이 잡힐 위험).
  - 사용자가 "구글 디테일 무료로 가능한거지?"라고 물어 가격표와 이번 달 호출 수를 확인했다.
- 처음 상세를 만들 때는 리뷰 요청에 `nationalPhoneNumber`를 더한다(같은 티어라 추가 비용 없음).
- 이미 요약된 장소는 35곳을 한꺼번에 받지 않는다. 상세를 처음 열 때 전화번호만 요청(Enterprise 티어)하고 `phone_checked_at`을 남겨 다시 묻지 않는다(제 판단 — 실제로 열어 본 장소만 호출된다).
- 상세 응답(장소·여행 장소)에 `phone`을 넣었다. 앱은 번호가 있을 때만 전화 버튼을 보여준다.

### 확인한 것
- 테스트
  - 처음 상세에서 함께 받은 번호 저장(전화번호 별도 요청 없음).
  - 요약 있는 장소는 번호만 한 번 요청하고 두 번째는 저장값을 쓴다(리뷰는 다시 받지 않음).
  - 번호 없는 장소도 확인 표시해 다시 요청하지 않는다.
  - 요청 실패 시 상세는 그대로 주고 다음에 다시 시도한다.
  - 서비스 테스트 13개, 여행 컨트롤러 32개, `./gradlew build` 통과.
- 로컬(개발 DB, 실제 Google): 요약 있는 장소(41) 상세를 두 번 요청 → 전화번호만 요청 1건, 응답·DB에 번호 저장, 두 번째는 호출 없음.

### 확인하지 않은 것
- 운영 반영 전이다.
- 따로 찾은 문제: 개발 DB의 "가야랜드"(41) 카탈로그 항목이 김해가 아닌 파주 가야랜드(경기)로 저장돼 있었다. 이름으로 Google 장소를 찾을 때 다른 지역 장소가 잡힌 것이라 이번 범위에서 뺐다.

## 2026-10-03 여행 장소 상세가 같은 이름의 다른 지역 장소로 연결됨 (#101)

### 문제와 조건
- 개발 DB에서 김해 "가야랜드" 여행 장소가 파주 가야랜드(341km 떨어짐)로 연결돼 있었다. 전화번호 작업(#99) 중 031 번호가 붙어 알게 됐다.
- 원인: `TripService.resolveDetailsPlace`는 Google 장소 ID가 없는 여행 장소를 이름만으로 검색해 1등 결과를 연결했다.
- 운영(읽기만): 연결된 여행 장소 12곳은 모두 3km 안으로 정상이었다. 미연결 11곳은 같은 위험이 있었다.
- 잘못 연결되면 다른 장소의 리뷰 요약·전화번호가 보이고, 취향 기록·임베딩도 그 장소로 쌓인다.

### 선택한 방법과 이유
- 사용자가 "R3로 진행하고 개발 DB 연결도 지워줘"로 골랐다.
  - 비교한 대안: R1 지역만 붙이기(1등이 여전히 틀릴 수 있음), R2 거리만 확인.
- 검색어에 여행 장소 지역을 붙인다("김해 가야랜드"). 이름에 이미 지역이 있으면 그대로 둔다.
- 여행 장소 좌표가 있으면 검색 결과 중 3km 안의 첫 결과만 연결하고, 없으면 연결하지 않는다.
  - 3km는 제 판단이다. 큰 시설과 지역 중심으로 대신한 좌표를 감안했고, 다른 지역(수십~수백 km)은 확실히 걸러진다.
  - 좌표가 없는 여행 장소는 확인할 방법이 없어 지역을 붙인 검색 1등을 쓴다.
- 앱: 상세를 못 받으면(404 등) "만들고 있어요 0%"에서 멈추던 것을 "리뷰 정보를 찾지 못했어요" 안내로 바꿨다.
- 개발 DB: 여행 장소 1의 잘못된 연결과 그때 쌓인 취향 기록 1건을 지웠다. 파주 장소 자체는 실제 장소라 카탈로그에 남겼다.

### 확인한 것
- 테스트
  - 다른 지역 결과만 있으면 연결하지 않는다.
  - 1등이 멀고 2등이 가까우면 2등을 연결한다.
  - 거리 확인을 빼면 두 테스트가 실패하는 것도 확인했다.
  - 여행 서비스 26개, 여행 컨트롤러 32개, `./gradlew build` 통과.
- 로컬(개발 DB, 실제 Google 검색): 연결을 지운 여행 장소 1의 상세를 다시 열었다. 김해 "가야랜드 엔젤파크"(경상남도 김해시 인제로 368, 055 번호)로 연결됐다.

### 확인하지 않은 것
- 운영 반영 전이다.
- 근처 결과가 없어 연결되지 않은 장소는 상세를 열 때마다 검색이 다시 나간다(드문 경우라 저장하지 않았다).
- 3km 안의 같은 이름 다른 지점(체인점 등)은 여전히 1등이 잡힐 수 있다.
