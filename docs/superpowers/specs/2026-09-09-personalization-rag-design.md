# 개인화 추천(RAG 기반) Phase 1 — 설계 스펙

> **v2 수정**: 처음 버전은 검색(Retrieval)만 있고 생성(Generation)이 없어서
> 엄밀히는 RAG가 아니라 "임베딩 기반 랭킹"이었다. 대화형 비서(Phase 2) 전체를
> 끌어오지 않고도 완전한 RAG로 만들 수 있는 최소 단위(추천 이유 한 줄 생성)를
> 이번 수정에서 Phase 1에 포함시켰다 — "생성 단계(Generation)" 절 참고.

## 배경

트로바는 인스타/유튜브 여행 영상에서 장소를 추출해 지도에 정리해주는 서비스다.
2026-09-08에 "대안 찾기"(⑤ 대안 찾기+교체, ⑥ 빈 시간 추천, ⑦ 날씨 경보 연동)
기능이 완성되어 배포됐고, 여기에 사용자별 개인화를 얹고 싶다는 요청에서 이 스펙이
시작됐다.

기존에도 개인화 시도가 하나 있었다 — `UserPreference`(mood 점수)가 북마크할 때마다
`Place.mood`(Gemini 태깅) 점수를 올려서 `RecommendationService`의 랭킹에 반영한다.
다만 이 방식은 "북마크"라는 단일 신호만 쓰고, mood라는 한 가지 축으로만 취향을
표현해서 표현력이 제한적이다.

이번 요청은 이걸 넘어서 "RAG 기반의 완전한 개인 AI 에이전트"를 원한다는 것이었고,
브레인스토밍을 거쳐 범위가 두 단계로 나뉘었다:

- **Phase 1(이 스펙)**: 개인화 데이터 모델 + RAG 검색(Retrieval) 로직을 만들어
  대안 찾기/빈 시간 추천의 랭킹에 반영하고, 검색된 근거를 그대로 프롬프트에
  넣어 "추천 이유" 한 줄을 생성(Generation)한다 — Retrieval과 Generation이
  둘 다 있어 이 자체로 완전한 RAG다. 다만 여러 턴을 주고받는 대화형
  인터페이스는 없다(단발성 생성 한 번뿐).
- **Phase 2(별도 스펙, 이후 진행)**: Phase 1의 검색 로직과 "추천 이유" 생성
  패턴을 그대로 재사용해서 여러 턴을 주고받는 반구조화 대화형 비서로
  확장한다(제안 버튼 중심 + 짧은 자유 입력, 턴/토큰 제한). 완전 자유 채팅보다
  구조화된 상호작용을 선호하는 게 실제 여행 AI 앱들(Mindtrip, Stardrift 등)의
  공통된 패턴이라 이 방향으로 잡았다.

**타겟층**: 트로바의 핵심 동작(영상 링크 → 장소 추출)이 숏폼 여행 콘텐츠를
소비하는 사람을 전제로 하므로, 20~30대 소셜미디어 사용층을 기준으로 설계한다.
시니어층 등 다른 타겟을 위한 UI/입력방식 재설계는 이 스펙의 범위 밖이다.

## 목표

- 사용자가 과거에 좋아했던 장소(북마크/여행에 담음/대안 교체 선택 등)와
  의미적으로(semantic) 비슷한 후보를, 대안 찾기·빈 시간 추천 결과에서 더
  위로 올린다.
- 무료 티어 원칙을 지킨다 — 검색 요청마다 무한정 Gemini 호출이 늘지 않게
  설계한다(임베딩은 장소 태깅 시점에 1회만 계산, 생성 호출은 요청당 최대
  1~2회로 제한).
- 신규 사용자(신호 없음)는 기존과 동일하게 동작한다(콜드스타트에서 깨지거나
  이상하게 보이면 안 됨).
- 검색(Retrieval)한 근거를 버리지 않고 생성(Generation)에 재사용해서, 이
  Phase만으로도 정직하게 "RAG를 썼다"고 말할 수 있는 최소 단위를 만족한다.

## 범위 밖(Out of scope, Phase 1)

- 여러 턴을 주고받는 대화형 인터페이스(Phase 2) — Phase 1의 생성은 "추천
  이유" 한 줄을 만드는 단발성 호출뿐, 사용자가 되묻거나 대화를 이어가는
  기능은 없다.
- 부정 신호(대안 후보로 보여줬지만 안 고른 것) — v1은 긍정 신호만
- 기존 `UserPreference`/mood 점수 시스템 변경 — `RecommendationService`는
  그대로 mood 기반 부스트를 계속 쓴다. 이 스펙은 `AlternativeFinderService`와
  `GapRecommendationService`에만 새 개인화 점수를 추가한다. 두 시스템을
  나중에 통합할지는 Phase 1 완료 후 실사용 데이터를 보고 별도로 판단한다.
- 임베딩 모델/차원의 최종 확정 — 아래 "임베딩 생성"에 초기값을 제시하지만,
  구현 시점에 Gemini API 최신 문서로 재확인해야 한다(모델 스펙은 자주
  바뀐다).

## 데이터 모델

### `places` 테이블에 컬럼 추가

```
ALTER TABLE places ADD COLUMN embedding vector(768);
CREATE INDEX places_embedding_idx ON places USING ivfflat (embedding vector_cosine_ops);
```

`vector(768)`는 초기값이다 — `gemini-embedding-001`의 실제 출력 차원을 구현
시점에 확인해서 맞춘다. `ddl-auto: update`는 pgvector 확장 설치나 `vector`
타입 컬럼을 만들지 못하므로, Task 9의 Notification 마이그레이션과 동일하게
**수동 SQL 마이그레이션이 필요하다**(로컬/개발 환경에서 수동 실행, 사용자
확인 후 진행):

```sql
CREATE EXTENSION IF NOT EXISTS vector;
ALTER TABLE places ADD COLUMN IF NOT EXISTS embedding vector(768);
CREATE INDEX IF NOT EXISTS places_embedding_idx ON places USING ivfflat (embedding vector_cosine_ops);
```

애플리케이션 코드에서 `vector` 타입을 다루려면 Hibernate에 커스텀 타입
매핑이 필요하다(예: `pgvector-java`의 Hibernate 6 지원, 또는 네이티브 쿼리로
우회). 정확한 라이브러리/버전은 구현 계획 단계에서 정한다.

### 새 테이블: `user_preference_signals`

사용자의 긍정 신호 이력. 임베딩 자체는 저장하지 않고 `place_id`로
`places.embedding`을 조인해서 쓴다(중복 저장/재계산 방지, `Place`가 이미
캐싱되는 것과 같은 원칙).

```sql
CREATE TABLE user_preference_signals (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id),
    place_id BIGINT NOT NULL REFERENCES places(id),
    signal_type VARCHAR(32) NOT NULL,
    created_at TIMESTAMP(6) NOT NULL
);
CREATE INDEX user_preference_signals_user_idx ON user_preference_signals(user_id);
```

`signal_type`은 자유 텍스트가 아니라 고정 enum(`SignalType`)으로 관리한다 —
`BOOKMARK`, `TRIP_PLACE_ADDED`, `ALTERNATIVE_REPLACED`, `GAP_INSERTED`,
`VIDEO_PLACE_MATCHED`. v1에서는 5개 타입 모두 동일 가중치(1.0)로 취급한다.
같은 사용자가 같은 장소에 대해 여러 신호를 남기는 것(예: 북마크했다가 나중에
여행에도 담음)은 막지 않는다 — 중복이 곧 그 장소를 더 좋아한다는 신호이므로
그대로 둔다.

## 임베딩 생성 파이프라인

**핵심 원칙: 임베딩은 검색 시점이 아니라 장소 태깅 시점에 1회만 계산한다.**
`PlaceTaggingRunner`가 장소당 Gemini를 1번 호출해서 mood/space를 태깅하는
바로 그 지점에 임베딩 생성도 얹는다. `Place`는 `googlePlaceId`로 캐싱되므로
(`PlaceCatalogService.upsertAll`), 한 번 계산된 임베딩은 재계산되지 않는다.

반대로 "대안 찾기"를 탭할 때마다 후보 10~20개를 즉석에서 임베딩하면 매 검색마다
Gemini 호출이 그만큼 추가되어 무료 티어 한도(현재 STT+장소추출+리뷰요약+태깅이
이미 나눠 쓰고 있는 한도)를 압박한다. 이걸 피하는 게 이 설계의 핵심 제약이다.

- **입력 텍스트**: `name + category + mood + reviewSummary`(있으면)를 합친
  문자열. `reviewSummary`가 아직 없는 신규 장소는 `name + category + mood`만
  사용(빈 리뷰 요약을 기다리지 않는다 — 태깅과 리뷰 요약은 별도 파이프라인이라
  타이밍이 다를 수 있음).
- **모델**: `gemini-embedding-001`(2026년 기준 `text-embedding-004` 후속,
  무료 티어 한도가 생성 모델보다 훨씬 넉넉한 것으로 확인됨 — 정확한 RPM/TPM은
  구현 시 재확인). 기존 `PlaceTaggingRunner`와 같은 python subprocess 패턴을
  재사용하거나, 임베딩은 응답 구조가 단순해서 Java에서 직접 REST 호출해도 됨
  — 구현 계획 단계에서 결정.
- **실패 처리**: 임베딩 생성이 실패해도(429, 타임아웃 등) 태깅 자체는
  실패시키지 않는다 — `embedding`이 `null`인 장소는 개인화 점수 계산에서
  제외될 뿐, 태깅 파이프라인의 다른 부분(mood/space)에는 영향 없음. 이번
  세션의 최종 리뷰에서 확립한 "부가 기능 실패가 본 기능을 죽이면 안 된다"
  원칙을 그대로 따른다.

## 신호 수집 (v1: 긍정 신호만)

실제 코드를 확인해서 정리한 5개 지점. 전부 이미 `Place` 카탈로그 행을
참조하는 지점이라(임베딩을 가진 행), 새로 매칭 로직을 만들 필요 없이 신호
기록만 얹으면 된다.

| # | 지점 | 신호 타입 | 비고 |
|---|---|---|---|
| 1 | `BookmarkService`의 북마크 생성 | `BOOKMARK` | 기존 `UserPreference` mood 점수 갱신과 같은 자리에 추가 |
| 2 | `TripService.addPlaceToDay` | `TRIP_PLACE_ADDED` | 검색해서 여행에 담을 때 |
| 3 | `TripService.replacePlace` | `ALTERNATIVE_REPLACED` | 대안 찾기에서 교체를 선택한 새 장소 — 이번에 만든 기능이 직접 개인화 신호가 됨 |
| 4 | `TripService.insertPlaceAfter` | `GAP_INSERTED` | 빈 시간 추천에서 선택 |
| 5 | `TripService.resolveDetailsPlace` | `VIDEO_PLACE_MATCHED` | 영상에서 자동 추출된 장소(`PlaceSource.VIDEO`)가 카탈로그와 매칭되는 바로 그 시점. **이게 없으면 트로바의 핵심 기능(영상→장소 추출)에서 나온 장소들이 개인화에 전혀 반영되지 않는다** — 이미 있는 매칭 로직(리뷰 요약 조회용으로 만들어진 것)에 신호 기록 한 줄만 추가 |

각 지점에서 신호를 기록할 때 `place.getEmbedding() == null`이면(아직 태깅
전) 신호 기록을 건너뛴다 — 어차피 랭킹 시점에 쓸모없는 신호이고, 나중에
그 장소가 태깅되면서 임베딩이 생겨도 신호를 소급 기록하지는 않는다(v1은
단순하게 간다 — 사용자가 이후에 같은 장소로 다시 신호를 남기면 그때 잡힘).

## 랭킹 통합

새 서비스 `PersonalizationService`:

```java
double personalizationScore(User user, Place candidate)
```

- `candidate.getEmbedding() == null`이면 0.0 반환(태깅 전 장소는 개인화 대상
  아님).
- 그 외에는 pgvector 코사인 유사도로 이 사용자의 `user_preference_signals`
  중 상위 K=5개 유사 신호를 찾아 평균 유사도를 반환한다(네이티브 쿼리 1회):

```sql
SELECT AVG(similarity) FROM (
  SELECT 1 - (p.embedding <=> :candidateEmbedding) AS similarity
  FROM user_preference_signals s
  JOIN places p ON s.place_id = p.id
  WHERE s.user_id = :userId AND p.embedding IS NOT NULL
  ORDER BY p.embedding <=> :candidateEmbedding
  LIMIT 5
) top_k;
```

신호가 없는 사용자는 이 쿼리가 빈 결과를 반환하고, `personalizationScore`는
0.0을 반환한다(콜드스타트 = 기존 동작과 동일).

**적용 대상**: `AlternativeFinderService`, `GapRecommendationService`.
지금 두 서비스는 필터만 통과시키고 정렬을 하지 않는다(순서는 Google Places
응답 순서 그대로) — 이번에 정렬을 새로 추가하면서 개인화 점수로 부스트한다.
기본 점수 함수는 `RecommendationService.score()`(`rating * log(reviewCount+1)`)와
동일한 형태를 재사용한다 — 지금 두 곳(`RecommendationService`, 이번에 추가될
곳)에 중복되므로 `recommendation` 패키지에 공용 유틸(`PlaceScoring.baseScore(Place)`
같은 이름)로 추출한다.

```
finalScore = baseScore(place) + personalizationScore(user, place) * PERSONALIZATION_BOOST_WEIGHT
```

`PERSONALIZATION_BOOST_WEIGHT = 0.5` — `RecommendationService`의 기존
`PREFERENCE_BOOST_WEIGHT`와 같은 값으로 시작한다(일관성, 그리고 실사용
데이터 없이 튜닝하는 건 근거 없는 추측이 되므로 기존에 검증 없이 쓰던 값을
그대로 가져다 쓰는 게 새로 지어내는 것보다 낫다). 이후 실사용 데이터가
쌓이면 조정 가능하다.

## 생성 단계(Generation) — Phase 1을 완전한 RAG로

`personalizationScore` 계산 과정에서 이미 이 사용자의 top-K 유사 과거 신호를
찾아낸다(장소 이름/카테고리/mood). 이 검색 결과를 점수 계산에만 쓰고 버리는
대신, Gemini 생성 호출의 프롬프트로 재사용해서 "추천 이유"를 한 문장 생성한다
— 이게 Retrieval과 Generation을 잇는 지점이고, 이 스펙이 완전한 RAG가 되는
이유다.

```java
Optional<String> explainRecommendation(User user, Place candidate)
```

- 입력: `candidate`와, `personalizationScore` 계산 때 이미 찾아둔 top-K 유사
  신호 목록(장소 이름 + 카테고리 + mood)을 재사용한다 — 검색을 두 번 하지
  않는다.
- 프롬프트: "사용자가 예전에 좋아한 장소들: {유사 신호 목록}. 이번 후보:
  {candidate 이름/카테고리/mood}. 왜 이 후보를 추천하는지 20자 내외 한
  문장으로." 형태(정확한 프롬프트 문구는 구현 계획 단계에서 다듬는다).
- **호출 횟수 제약(중요)**: 후보 전부가 아니라 **최종 정렬 후 상위 1~2개에만**
  호출한다. `PlaceReviewService`의 리뷰 요약 호출과 같은 빈도 수준이라 기존
  무료 티어 한도 안에서 감당 가능하다 — 대안 찾기를 한 번 탭할 때 임베딩
  호출은 0회(이미 캐싱됨), 생성 호출은 최대 1~2회만 추가된다.
- 유사 신호가 하나도 없는 사용자(콜드스타트)에게는 호출 자체를 생략하고
  `Optional.empty()`를 반환한다 — 근거 없이 생성하면 그럴듯한 거짓 설명이
  나올 위험이 있다(신호가 있을 때만 생성하는 게 RAG의 핵심 원칙이기도 하다).
- 실패 처리: 생성 실패(429, 타임아웃 등)는 조용히 `Optional.empty()`로
  폴백 — 설명 문구가 없을 뿐 후보 자체는 정상 표시된다. 이번 세션에서
  확립한 "부가 기능 실패가 본 기능을 죽이면 안 된다" 원칙과 동일하다.

**UI**: `AlternativeFinderSheet`(trova-app)의 후보 카드에 설명이 있을 때만
"✨ {추천 이유}" 한 줄을 추가한다. 이 스펙은 백엔드 중심이라 앱 쪽 변경은
구현 계획 단계에서 별도 태스크로 다룬다(오늘 대안 찾기 UX 수정과 같은
파일들을 건드리게 된다).

## 콜드스타트 및 에러 처리

- **신호 없는 신규 사용자**: `personalizationScore`가 항상 0 → 기존
  필터-only 순서와 사실상 동일(baseScore로만 정렬됨). 새로 생긴 정렬 자체가
  기존 대비 개선이라, 콜드스타트여도 결과가 나빠지지 않는다.
- **임베딩 없는 후보(태깅 전)**: `personalizationScore` 0으로 처리, 필터링해서
  제외하지 않는다(태깅 여부와 무관하게 후보로는 계속 보여줘야 함 — 기존
  indoor 필터링 로직과 같은 원칙).
- **pgvector 쿼리 실패**(DB 오류 등): `AlternativeFinderService`의 기존
  `searchNearby` try/catch와 같은 원칙으로, personalizationScore 계산
  실패는 로그만 남기고 0.0으로 폴백 — 대안 찾기 화면 전체가 죽지 않는다.

## 관측성 / 비용

`PlaceTaggingRunner`에 얹는 임베딩 생성 호출과 `explainRecommendation`의 생성
호출 둘 다 `ApiCallLogService.record(...)`로 로깅한다 —
`provider="gemini", operation="place-embedding"` /
`provider="gemini", operation="recommendation-explanation"`. 이번 세션
최종 리뷰에서 "새 외부 호출 지점은 전부 로깅"이 필수 규칙으로 확립됐으므로
동일하게 적용한다. 특히 `explainRecommendation`은 요청마다 호출되는(캐싱
안 되는) 유일한 지점이라 실제 호출 빈도를 관측하는 게 무료 티어 한도 관리에
중요하다.

## 테스트 전략

- `PersonalizationService`: Mockito 기반 유닛 테스트로 쿼리 결과 매핑/콜드스타트(빈
  결과 → 0.0)/임베딩 null 처리 검증. 기존 `AlternativeFinderServiceTest`의
  reflection-`setId` 패턴을 재사용(엔티티가 영속화 안 된 상태에서 id가
  필요한 경우).
- pgvector 네이티브 쿼리 자체는 실제 Postgres가 필요해서 순수 Mockito로는
  검증 불가 — `@DataJpaTest` 스타일 통합 테스트(기존 `PlaceCatalogServiceTest`,
  `SavedPlaceRepositoryTest` 패턴 참고)로 실제 유사도 검색이 기대한 순서를
  반환하는지 확인한다. 단, 이 프로젝트 테스트 DB에 pgvector 확장이 설치돼
  있어야 하므로, 구현 계획 단계에서 테스트 환경 설정을 별도로 다룬다(CI/로컬
  테스트 DB에 확장이 없으면 이 테스트만 스킵되도록).
- `AlternativeFinderService`/`GapRecommendationService`의 정렬 추가는 기존
  테스트 스위트가 이미 반환 개수/필터링을 검증하므로, 정렬 순서를 검증하는
  케이스를 추가한다(예: personalizationScore가 다른 두 후보를 만들어 순서
  확인).
- `explainRecommendation`: 유사 신호 없음(콜드스타트) → `Optional.empty()`
  즉시 반환하고 Gemini 호출 자체가 안 나가는 것을 검증(Mockito
  `verifyNoInteractions`류). 생성 실패 시 예외가 전파되지 않고
  `Optional.empty()`로 폴백하는 것도 검증.
