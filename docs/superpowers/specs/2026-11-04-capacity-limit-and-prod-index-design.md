# 운영 인덱스 반영 검증과 운영 사양 복제 환경의 한계 찾기 — 설계

작성: 2026-11-04. 대화에서 사용자가 정한 것과 Claude가 정한 것(“Claude 판단”)을 구분해 적는다.

## 1. 왜 하나

사용자 목표는 두 가지다(사용자 발언).
1. 면접에서 말할 **병목 해결 경험**: 극한 부하 → 처음 보는 에러/멈춤 → 원인 → 해결 → 해결책 이해.
2. **Trova가 실제로 몇 명까지 버티는지** 알기.

면접에서 강한 이야기는 “운영 지표 → 격리 재현 → 원인 확정 → 수정 → 운영 반영 → 운영 지표로 확인”이다.
PR #308(장소 목록 인덱스)은 격리 검증까지 끝났지만 운영 반영·운영 확인이 비어 있다. 그래서 순서는
**1단계: #308 운영 반영과 운영 전후 확인 → 2단계: 운영 사양 복제 환경에서 한계 찾기**다(사용자 확정).

## 2. 목표 / 비목표 / 실패로 보는 것

목표
- 1단계: 운영에서 인덱스 전/후를 같은 조건의 작은 통제 부하로 비교한 실측 기록.
- 2단계: 운영 사양을 흉내 낸 로컬 환경에서 기준별 버티는 인원(N명), 무너지는 지점마다 원인·해결·재측정.
- 모든 단계에서 Prometheus/Grafana로 관측하고, 그래프 캡처를 문서·PDF에 남긴다(사용자 요청).

비목표
- 운영 서버에 한계 부하를 거는 것. 운영 DB에 대량 합성 데이터를 넣는 것.
- 고정 RPS 용량 계획, 장시간 안정성(soak), AI 분석 속도 개선.

실패로 보는 것(기술적으로 돌아가도)
- 로컬 숫자를 운영 숫자처럼, 격리 98% 감소를 운영 결과처럼 쓰는 것.
- k6를 돌리는 맥의 한계를 서버 병목으로 착각한 결과.
- 운영 사용자 장애, Gemini 하루 한도 소진, 운영 DB 오염.

## 3. 성공 기준(“버틴다”) — 사용자 확정

| 단계 | 조회 API p95 | 오류율 |
|---|---|---|
| 쾌적 | ≤ 0.2초 | < 1% |
| 양호 | ≤ 0.5초 | < 1% |
| 한계 | ≤ 1.0초 | < 1% |

- 서버 응답 기준이다. 사용자 체감은 여기에 모바일 네트워크·렌더링이 더해진다(근거: Nielsen 0.1초/1초/10초).
- 공유 제출(`POST /api/shares`)은 “접수 응답”만 이 기준으로 보고, 분석 완료 시간은 따로 기록한다.
- 각 단계마다 “몇 명까지 버텼나”를 따로 보고한다.

## 4. 1단계 — PR #308 운영 반영과 전후 확인

1. 정리: `docs/monitoring/2026-11-02-index-abba/prometheus-abba.png` 작업 트리 변경은 Google Play Console
   로그인 화면으로 잘못 덮어쓴 것(2026-11-04 시각 확인) → HEAD 버전으로 복원. 최신 main 반영(#324 등 다른 세션의
   운영 반영 포함), `docs/experience-notes.md` 충돌 해결, `./gradlew build`, 푸시.
2. 관측 준비: `monitoring/tunnel.sh`로 운영 지표 터널 재가동, Prometheus `trova-prod` up=1 확인
   (2026-11-04 확인 시 up=0). 운영 `saved_places` 행 수·테이블 크기를 먼저 확인한다.
3. 인덱스 전 측정: 사용자가 적은 시간대, 운영 테스트 계정, 약한 통제 부하(Claude 판단: 5 VU·수 분·`GET /api/places`).
   k6 p95, Prometheus 원본, Grafana 캡처, EXPLAIN 저장.
4. 인덱스 생성: Claude가 지정된 운영 환경 파일을 명시적으로 읽어 psql로
   `docs/bench/sql/place-list-user-order-index.sql`(CONCURRENTLY, 트랜잭션 밖) 실행. **실행 직전 사용자에게 재확인.**
   `pg_index.indisvalid` 확인. JPA가 운영에서 먼저 인덱스를 만들지 않도록 DB에 먼저 만든다.
5. PR #308 머지(`gh pr merge --squash`) → devflow deploy로 운영 배포.
6. 인덱스 후 측정: 3과 같은 조건으로 재측정, 비교.

주의(Claude 추측): 운영 테이블이 작으면 개선 폭이 작게 나올 수 있다. 그대로 기록하고 “데이터가 늘면 격리 실험처럼
차이가 커진다”는 해석과 근거를 함께 적는다.

관측 지표: k6 p95(주 지표), Prometheus 평균 지연·RPS, `hikaricp_connections_pending`, JVM CPU·메모리.
한계: 지금 앱은 HTTP 지연 히스토그램이 꺼져 있어 Prometheus는 평균만 본다. Supabase DB CPU는 Prometheus에 없다 →
Supabase 대시보드 캡처로 보완(무료 플랜의 Prometheus 지표 주소 제공 여부는 확인 후 사용).

## 5. 2단계 — 운영 사양 복제 환경에서 한계 찾기

### 준비
- **HTTP 지연 히스토그램 켜기**(사용자 확정: 2단계 준비 작업). Grafana에서 서버 쪽 p95를 보기 위함.
  운영 반영 여부는 별도 결정.
- 환경: `monitoring/capacity/` 확장. 앱 컨테이너 메모리 1GB, 운영과 같은 JVM 옵션.
  CPU 제한은 **1단계 운영 측정으로 보정**(Claude 판단): 같은 5 VU 부하에서 운영과 비슷한 지연이 나오는 제한값을 찾고
  근거를 기록한다. DB는 로컬 Postgres 17을 Supabase 무료 수준 메모리·연결 수로 제한(정확한 값은 확인 후).
- 외부 호출: Gemini·카카오·yt-dlp는 테스트용 가짜 구현으로 대체. 실제 호출 0.
- 데이터: 반복문 stored procedure와 `generate_series`로 각각 생성하고 적재 속도를 비교 기록.
  규모 100만 행 → 1,000만 행 단계적. 사용자·장소 분포는 Trova 실제 구조(사용자별 장소, 여행, 북마크 등)를 따른다.

### 부하 시나리오
- 실제 사용 섞기(사용자 확정): 장소 목록, 여행 목록, 북마크, 대기 폴링 등 앱이 부르는 조회 + 공유 제출(가짜 외부 호출).
- 섞는 비율은 운영 Prometheus의 API별 요청 수에서 산출.
- 계단식 VU 증가 → 무너지는 지점(오류 급증, 지연 폭증, 프로세스 종료)에서 멈춤.

### 무너질 때마다
1. Grafana/로그/스레드 덤프/힙/EXPLAIN으로 원인 확정. 동시에 k6 맥 CPU·`dropped_iterations`로 부하 발생기 한계 배제.
2. 고치고, 같은 시나리오로 재측정(가능하면 지난번처럼 전/후 교대 반복).
3. 에러 원문·원인·해결·전후 수치·이해해야 할 개념을 기록.

참고: 2026-09-21 운영 E2.1.Micro 테스트(`/actuator/health`만, DB 없음)는 1,000 VU에서도 오류 없이 느려지기만 했다
(Tomcat 기본 설정, 백프레셔 없음). 이번에는 DB가 포함된 실제 API라 다른 양상이 예상되지만, “안 죽고 느려지기만”하는
경우도 결과로 인정하고 기준(0.2/0.5/1초)으로 판정한다.

### 운영 반영
2단계에서 나온 수정 중 운영에 넣을 것은 따로 골라 사용자 결정 후 1단계 방식으로 반영한다. 자동 반영하지 않는다.

## 6. 결과물(사용자 확정)
- 레포: `docs/monitoring/`에 보고서 md + k6·Prometheus 원본 JSON + 재현 스크립트 + 캡처.
- 쉬운 해설 PDF: **Prometheus/Grafana 그래프 캡처를 실제 값이 보이게** 1단계 전/후, 2단계 무너진 지점별로 넣는다.
  환경(로컬/운영)·조건을 모든 수치 옆에 표시.
- 면접 노트: “어떤 에러가 왜 났고 어떻게 고쳤나” 질문-답 형태.
- 작업 끝에 `docs/experience-notes.md` 기록, 새 정책이 생기면 ADR.

## 7. 제약
- 운영 서버 메모리 약 956MiB, 실제 사용자 있음. 통제 부하는 약하게, 사용자 적은 시간에.
- 로컬 서버 8080·QA 시뮬레이터·Gemini 한도 등 하나뿐인 자원은 다른 작업과 동시 사용 금지.
  복제 환경은 별도 compose 프로젝트·포트를 쓴다.
- 운영 설정·자격증명은 출력·커밋 금지. 루트 `.env` 복사 금지.
- 이슈 하나 = 워크트리 하나. 2단계는 새 이슈·브랜치(`test/#번호-...`)로 진행.

## 8. 검토 후 사용자가 정한 것
- **'명'의 정의**: 실제 앱 사용자처럼 행동하는 가상 사용자(화면 체류·쉬는 시간·폴링 간격은 앱 코드 기준).
  보고는 “동시에 앱을 쓰는 사람 N명”. 행동 모델과 근거(앱 파일·간격)를 보고서에 명시한다.
- **1단계 운영 데이터**: 운영 DB에 합성 데이터를 넣지 않는다. 운영 그대로 측정하고, 차이가 작으면 그대로 기록한 뒤
  격리 실험 근거로 “데이터가 늘면 커진다”를 설명한다.
- **데이터 규모 해석**: 두 구간으로 나눠 보고. Supabase 무료 용량(500MB) 안 규모 = “지금 Trova 한계”,
  100만~1,000만 행 = “성장해 유료 DB로 옮긴 가정”의 한계. DB 제한값도 구간별로 다르게 둔다.
- **2단계 종료·수정 범위**: 무너지는 지점(병목) 최대 3개까지 찾아 고친다. 설정(스레드·커넥션 풀·JVM)과 쿼리·코드 수정 포함.
  캐시는 앱 내부 메모리처럼 무료인 것만. 구조 변경이 생기면 ADR.

## 9. 검토에서 Claude가 정한 것
- 복제 대상은 **지금 운영 중인 E2.1.Micro**(A1 k3s 계획 아님).
- 운영 앱↔Supabase 왕복 지연을 1단계에서 실측해, 복제 환경 DB 앞에 같은 지연을 넣는다(예: Toxiproxy 등 무료 도구).
  CPU 제한은 지연을 넣은 뒤 보정한다. 지연을 빼면 커넥션 풀 병목이 CPU 병목으로 바뀌어 원인 이야기가 달라지기 때문.
- 운영 Prometheus의 API별 요청 표본이 너무 적거나 QA·헬스체크 위주면, 앱 화면 흐름(앱 레포의 호출·폴링 간격)으로
  비율을 정하고 그 근거를 기록한다.
- 운영 IP 제한(기본 300/분) 안에서 1단계 통제 부하의 요청 간격을 정한다.
