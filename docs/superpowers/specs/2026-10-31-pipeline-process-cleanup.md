# #264 파이프라인 취소 시 프로세스·출력·작업 파일 정리

## 문제

PipelineRunner의 waitFor/join 인터럽트는 실행 중 Python을 종료하지 않고 예외를 던졌다. finally는 작업 폴더만 지워 프로세스가 삭제된 경로에 쓰거나 계속 외부 API를 부를 수 있었다. stdout readAllBytes 전용 스레드는 하위 프로세스가 출력 파이프를 상속하면 EOF를 기다리며 남을 수 있었다.

## 구현

- 최종 stdout JSON은 임시 파일로 받아 별도 reader 스레드를 없앤다. 진행 이벤트는 기존 stderr 파일에서 계속 읽는다.
- 실행 중 하위 ProcessHandle을 관찰·보관하고, 종료 경로에서는 추가 수집 후 소유한 부모 및 관찰한 하위 프로세스를 강제 종료한다.
- 인터럽트, 시간초과, 콜백 실패도 같은 정리를 수행한다. 전체 종료 대기 예산은 5초이며, 대기 중 인터럽트는 정리를 마친 후 플래그로 복원한다.
- 정상 완료에서도 관찰한 하위 프로세스 종료를 확인하고 출력 JSON을 읽은 다음 파일을 삭제한다.
- 종료를 확인하지 못하면 작업·출력 파일을 보존하고 오류 로그를 남긴다. 성공으로 반환하지 않는다.
- 기본 실행 제한 5분은 그대로다. 테스트에만 짧은 제한을 지정할 수 있는 package-private 생성자를 사용한다. Spring이 기존 공개 생성자를 고르도록 @Autowired를 명시한다.

## 범위

실행 중 Java가 관찰한 프로세스와 하위 트리를 정리한다. 관찰 전에 분리·재부모화됐거나 수집과 종료 사이 새로 생긴 프로세스를 원자적으로 잡는 OS 프로세스 그룹 보장은 아니다. JVM SIGKILL 시 Java finally는 실행되지 않으며 OS/서비스 관리자 수준의 종료 정책이 필요하다. 다른 Python runner들에는 이번 변경을 일괄 적용하지 않는다.
