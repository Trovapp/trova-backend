# 일정 AI 자동 생성 + 수동 편집 설계

## 배경

지금 서비스는 영상에서 장소를 추출해서 지도+리스트로 보여주기만 한다. 이미 `dayNumber`/`orderInDay`
필드와 `ItineraryView`(일자 탭 UI), `PlaceMapSection`(지도+장소 리스트) 컴포넌트가 있지만 전부
읽기 전용이고, `dayNumber`/`orderInDay`는 파이프라인(Gemini 추출) 단계에서 "영상이 이미 일정형으로
구성된 경우"에만 채워진다. 일정형이 아닌 영상(장소를 그냥 나열한 경우)은 `dayNumber`가 전부
null이라 지도+장소 리스트만 뜨고 일자 탭이 없다.

경쟁 앱 "albo"와 대부분 비슷하게 가되, "AI 자동 일정 생성 + 수동 수정" 기능을 차별화 포인트로
삼는다.

## 목표

- 일정형이 아닌 영상에 대해, 사용자가 상세 페이지에서 버튼을 눌렀을 때만 AI(Gemini)가 장소들로
  며칠짜리 일정(day 배정 + 하루 안에서의 순서)을 짜준다.
- 사용자가 일정(파이프라인이 이미 판정한 것이든, AI가 새로 짜준 것이든 전부)을 직접 수정할 수
  있다: 장소를 다른 날로 옮기기, 하루 안에서 순서 바꾸기, 날짜 추가, 날짜 삭제.

## 비목표

- 거리/이동시간 기반의 직접 짠 라우팅 알고리즘 — day/순서는 Gemini 추론에 맡긴다.
- Kakao 길찾기(경로) API 연동.
- 새로운 엔티티 추가 — 기존 `SavedPlace`의 `dayNumber`/`orderInDay`를 그대로 재사용한다.

## AI 일정 생성

### 트리거

- 일정형이 아닌 영상(해당 `ProcessingJob`에 속한 모든 `SavedPlace`의 `dayNumber`가 null)의
  상세 페이지에만 "일정 짜기" 버튼이 노출된다.
- 버튼을 눌렀을 때만 호출한다 — 자동/일괄 생성 없음. Gemini 무료 티어라도 불필요한 호출을 만들지
  않는다는 이 프로젝트의 비용 원칙(CLAUDE.md 참고)에 따른 것이다.

### 처리 흐름

1. `POST /api/places/videos/{jobId}/itinerary` — 프론트가 버튼 클릭 시 호출.
2. 해당 `ProcessingJob`에 속한 모든 `SavedPlace`(placeName, region, category)를 조회한다.
3. `ItineraryGenerationService`(신규, 외부 API 연동이므로 별도 Service로 분리)가 Gemini에
   장소 목록을 프롬프트로 전달하고, `{ dayNumber, orderInDay }`를 장소별로 받는다. 응답은
   기존 파이프라인의 `nameCandidates` 파싱과 같은 방식으로 엄격하게 검증한다(각 장소마다
   dayNumber/orderInDay가 없으면 400 에러로 실패 처리 — 일부만 채워진 상태로 저장하지 않는다).
4. 응답으로 받은 dayNumber/orderInDay를 각 `SavedPlace`에 반영해 저장한다.
5. 외부 API 호출을 포함하므로 `@Async` 처리 원칙에 따라 비동기로 실행하고, 프론트는 기존
   `/processing/[jobId]` 폴링 패턴과 동일하게 완료를 폴링한다.

이 엔드포인트는 멱등이 아니다 — 이미 dayNumber가 채워진 영상에는 노출되지 않으므로(비목표:
재생성 기능은 없음) 호출 전 가드가 필요 없다.

## 수동 편집

### 편집 대상

파이프라인이 판정한 일정과 AI가 생성한 일정 모두 동일한 방식으로 수정 가능하다 — `dayNumber`가
non-null인 모든 `SavedPlace`가 편집 대상이다.

### API

기존 `PlacesController`에 다음 엔드포인트를 추가한다. 전부 해당 영상(같은 `ProcessingJob`)의
장소만 대상으로 하며, day/순서 정합성은 서버가 재계산한다(클라이언트가 orderInDay 전체 목록을
보내지 않아도 되게).

- `PATCH /api/places/{id}/day` — body: `{ dayNumber: number }`. 장소를 다른 날로 옮긴다.
  대상 day의 `orderInDay` 맨 뒤에 배정한다.
- `PATCH /api/places/{id}/order` — body: `{ direction: "UP" | "DOWN" }`. 같은 날 안에서
  인접한 장소와 `orderInDay`를 교체한다.

날짜 추가/삭제는 백엔드 엔드포인트가 없다 — 아래 "빈 날짜 표현" 참고.

### 빈 날짜 표현

`SavedPlace`에 장소가 하나도 없는 "빈 날짜"는 DB에 존재를 저장할 방법이 없다(엔티티는 장소당
1로우). 그래서 날짜 추가/삭제는 순수 프론트 로컬 상태(`emptyDayNumbers: number[]`)로만 처리하고
백엔드를 호출하지 않는다:

- **날짜 추가**: 로컬 상태에 새 day 번호(기존 최대 dayNumber + 1)를 추가해 빈 탭을 보여준다.
  장소가 그 날짜로 이동해 온 순간(`PATCH /api/places/{id}/day` 호출) 비로소 DB에 그 dayNumber가
  나타나고, 그때부터는 서버가 응답하는 실제 dayNumber 목록에 포함되므로 로컬 상태에서 제거해도 된다.
- **날짜 삭제**: 로컬 상태에서 해당 day 번호를 제거한다. 장소가 있는 날짜는 삭제 버튼 자체를
  비활성화해서(장소 개수는 이미 클라이언트가 알고 있는 값이므로) 막는다 — 별도 서버 검증이
  필요 없다.
- 새로고침하면 아직 장소가 없는 빈 날짜는 사라진다 — 의도된 단순화다. 빈 날짜를 서버에
  영속화하려면 새 개념(예: `ItineraryDay` 엔티티)이 필요한데, 장소 하나 없는 날짜를 굳이 저장할
  필요는 없다(비목표: 새 엔티티 추가 없음).

### 프론트엔드 편집 UI

- **진입점**: 영상 상세 페이지에서 장소들에 `dayNumber`가 채워져 있으면(파이프라인 판정이든
  AI 생성이든) 기존 `ItineraryView`의 일자 탭 UI에 "편집" 토글이 추가된다. 토글을 켜면 같은
  화면에서 각 장소 행이 읽기 전용 → 편집 모드로 바뀐다(별도 라우트 없음).
- **다른 날로 옮기기**: 편집 모드의 각 장소 행에 날짜 선택 드롭다운(기존 day 번호 + "새 날짜
  추가"). 다른 날짜를 선택하면 `PATCH /api/places/{id}/day` 호출.
- **같은 날 안에서 순서 바꾸기**: 각 행에 위/아래 화살표 버튼(드래그앤드롭 라이브러리는 YAGNI —
  짧은 리스트 순서 바꾸기에 DnD까지는 불필요). 클릭 시 `PATCH /api/places/{id}/order` 호출.
- **날짜 추가**: 일자 탭 줄 끝의 "+ 날짜 추가" 버튼 — 백엔드 호출 없이 프론트 로컬 상태에 빈
  날짜 탭을 추가한다(위 "빈 날짜 표현" 참고).
- **날짜 삭제**: 일자 탭의 삭제 아이콘, 해당 날짜에 장소가 0개일 때만 활성화.
- **저장 방식**: 모든 편집 액션은 즉시 서버에 반영한다(낙관적 업데이트 + 실패 시 롤백) — 별도의
  "저장" 버튼으로 모으지 않는다. 이 앱은 URL 제출, 장소 삭제 등 다른 곳에서도 명시적 저장 단계가
  없으므로 일관성을 유지한다.

## 에러 처리

- AI 생성 실패(Gemini 429/malformed 응답): 기존 `ProcessingJob` 실패 처리와 동일하게 `FAILED`
  상태로 표시하고, 상세 페이지에 "다시 시도하기"를 노출한다(기존 `/processing/[jobId]` 패턴 재사용).
- 편집 API 실패(네트워크 오류 등): 프론트가 낙관적 업데이트를 롤백하고 토스트로 에러를 알린다.
- 날짜 삭제는 백엔드 호출이 없으므로(위 "빈 날짜 표현" 참고) 서버 에러 케이스가 없다 — 장소가
  남아있는 날짜는 프론트가 삭제 버튼을 비활성화해서 애초에 삭제 시도 자체를 막는다.

## 테스트 전략

- `ItineraryGenerationServiceTest`: Gemini 응답 파싱(정상/일부 누락/malformed) 단위 테스트.
- `PlacesControllerTest` (또는 통합 테스트): `/day`, `/order` 엔드포인트의 정상 케이스 +
  다른 영상의 장소를 옮기려는 경우(권한/스코프 검증) + 순서 교체 시 경계값(맨 위에서 UP, 맨
  아래에서 DOWN — no-op으로 처리).
- 프론트: 편집 모드 토글, 낙관적 업데이트 → 롤백 시나리오를 컴포넌트 테스트로 검증.

## 열린 질문 없음

이 스펙은 브레인스토밍 세션에서 4개의 확인 질문(AI 생성 도입 범위, 트리거 시점, 편집 범위,
수정 가능 대상)과 3개 섹션(AI 생성, 수동 편집 API, 프론트 편집 UI)에 대한 승인을 거쳐 작성됐다.
