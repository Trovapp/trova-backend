# 영상 분석 시작을 교체 가능한 작업 대기열로 (#244)

## 왜
- 지금 영상 분석은 서버 메모리 안의 `@Async` 대기열(`pipelineTaskExecutor`, 동시 2·대기 50)에서 돈다. 서버가 재시작되면 대기 중이던 작업이 사라지고,
  `OrphanedJobRecoveryService`가 15분 뒤 실패로 바꿔 줄 뿐이다(#43).
- 사용자 결정(2026-10-29): "포트폴리오 때문에 Kafka가 꼭 필요하다면 … 영상 공유 → 분석 시작 … 로컬 Docker나 Aiven 무료 플랜으로 '교체 가능한 구조'만 보여 주는 쪽" → "이걸로 진행해줘".
- 운영 서버(E2.1.Micro, 956MB)에는 Kafka 브로커(메모리 1GB 이상)를 못 띄우고, 사용자 5명 규모라 운영 기본은 바꾸지 않는다(ADR 0002 비용 0).

## 범위
- 분석 시작을 `ShareJobQueue.enqueue(jobId)` 하나로 모은다. 부르는 곳: `SharesController`(공유), `RetryJobAction`(관리자 재시도).
- 구현 두 개, 설정 `app.queue.type`으로 고른다:
  - `async`(기본, 값이 없을 때도): 지금과 똑같이 `@Async` 실행기에 넘긴다. 대기열이 차면 `TaskRejectedException` → 부르는 쪽이 작업을 지우고 503(#31).
  - `kafka`: 토픽 `trova.share-jobs`(키·값 = 작업 id)로 보낸다. 브로커가 받았다는 응답을 5초 기다리고, 못 받으면 같은 `TaskRejectedException`으로 바꿔 부르는 쪽 계약을 지킨다.
- Kafka 리스너(`kafka`일 때만 생김): 메시지를 받아 분석을 **끝까지 같은 스레드에서** 돌린 뒤 오프셋을 커밋한다 → 처리 중 서버가 죽으면 다시 받는다(지금 방식과 다른 점).
  - 동시 처리 2(지금 실행기와 같음), 한 번에 1건씩 가져옴.
  - 다시 받은 메시지 중 이미 끝난 작업(DONE·FAILED)이나 지워진 작업은 건너뛴다(같은 영상 두 번 분석 = Gemini 두 번 방지).
- 일정 재구성·푸시 발송은 다음 후보(같은 방식으로 늘릴 수 있게 이름·구조만 맞춘다).

## 안 하는 것
- 운영 서버에 Kafka 연결(설정 기본값 `async`, 운영 .env 안 바꿈).
- 결과 이벤트(분석 완료 → 알림) 발행, 다른 서비스로 나누기.

## 확인
- 단위: 각 구현이 맞는 일을 하는지(async는 실행기에, kafka는 보내기 실패 → TaskRejectedException), 리스너가 끝난 작업을 건너뛰는지.
- 통합: 내장 Kafka 브로커로 보내기 → 리스너 → 분석 호출까지(분석 서비스는 가짜, Gemini 안 부름).
- 로컬 Docker Kafka + 임시 서버(8091)로 실제 브로커 연결 확인. Gemini를 쓰지 않게 이미 끝난 작업 id로만 보낸다.
- 기본(`async`)일 때 Kafka에 연결하지 않는지, 메모리가 늘지 않는지(서버 시작 후 RSS).
