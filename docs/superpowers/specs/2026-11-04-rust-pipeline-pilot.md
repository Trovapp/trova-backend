# Rust 부분 비교 실험 설계 (#309)

상태: **제안·미실행**. 사용자 승인 범위는 기존 운영 기록 분석과 시험 설계/전후 기록이다. Rust 구현·컴파일·새 영상 분석·운영 실험·배포는 이번에 실행하지 않는다. 언어 도입 결정은 아직 없으며 ADR0003/0004/0020/0021의 기존 파이프라인과 대기열 정책을 유지한다.

## 목표와 판단 경계

현재 Python은 yt-dlp/FFmpeg/Gemini 호출을 조합한다. 먼저 작은 부품의 속도/메모리 차이를 측정하고, 그것이 실제 분석 시간에 기여할 여지가 있는지 판단한다. 과거 유튜브 직접 분석 표본을 인스타 미디어 가공 성능이나 Rust의 전후 대조군으로 사용하지 않는다.

첫 후보는 `pipeline-test/extract_places.py:build_parts`의 파일 읽기·base64 변환·요청 parts 생성이다. base64는 이진 파일을 API JSON 안에 넣을 수 있는 문자로 바꾸는 작업이다. Python의 base64도 내부 네이티브 코드를 사용하므로 Rust가 더 빠르다고 가정하지 않는다. FFmpeg 자체 구현이나 영상 분석 모델을 다시 만들지 않는다.

## 비교 프로그램의 계약

- 별도 실험 폴더에 Python 제어 CLI와 Rust 실험 CLI를 둔다. 제어 CLI는 소스가 고정된 기존 `build_parts`를 재사용한다. stdout은 요청1개당 줄 단위 결과 JSON1개, 진단/시간은 별도 파일 또는 stderr다. 실험 CLI의 바깥 JSON은 양쪽 모두 UTF-8·compact·객체 키 정렬의 동일 규칙을 쓰고, 배열과 text 안의 후보/프롬프트 문자열은 원본 그대로 보존한다. 이 CLI 전송 형식은 실제 Gemini 요청 형식 변경을 뜻하지 않는다.
- 입력은 로컬 파일 경로, `transcript`, `post_description`, `video_uri` 문자열, `photo_post`, `prompt`, `candidates`, 작업 순서다. `video_uri`는 기존 file_data와 같은 참조 문자열이며 CLI가 URL을 다운로드하지 않는다. 키/.env/HTTP/DB/대기열 코드는 포함하지 않는다.
- collect와 filter용 parts를 같은 입력·프롬프트·후보 순서로 각각 만든다. 미디어 순서·텍스트·MIME·base64 문자열을 원본과 비교한다. JSON은 객체 키 순서/공백을 정규화할 수 있지만 **배열 순서는 그대로** 유지한다. 실제 출력 바이트 수와 원본 raw 해시도 따로 기록한다.
- MIME 판별은 Python의 실제 결과를 골든으로 삼고 다른 확장자/없는 파일의 차이를 실패로 표시한다. 파일 누락/잘못된 입력 때 성공한 척하거나 다른 파일을 대신 쓰지 않는다.
- Rust는 release/locked 빌드를 사용한다. JSON/base64 라이브러리가 필요하면 구현 시 버전·라이선스·Cargo.lock을 고정한다. 외부 서비스·유료 API는 추가하지 않는다. 단일 준비 작업에는 Tokio 같은 비동기 런타임을 추가하지 않는다.

## 고정 입력24개

| 종류 | 개수 | 확인할 것 |
|---|---:|---|
| 유튜브 링크 참조 | 4 | 설명 있음/없음, Unicode URL/텍스트, 미디어를 읽지 않는 경로 |
| 텍스트/자막 | 4 | 한글·영문·빈 선택 필드·긴 자막 |
| 오디오 파일 | 4 | 작은/중간/큰 파일·확장자별 MIME |
| 프레임 파일 | 4 | 1/4/8장·한글 파일명·순서 |
| 오디오+프레임 | 4 | 혼합 입력·설명·후보 목록·collect/filter 둘 다 |
| 사진 게시물 | 4 | 사진 순서와 PHOTO_POST_TEXT·후보·설명 |

운영에서 받은 사용자 파일 대신 합성/배포 가능한 고정 파일을 사용한다. 파일별 크기·해시를 고정한다. 초기 실험용 입력은 건당 총16MiB 이하로 제한한다(실험 자원 한도이며 Gemini의 한도라는 뜻이 아니다). 초과·누락 입력 실패 시험은 성능24개와 별도로 한다. 영상 프레임8장/512px와 오디오16kHz/mono/64kbps 등 기존 전처리 설정을 임의로 바꾸지 않는다.

## 대조 실험과 통제

1. 로컬에서는24개 모두 출력 호환성/실패 처리를 먼저 검사한다. 여기서 얻은 Mac 시간은 운영 성능 결론으로 사용하지 않는다.
2. 실제 성능은 운영 서버의 한가한 시간에 **분리된 소유 임시 폴더/프로세스**에서 비교하도록 설계한다. 이번에는 실행하지 않는다. 운영 JAR/Python/환경/서비스/기존 작업/8080/DB/대기열/공유 한도를 바꾸지 않는다. 운영 서버에서 Rust를 컴파일하지 않고 CPU 아키텍처·런타임 호환성을 확인한 산출물을 별도 준비한다.
3. 같은 입력을 Python→Rust / Rust→Python 순서로 번갈아 실행한다. seed309로 입력 순서를 고정하고 입력/반복 인덱스의 홀짝으로 먼저 실행할 구현을 교대한다. 동시성은1로 둔다. CPU/IO 실험에 실제 Gemini/카카오/yt-dlp 요청은 없다.
4. 새 프로세스와 지속 프로세스 두 묶음을 분리한다. 각 입력/묶음의 첫 쌍은 워밍업으로 별도 보존하고, 측정3쌍을 기록한다. 24입력×3쌍×2구현×2묶음=288개 측정 관측치이며 전체 서비스 표본 수가 아니다. 워밍업은96관측을 별도로 남긴다. 관측1개는 collect+filter 준비2회의 합이며 각 시간도 기록한다. 지속 묶음은 입력마다 새 프로세스를 만들고 그 입력의 워밍업1회+측정3회를 같은 PID에서 진행한다. 지속 프로세스의 최대 RSS는 묶음 전체 값이며 개별 요청의 최대라고 하지 않는다.
5. 파일 캐시를 강제로 비우지 않는다. 같은 파일을 번갈아 쓰고 캐시/서버 부하가 통제되지 않은 한계를 기록한다. 같은 정책의 Python A/A를 먼저 실행해 측정기 흔들림과 계측 비용을 확인한다.

### 프로세스 수가 달라지는 문제

독립 Python CLI→Rust CLI의 시작 시간 절감은 **기존 서비스에서 Python 프로세스가 사라진다는 뜻이 아니다**. 기존 Gemini 호출을 Python에 남기고 Rust 보조 프로세스를 추가하면 실행/통신 비용이 늘 수 있다. 따라서 CLI 비교가 좋아도 채택 전에 별도 격리 어댑터에서 기존 Python 준비 경로와 Python→Rust 보조 경로의 전체 시간을 비교한다. 이때 Python 시작·Rust 시작·입출력 복사를 모두 포함한다. 이 실험도 별도 구현 단계이며 이번에는 진행하지 않는다.

캐시 재사용·미디어를 한 번만 인코딩·압축률/프레임 수 변경은 언어 비교와 분리한다. 이를 시험한다면 같은 최적화를 한 Python 대조군을 추가해야 한다.

## 지표와 전후 기록

- 결과 일치: parts의 배열 순서·문자열·MIME·base64 디코드 원본 바이트·오류 종류. 골든 불일치가 있으면 속도 승자를 선정하지 않는다.
- 시간: 전체 벽시계 시간(사용자가 기다리는 경과 시간), 준비 함수 시간, 새 프로세스 시작/통신 포함 시간. 평균·중앙값·범위·개별 짝 차이/순서를 모두 보존한다.
- 자원: 준비 프로세스의 user/system CPU 시간과 해당 프로세스 peak RSS(최대 메모리)를 기록한다. 기존 JVM RSS를 Python 메모리로 쓰지 않는다.
- 프로세스 트리는 같은 시점 RSS/PSS 합의 주기 샘플을 별도로 기록한다. 트리의 루트는 각 비교 구현의 worker PID로 한정해 상대 구현·계측 드라이버를 제외한다. 통합 비교는 Python 부모와 Rust 자식을 같은 루트에 포함한다. 공유 메모리 중복과 짧은 피크 누락/계측 간격을 명시하며 부모·자식의 개별 최대치를 더해 동시 최대치라고 하지 않는다.
- 기준 소스/Python/rustc/Cargo.lock/FFmpeg/CPU아키텍처/OS/입력·출력 해시/명령/측정기 버전을 고정한다. 누락은 null, 실패는 실패로 기록한다.

## 판단 제안 — 사용자 확정 전

준비 함수가10배 빨라도 그 함수가 전체 분석의1%면 전체 절감은0.9%에 불과하다. 별도 CLI의 성능보다 통합 경로의 **실제 절감 시간·메모리·복잡성**을 우선한다. 우선 검토 기준은 건당0.5초 수준의 실질 절감 또는 통합 경로16MiB 수준 메모리 절감이며, 이는 측정 결과를 본 뒤 사용자가 판단할 제안값이다. 근거가 작거나 오히려 느리면 기존 Python을 유지하고 중복 호출/전송·대기를 먼저 개선하는 쪽을 추천한다.

실제 Gemini 입력이 동일하다는 호환성 검사는 추출 정확도를 새로 평가했다는 뜻이 아니다. 프롬프트/미디어/호출 횟수/모델까지 바꾸려면 별도20~30개 평가 세트와 제한된 운영 검증을 설계하고 승인을 받아야 한다. 기존 실패한 예약 벤치를 이 실험 명목으로 다시 실행하지 않는다.
