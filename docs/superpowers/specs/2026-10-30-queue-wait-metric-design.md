# 공유 → 분석 시작 대기 시간 지표 (#249)

## 왜
- Kafka 대기열(#244, ADR 0021)을 운영에 켰지만, 분석 시간(시작 → 끝)은 두 경로가 같았다(14.5초·14.8초).
  Kafka가 실제로 더하거나 줄이는 건 **작업이 만들어진 뒤 분석이 시작되기까지의 대기**인데, 이 값을 재는 곳이 없었다.
- 사용자(2026-10-30): "성능이 더 좋아졌나?" → 경로별 대기 시간을 숫자로 남기자는 제안에 "진행해줘".

## 정한 것
- 분석을 시작할 때(`PlaceExtractionService.processNow`) 작업의 `createdAt`부터 지금까지를 잰다.
- 지표: Timer `trova.queue.wait{path}`. path는 `kafka`(리스너) 또는 `async`(서버 안 대기열, Kafka 실패 시 넘김 포함).
  넘김 여부는 `trova.queue.fallback`이 따로 센다.
- 버킷은 100ms·500ms·1s·5s·30s·5m만 둔다. Grafana에서 구간 비율을 보려는 것이고, 운영 지표 수(현재 Kafka만 290개)를 크게 늘리지 않는다.
- 로그 시작 줄에 경로와 대기 ms를 붙인다(`파이프라인 시작(kafka, 대기 132ms)`).
- 작업 시각은 따로 한 번 읽는다(`findById`). `markProcessing`의 반환형을 바꾸면 테스트 여러 곳이 바뀌는데, 작업당 조회 한 번은 비용이 작다.
- 시각 기준: `createdAt`은 서버 기본 시간대의 `LocalDateTime.now()`라, 같은 방식으로 비교한다(운영·로컬 모두 TZ=Asia/Seoul).

## 확인
- 단위: 경로 태그별 기록, 음수(시계 어긋남)는 0으로, 작업이 없으면 기록 안 함.
- 로컬 임시 서버 + Docker Kafka: kafka·async 각 1건 이상 기록되는지(Gemini 안 쓰는 방식으로).
- 운영: 배포 뒤 실제 공유가 쌓이면 경로별 중앙값을 기록.
