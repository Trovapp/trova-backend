# 0034 장소 목록은 필요한 값만 조회한다

- 상태: 확정 · 날짜: 2026-11-02 · 관련: #305

## 배경

시뮬레이터 조회 관찰 후 H2 합성 데이터로 목록 조회를 측정했다. 기존 EntityGraph는 N+1을 막지만
장소 1,000개·작업 100개에서 엔티티 1,101개를 로딩한다. 목록에 없는 사용자 정보·작업 상태·영업시간까지
조회하고 관리 객체를 만들며, 같은 작업 URL을 장소마다 두 번씩 정규화한다.

## 결정

- `GET /api/places`만 `SavedPlaceListRow` scalar constructor projection으로 조회한다.
- 사용자 소유 조건, createdAt/id 내림차순, 응답 필드와 null/영상 메모 처리를 유지한다.
- 대표 영상 선택은 기존처럼 작업 원본 URL을 `ShareUrl.videoKey`로 정규화한 뒤, 장소가 있는 작업 중
  가장 큰 작업 ID를 선택한다. 저장 장소의 원본 URL과 작업 원본 URL을 서로 대체하지 않는다.
- 정규화 결과는 요청 안에서 작업 ID별로 공유한다. 전역 캐시나 만료 정책은 추가하지 않는다.
- 기존 엔티티 조회는 편집·삭제·다른 호출에서 유지한다. DB 스키마와 API 계약은 바꾸지 않는다.

## 검증과 한계

기존 경로와 새 경로의 전체 DTO·순서를 대조하고 소유권, 같은 영상의 URL 별칭, 장소 없는 최신 작업,
동일 생성 시각, 좌표 null, 영상 메모를 검사한다. 새 경로는 SQL 1회·엔티티 로딩 0회를 검증한다.
성능은 opt-in H2 비교에서 워밍업 뒤 순서를 번갈아 측정하며 원본을 보관한다.
사용자 인증 조회·HTTP 직렬화·네트워크·운영 PostgreSQL 성능은 해당 측정에 포함되지 않는다.
목록 전체 조회이므로 데이터가 계속 늘면 페이지네이션 검토는 여전히 필요하다.
