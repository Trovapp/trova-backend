# 0021 영상 분석 시작은 교체 가능한 대기열로 — 운영은 Aiven 무료 Kafka, 브로커가 안 되면 서버 안 대기열로
- 상태: 확정 · 날짜: 2026-10-30 · 근거: 이슈 #244, 사용자 결정(2026-10-29 "로컬 Docker나 Aiven 무료 플랜으로 '교체 가능한 구조'만 보여 주는 쪽" → "이걸로 진행해줘",
  2026-10-30 "이력서에 로컬로 했다고 하면 안해봤다고 생각하지 않을까 운영에서 해야지" → 운영 연결 + 자동 넘기기 제안에 "진행할게")
- 더하는 결정: [0002](0002-cost-zero-free-tiers.md)(비용 0원), [0005](0005-deploy-e2-micro-systemd.md)(E2.1.Micro 단일 서버)

## 결정
- 영상 분석 시작은 `ShareJobQueue.enqueue(jobId)` 하나로 모은다(공유, 관리자 재시도).
- 구현은 `app.queue.type`(환경 변수 `APP_QUEUE_TYPE`)으로 고른다.
  - `async`(코드 기본값): 지금처럼 서버 안 `pipelineTaskExecutor`.
  - `kafka`(운영): 토픽 `trova.share-jobs`(파티션 2, 키·값 = 작업 id). 브로커는 Aiven 무료 플랜 — 운영 서버(956MB)에 브로커를 같이 띄우지 않는다.
    Oracle A1(무료 2 OCPU·12GB)이 확보되면 브로커를 그쪽으로 옮기는 것을 다시 본다.
- Kafka 리스너는 분석을 같은 스레드에서 끝까지 돌린 뒤 오프셋을 커밋한다. 동시 처리는 2, 한 번에 1건씩 가져온다.
  - 다시 받은 메시지 중 이미 끝났거나 지워진 작업은 건너뛴다.
  - Spring Kafka 기본 재처리(9회)는 끈다. 분석을 다시 돌리면 Gemini를 또 부르기 때문이다.
- 보내기는 브로커 응답을 최대 5초 기다린다(`max.block.ms`도 5초). **실패하면 공유를 막지 않고 서버 안 대기열(async)로 넘긴다.**
  넘긴 횟수는 지표 `trova.queue.fallback`으로 남고, 한 번 실패하면 1분 동안은 Kafka를 건너뛴다(공유마다 5초씩 기다리지 않게).
  서버 안 대기열까지 가득 차면 예전처럼 작업을 지우고 503.
- 로컬 브로커는 `deploy/kafka/docker-compose.yml`(KRaft 1대)로 띄운다. 원격은 Aiven 무료 플랜을 후보로 둔다. 무료 플랜은 토픽 5개, 토픽당 파티션 2개, 125KiB/s이고, 연결에 SSL 설정을 환경 변수로 더해야 한다.

## 이유
- async 대기열은 서버 메모리에만 있다. 재시작하면 대기 작업이 사라지고 15분 뒤에야 실패로 정리된다(#43). Kafka 방식은 처리가 끝나야 커밋하므로, 처리 중 재시작해도 다시 받는다.
- 브로커를 운영 서버에 같이 띄우지 않는 이유: 로컬 실측에서 힙을 256MB로 줄여도 컨테이너가 297~327MB였다. 운영 서버는 956MB인데 앱이 이미 약 400MB를 쓴다.
- 원격 무료 브로커(Aiven)를 쓰면 외부 의존과 장애 지점이 하나 늘어난다. 처음에는 이 이유로 운영에 켜지 않으려 했다.
  사용자가 운영에서 돌려 본 경험을 원해서 다시 정했고, 장애는 자동 넘기기로 막는다. 브로커가 꺼져도 사용자가 겪는 일은 지금과 같다.
- 사용자 5명 규모에서 처리량 이득은 없다. 얻는 것은 재시작에 강한 처리와, 서버를 늘릴 때 그대로 쓰는 구조다.
- 하나의 진입점으로 모아 두면, 사용량이 커지거나 서버가 여러 대가 될 때 설정만 바꿔 옮길 수 있다. 일정 재구성·푸시 발송도 같은 방식으로 늘릴 수 있다.

## 검토한 다른 방법
1. DB 테이블을 대기열로(`SELECT … FOR UPDATE SKIP LOCKED`) — 추가 인프라 없이 재시작에 강하다. 사용자가 Kafka 구조를 보이는 쪽을 골랐다. 운영에서 재시작 유실을 먼저 막아야 하면 이걸 다시 본다.
2. 운영에 Kafka만 연결(넘기기 없음) — 24시간 쓰지 않으면 꺼진다는 정리 사이트 기록이 있다(공식 확인 전). 꺼지면 공유가 막힌다. 그래서 넘기기를 붙였다.
4. 서버를 키워 브로커를 같이 띄우기 — 유료라 [0002](0002-cost-zero-free-tiers.md)와 부딪힌다. 무료인 Oracle A1 확보를 다시 시도 중이다(2026-10-30 재시작).
3. RabbitMQ·Redis Streams — 가볍지만 사용자가 요청한 것이 Kafka다.

## 결과
- 로컬 실측(-Xmx384m, 개발 DB, 각 2회):
  - JAR: 71.2MB → 83.9MB. 압축 라이브러리 zstd·snappy를 빼기 전에는 93.6MB였다.
  - 시작 20초 뒤 non-heap: 기준 138MB, async 138MB, kafka 152MB.
  - RSS: 기준 386/414MB, async 412/391MB, kafka 408/410MB. 흔들림이 커서 RSS로는 차이를 구분하지 못했다.
- 기본(async)에서는 Kafka에 연결하지 않는다. Kafka 모드는 브로커가 꺼져 있어도 서버가 뜬다.
- 브로커 꺼짐: 넘기기 전에는 공유가 6초 뒤 503으로 끝났다. 넘긴 뒤에는 5초 뒤 202로 접수되고, 서버 안 대기열에서 분석이 끝까지 돌았다(DONE).
- 처리 중 강제 종료(`kill -9`) 뒤 다시 띄우면, 커밋되지 않은 메시지를 다시 받아 같은 작업을 끝까지 처리했다. 다시 받기까지 약 37초 걸렸는데, 이전 소비자가 그룹에서 빠지는 시간(세션 제한 기본 45초)으로 보인다.

## 확장: 자동 일정 초안도 같은 대기열 구조로 (2026-11-11, #390)
- 근거: 사용자 "카프카 넣을곳이나 카프카를 위해 넣을 기능들 있을까?" → 후보 중 1번(자동 초안) "1".
- 문제: 공유 → 영상 분석은 Kafka라 재시작해도 다시 받지만, 분석이 끝난 뒤 자동 초안(`AutoDraftService` → `TripPlannerService.process`)은
  서버 안 `planTaskExecutor`였다. 재시작하면 초안이 사라지고 15분 뒤 `OrphanedJobRecoveryService`가 실패로 정리했다.
- 결정:
  - 자동 초안 시작은 `DraftJobQueue.enqueue(draftId)`로 넣는다. 구현은 같은 설정 `app.queue.type`으로 고른다(async 기본, 운영 kafka).
  - 토픽 `trova.draft-jobs`(파티션 2, Aiven 무료 토픽 5개 중 2개째), 그룹 `trova-draft-jobs`, 동시 처리 1(`app.queue.kafka.draft-concurrency`).
  - 보내기 실패 규칙은 공유 대기열과 같다 — 5초 기다린 뒤 서버 안 대기열로 넘기고(지표 `trova.queue.draft.fallback`), 1분 동안 Kafka 건너뜀.
  - 다시 받은 초안은 `TripPlannerService.processNow`가 상태를 보고, PENDING·PROCESSING만 만든다. 끝났거나(READY·APPROVED·FAILED)
    답을 기다리는(NEEDS_INPUT) 초안은 Gemini를 부르지 않고 건너뛴다. 같은 초안은 서버 한 대 안에서 한 번에 하나만 돈다.
  - 사용자가 직접 만든 초안(`TripDraftController`)과 일정 재구성은 아직 서버 안 대기열이다 — 화면에서 기다리는 흐름이라 다음 단계로 둔다.
- 확인(로컬, 내장 Kafka): 보내기 → 리스너 → 초안 만들기, 받은 소비자가 커밋 없이 닫힌 뒤 새 리스너가 같은 초안을 다시 받음,
  끝난 초안·답 기다리는 초안 건너뛰기, 처리 중 죽은(PROCESSING) 초안 이어서 만들기. 운영 서버에서 재시작 실험은 하지 않았다.
- 대가: Kafka 소비자 하나(스레드 1)가 더 붙는다. 초안이 토픽에서 15분 넘게 기다리면 예전처럼 실패로 정리된다.
