# 0024. 단일 JVM에서 중복 분석은 기다린 뒤 상태를 재확인한다

- 상태: 확정
- 날짜: 2026-10-31
- 관련: #261, ADR 0005(단일 서버), ADR 0021(Kafka + async 폴백)

## 결정

현재 운영 단일 JVM에서 영상 분석 서비스의 두 진입 경로를 같은 작업 잠금으로 직렬화한다. 늦은 경로는 선행 분석이 끝날 때까지 기다린다. 완료·실패·삭제 상태를 DB에서 재확인해 파이프라인을 생략하며, 메모리 상태만으로 처리 완료를 판단하지 않는다.

고정 256개 버킷을 사용해 임의 작업 ID에 대한 잠금 객체가 계속 쌓이지 않게 한다. 충돌한 다른 작업도 기다릴 수 있으나, 서로 다른 버킷은 병렬 처리한다.

## 이유

- 실행 중인 Kafka 중복을 즉시 반환하면 아직 분석 중인 async 작업보다 먼저 오프셋을 확정할 수 있다.
- PROCESSING을 항상 버리면 직전 프로세스에서 중단된 Kafka 작업을 재수신해 복구할 수 없다.
- 같은 프로세스에서는 기다린 뒤 완료 여부를 확인하고, 재시작하면 메모리 잠금이 사라져 중단된 PROCESSING을 재수신 처리할 수 있다.
- 기존 일정 생성도 쓰는 markProcessing은 그대로 두고 영상 분석 시작만 별도로 검사한다. analysisStatus가 있는 일정 생성 중 작업은 재추출하지 않는다.

## 한계와 다시 볼 조건

한 JVM/서비스 인스턴스의 동시 실행 방지다. 여러 프로세스가 같은 DB를 소비하면 원자적 DB 선점·소유권·임대/복구 정책을 함께 도입해야 하며, 이 구현만으로 확장하면 안 된다. Kafka 소비 스레드는 기다리는 동안 점유되므로 장시간 작업의 max.poll.interval/부하도 따로 점검해야 한다. 정확히 한 번의 외부 호출이나 재시작 전 부분 저장 제거를 약속하지 않는다. 오프셋 확정·브로커 데이터 보존 정책은 ADR 0021의 한계를 따른다.

대기 지표는 중복을 집계하지 않도록 분석 시작을 허용한 뒤 기록한다. 시작 상태 검사/커밋 시간이 포함되므로 이전 배포와 지표를 비교할 때 순수 브로커 지연 증가로 단정하지 않는다.

## 검증 후속

로컬 내장 Kafka와 별도 JVM 작업자·H2 파일 DB·Python fixture로 실제 오프셋 및 강제 종료 후 재수신을 확인했다. 동일 JVM의 async 선행 중복은 완료 전 오프셋을 유지했다. 운영/외부 API/다중 프로세스 동시 실행·부분 저장 복구 보장을 추가한 것은 아니다. `docs/reviews/kafka-process-recovery-20261031.md` 참고.
