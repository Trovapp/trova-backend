# 0036. 조회 API의 사용자 존재 확인을 메모리에 기억한다

- 날짜: 2026-11-05
- 상태: 확정 (로컬 격리 검증, 운영 미적용)
- 관련: #332, ADR 0025·0027(단일 JVM 범위), ADR 0026(정지 목록 커밋 뒤 반영)

## 배경

로그인한 요청은 컨트롤러마다 `CurrentUserService.resolve()` → `userRepository.findById()`로 사용자 행을 읽었다.
Spring Data의 읽기 전용 트랜잭션이라 요청마다 `BEGIN READ ONLY`+조회, `COMMIT`으로 **DB 왕복 2번**이 본 조회 앞에 붙었다.
운영 서버→Supabase 왕복은 31.5ms라(2026-11-04 실측) 장소 목록 등 조회 API에서 약 63ms가 사용자 확인에만 쓰였다
(`docs/monitoring/2026-11-05-db-roundtrips.md`).

## 결정

- `KnownUsers`(단일 JVM 메모리)에 DB에서 존재를 확인한 사용자 ID를 기억한다.
- `CurrentUserService.resolveUserId(auth)`: JWT 사용자는 기억돼 있으면 DB를 보지 않고 ID를 돌려준다. 처음 한 번만 `existsById`로 확인한다.
  없는 사용자는 지금처럼 인증 예외(401)로 끝나며 기억하지 않는다. 웹 세션(OAuth2) 사용자는 기존 `resolve()`를 그대로 쓴다.
- **사용자 ID만 필요한 자주 불리는 조회 API 7개**만 이 경로를 쓴다: 장소 목록, 처리 목록, 여행 목록, 찜, 찜 폴더, 알림, 자동 초안.
  저장소에 사용자 ID로 읽는 메서드를 추가했다. 수정·생성 API와 사용자 정보가 필요한 API는 기존처럼 사용자 행을 읽는다.
- 사용자 행은 탈퇴(`UserAccountService.withdraw`)로만 지워진다. 탈퇴가 **커밋된 뒤** ID를 기억에서 뺀다
  (커밋 전에 빼면 그 사이 요청이 남아 있는 행을 보고 다시 기억할 수 있다). 정지는 기존 `SuspendedUsers`가 JWT 필터에서 막는다.

## 고르지 않은 안

- 사용자 엔티티 전체를 캐시: 닉네임 변경·정지 같은 수정이 오래된 값으로 덮일 수 있어 제외.
- 트랜잭션 없이 조회만(`COMMIT` 1번 절약): 효과가 절반이라 이번에는 캐시를 택함.
- 토큰의 ID로 바로 조회(사용자 확인 생략): 탈퇴한 토큰이 401 대신 빈 목록을 받게 돼 제외.

## 한계와 비용

- 단일 JVM 전제. 서버를 여러 대로 늘리면 다른 서버의 탈퇴를 모르므로, 그때는 공유 무효화가 필요하다.
- 탈퇴 커밋과 기억 삭제 사이의 아주 짧은 순간에는 탈퇴한 토큰이 빈 목록을 받을 수 있다(데이터는 이미 삭제됨).
- 메모리: 사용자 ID 수만큼 Long 집합. 현재 사용자 수에서 무시할 수 있는 크기.

## 검증

- 단위: 처음 한 번만 DB 확인, 없는 사용자는 예외·미기억, 기억에서 빠지면 다시 DB 확인.
- 통합: 7개 API 호출 뒤 탈퇴하면 기억에서 빠지고 `/api/places`가 401.
- 왕복 수: 같은 로컬 지연 기울기 측정으로 전/후 비교(`docs/monitoring/2026-11-05-db-roundtrips.md`).
