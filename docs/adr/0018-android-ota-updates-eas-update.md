# 0018 안드로이드 앱은 무선 업데이트(EAS Update)로 JS 변경을 내보낸다
- 상태: 확정 · 날짜: 2026-10-15 · 근거: 이슈 #209, 앱 레포 Trovapp/trova-app#33, 사용자 결정("expo-updates 넣는 거 진행해줘", 설계 확인 뒤 "진행해줘")
- 더하는 결정: [0017](0017-android-native-app.md)(안드로이드 네이티브 앱) — 출시 뒤 앱 코드 변경을 어떻게 내보내는지

## 결정
- 앱에 `expo-updates`를 넣고 EAS Update(무료 플랜)로 JS·화면 변경을 내보낸다. 앱은 켤 때 새 업데이트를 확인해 뒤에서 받고, **다음 실행 때** 적용한다(사용 중 화면이 바뀌지 않는 기본 동작).
- `runtimeVersion`은 `fingerprint` 방식. 네이티브 쪽(라이브러리·권한·앱 설정)이 바뀌면 값이 달라져, 새 빌드가 필요한 변경이 옛 앱에 업데이트로 내려가지 않는다. 그런 변경은 지금처럼 새 빌드를 낸다.
- 채널은 빌드 프로필과 같은 `preview`(에뮬레이터 확인용)·`production`(플레이 출시용) 두 개.
- 서버 주소(`EXPO_PUBLIC_API_BASE_URL`)는 `eas.json`이 아니라 EAS 환경 변수(preview=로컬, production=운영)에 둔다. `eas update`는 `eas.json`의 env를 쓰지 않기 때문이다.
- 업데이트는 앱 레포 `scripts/publish-update.sh <채널> "<메시지>"`로만 올린다. 그 채널 환경 변수로 번들을 만들고, 번들 안 서버 주소를 검사해(운영 채널에 `http://localhost`·`127.0.0.1`이 있거나 운영 주소가 없으면 멈춤) 통과한 그 번들을 그대로 올린다.
- 아이폰 PWA는 지금처럼 웹 배포로 바로 바뀐다. 웹에서 `expo-updates`는 아무것도 하지 않는다.

## 이유
- 안드로이드 앱은 코드가 바뀔 때마다 빌드(무료 월 15번, 대기열 느림)·플레이 심사를 거쳐야 했다. 이번 카카오맵 검색 수정(앱 #32)처럼 작은 화면 수정도 PWA는 바로 바뀌는데 앱은 다음 출시까지 기다려야 한다.
- 무료 플랜: 월 활성 사용자 1,000명·전송 100GiB·업데이트 횟수 무제한, 넘어도 추가 요금 없이 제한만(expo.dev/pricing, 2026-10-15 확인). 비용 0원 원칙([0002](0002-cost-zero-free-tiers.md))에 맞는다.
- 주소 검사는 같은 날 PWA를 로컬 `.env`로 빌드해 `localhost:8080` 버전이 1~2분 운영에 나간 실수에서 나왔다. 앱은 업데이트가 기기에 내려간 뒤라 되돌리기가 더 어렵다.

## 검토한 다른 방법
1. 업데이트 없이 매번 새 빌드·출시 — 추가 서비스가 없지만 작은 수정도 빌드 횟수·심사 시간을 쓴다.
2. `runtimeVersion: appVersion`(앱 버전 = 호환 기준) — 단순하지만 네이티브를 바꾸고 버전 올리기를 잊으면 옛 앱이 깨지는 업데이트를 받는다. fingerprint가 이걸 자동으로 막는다.
3. 직접 업데이트 서버(expo-updates 사양 구현) — 사용자 1,000명 전에는 이득이 없고 운영할 게 늘어난다.

## 결과
- fingerprint가 로컬과 빌드 서버에서 같아야 업데이트가 맞물린다. 그래서 앱 설정의 Firebase 파일 경로를 `./google-services.json`으로 고정하고, 빌드 서버에서는 `eas-build-pre-install`이 EAS 파일 변수를 그 자리로 복사한다. http 허용 여부는 `eas.json` 프로필 변수 `TROVA_ALLOW_HTTP`(preview=1, production=0)로만 정한다 — 처음엔 `EAS_BUILD_PROFILE`로 정했는데 이 값은 빌드 서버에만 있어, 맥에서 eas-cli가 미리 계산한 값과 달라 첫 빌드가 멈췄다. 올리기 스크립트도 같은 값을 둔다.
- 월 활성 사용자가 1,000명에 가까워지면 그때 유료 전환이나 다른 방법을 다시 정한다.
