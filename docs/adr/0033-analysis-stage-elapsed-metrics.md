# 0033 영상 분석의 Java 단계와 실행 시간을 결과별로 계측한다

- 상태: 확정 · 날짜: 2026-11-01 · 근거: #305, 실사용 job 125/126 관찰과 사용자 진행 요청

## 배경

첫 영상의 후보 재검토 시작→DONE 11.844초 중 후보 선택 AI 기록은 1.031초였다.
기존 Python 단계/외부 호출 지표만으로는 후보 선택의 부대 처리, 검증, 저장 중 지연 위치를 구분할 수 없었다.

## 결정

- `trova.analysis.stage{stage,outcome}`: preparing/extracting/geocoding/selecting/verifying/saving 경과 시간을 기록한다.
  각 단계의 상태 DB 갱신부터 다음 단계 직전까지이며 저장 단계에는 결과 커밋이 포함된다.
- `trova.analysis.execution{outcome}`: 분석 선점 커밋 후부터 저장 완료/예외 시점까지 기록한다.
  큐 대기·선점 DB 처리·실패 상태 복구·자동 일정 초안은 제외한다. DB 생성→완료 시간과 범위가 다르다.
- outcome은 success/failure/no_places/discarded만 사용한다. 중복 수신으로 시작을 건너뛴 작업은 세지 않는다.
- 다음 단계로 진행한 단계는 success이며 전체 작업의 성공 여부와는 다르다. 대상이 없어 외부 호출을
  생략한 선택/검증 단계도 상태 갱신·분기 시간은 기록한다. 별도 API 실행 횟수로 해석하지 않는다.
- 기존 `trova.pipeline.stage`(Python 세부 단계)는 유지한다. Java extracting에 포함되므로 합산하지 않는다.
- 고정 28개 Timer를 미리 등록해 첫 작업 이전 0 표본을 제공한다. 히스토그램은 켜지 않고 count/sum/max를 사용한다.
  p95를 제공한다고 주장하지 않는다. jobId는 로그에만 남긴다.
- 단조 시계로 경과 시간을 측정하며 완료 후 다시 닫아도 중복 기록하지 않는다. 기록 중 예외는 원래 분석을 방해하지 않는다.

## 한계와 검증

프로세스 강제 종료는 완료 지표를 남기지 못한다. 수집 공백·첫 수집 이전 종료·재시작은 `increase()` 결과에 영향을 준다.
계측은 원인 규명 준비이며 성능 최적화가 아니다. 예전 11.844초의 정확한 원인을 소급 확정하지 않는다.

MockClock으로 단계 합/총 시간/자동 초안 제외/중복 종료 방지를 검증한다. 서비스 테스트에서 정상, 추출 실패,
저장 실패, 단계 갱신 실패, 장소 없음, 저장 취소, 중복 수신, 초안 실패의 분류를 검증한다.
운영에는 강제 장애나 새 AI 요청을 만들지 않고 지표 0 표본 노출과 수집을 확인한다.
