# 0038. 내려받기 영상 분석은 동시에 1개만 (낮은 CPU 우선순위는 운영 측정 뒤 끔)

- 날짜: 2026-11-08
- 상태: 확정 — 동시 1개 유지, `nice`는 기각(기본 0, 2026-11-08 운영 측정 뒤 #347)
- 관련: #344, #345, #347, 문제 기록 #16(`docs/monitoring/2026-11-04-capacity-issue-log.md`), ADR 0021(대기열), ADR 0037

## 문제

운영 서버(E2.1.Micro)에서 쇼츠 5·릴스 5를 한꺼번에 넣고 50명이 조회하면 조회 p95가 10초(시간 초과), 오류가 50%대였다.
4시간 쉬어 CPU 몫을 회복한 뒤 다시 재도 같았다(2026-11-08 20시). 같은 조건의 일반 유튜브 10개는 조회 p95 2.4초·오류 0%였다.
→ 서버가 영상을 내려받고 프레임을 뽑는 분석(인스타그램)의 CPU 부담이 조회 응답을 밀어낸다. 몰아 받으면 인스타그램이 요청을 막기도 했다(2건).

## 해결안

| 안 | 판단 |
|---|---|
| 분석 파이썬을 `nice`로 실행 | 같은 VM 안에서 조회(java)가 먼저 CPU를 받는다. 코드 한 곳, 설정으로 끌 수 있다. 분석은 느려질 수 있다 |
| 내려받기 분석 동시 1개 | CPU 몰림과 인스타그램 차단이 같이 준다. 뒤 작업 대기가 길어진다 |
| **둘 다 (고름, 사용자 선택 1)** | 두 효과가 겹치지 않는다(우선순위 / 동시 수) |
| 기록만 | 실제 사용자 12명이라 당장 몰릴 가능성은 낮다 |

## 결정

- `PipelineRunner`가 분석 파이썬을 `nice -n ${PIPELINE_NICE:10}`으로 실행한다(0이면 끔). yt-dlp·ffmpeg는 우선순위를 물려받는다.
- 유튜브가 아닌 링크(서버가 내려받음)의 분석은 `${PIPELINE_DOWNLOAD_CONCURRENCY:1}`개만 동시에 실행한다(0이면 제한 없음). 실행 시간 제한(5분)은 차례를 받은 뒤부터 센다.
  단일 JVM 범위(ADR 0025·0027과 같음).
- 차례 대기 + 실행이 Kafka 기본 `max.poll.interval.ms`(5분)를 넘어 소비자가 빠지지 않게 15분으로 늘린다.
- 영상 분석 뒤의 작은 파이썬 호출(후보 선택·검증 등)은 바꾸지 않는다.

## 확인할 것

운영 반영 뒤 같은 측정(`monitoring/limit/prod_analysis.py`, 쇼츠5·릴스5 + 조회 50명)으로 조회 p95·오류, 분석 성공 수, 인스타그램 차단 수를 전후 비교한다. 결과로 상태를 확정하거나 되돌린다.

## 운영 측정 결과와 바꾼 결정 (2026-11-08 21:29, #346 배포 fc561e3)

| | 적용 전(20:36) | 적용 뒤(21:29) |
|---|---|---|
| 조회 p95 / 오류 | 10초 / 50.4% | 10초 / 73.3% |
| steal 평균 | 1.44코어 | 1.51코어 |
| 분석 성공 | 쇼츠 4 | 쇼츠 4 |
| 릴스 | 시간 초과 3, 인스타 차단 2 | 시간 초과 5, 인스타 차단 0 |

- `nice`는 조회를 지키지 못했고 릴스만 굶겨 시간 초과를 늘렸다. 서버 안의 순서는 클라우드가 VM 전체에 주는 CPU 몫을 늘리지 못한다(추정).
  → **기본값 0(끔)**. 운영은 drop-in `PIPELINE_NICE=0`으로 먼저 껐다.
- 동시 1개 제한은 인스타그램 차단 0건(표본 1회)이라 유지한다.
- 분석과 조회가 겹칠 때 조회가 막히는 문제(문제 기록 #16)는 남는다. 다음 후보: 파이썬 CPU 절대 상한(cgroup), 릴스 처리 비용 줄이기.
