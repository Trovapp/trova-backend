# 0037. 운영 java의 GC·스왑 설정과 동시 사용자 한계 판단

- 날짜: 2026-11-08
- 상태: 확정 (운영 적용·운영 실측 완료)
- 관련: #331, #333, #335, #340, #342, 문제 기록 #12~#15(`docs/monitoring/2026-11-04-capacity-issue-log.md`)
- 근거 문서: `docs/monitoring/2026-11-04-full-gc-analysis.md`, `2026-11-07-replica-limit.md`, `2026-11-08-prod-limit.md`

"부하 한계 찾기"(2026-11-04~08)에서 문제를 하나씩 만나며 고른 해결책을, **문제 → 해결안 → 고른 것 → 이유** 순서로 남긴다.
각 선택은 그 시점에 사용자가 번호로 골랐다(작업 규칙: 문제가 생기면 해결안 2~4개를 보고하고 사용자가 고른다).

## 결론 (지금 운영 설정)

- GC: G1 (`-XX:+UseG1GC`, GC 로그 유지), 힙 최대 384MiB 그대로. → **2026-11-11 ADR 0040에서 144MiB로 바꿈**(영상 분석과 조회가 겹칠 때 G1 힙 확장으로 무너짐).
- java 서비스는 스왑 금지(systemd `MemorySwapMax=0`).
- Tomcat 스레드 상한·힙 축소·`MALLOC_ARENA_MAX`는 **넣지 않는다.** 운영 실측에서 필요가 없었다.
- 동시 사용자 한계는 운영 실측 숫자를 기준으로 본다(복제 환경 숫자는 설정 비교용).

## 1. 긴 GC 멈춤 (#331)

**문제**: 운영에서 Serial GC의 Full GC가 5~9.8초 멈췄다(힙 64MiB를 치우는 데 8.75초, CPU를 실제로 쓴 시간은 1.13초).

| 해결안 | 판단 |
|---|---|
| A. Serial 유지 + 원인만 관찰 | 멈춤이 사용자 요청과 겹치면 그대로 노출 |
| **B. G1로 전환 (고름)** | 복제 환경 비교에서 Full GC가 없고 멈춤이 짧았다 |
| C. 서버 사양 올리기 | 무료 원칙(유료 서버)과 충돌 |

**이유**: 설정 한 줄(systemd drop-in)로 되돌릴 수 있고, 복제 환경에서 Serial보다 멈춤이 짧았다. 비용이 들지 않는다.

## 2. G1에서도 1초 넘는 멈춤 — 원인은 스왑

**문제**: G1 전환 뒤에도 Remark 멈춤이 2.8~5.5초 나왔다. 기록기로 보니 메모리가 모자랄 때 커널이 java 메모리를 스왑으로 밀어내고, GC가 그것을 다시 읽으며 멈췄다.

| 해결안 | 판단 |
|---|---|
| 스왑 성향 낮추기(`swappiness=10`)+fwupd 끄기 | 먼저 적용 → 27분 뒤 다시 2.78초 멈춤, 부족 |
| **java 서비스 스왑 금지 `MemorySwapMax=0` (고름)** | 멈춤의 원인을 구조적으로 없앤다 |
| 같은 서버의 다른 수집기 옮기기 | safeKor 수집기는 정부 API 허용 IP가 이 서버라 옮기기 어렵다 |
| zram(압축 스왑) | 패키지 설치, 1/8 OCPU에서 압축 CPU 부담 |

**이유**: 적용 뒤 1초 넘는 멈춤 0회, 최대 0.21초, java 스왑 0을 확인했다(밤사이 최대 99.5ms).
**대가**: 메모리가 정말 모자라면 느려지는 대신 OOM으로 죽는다(5초 뒤 자동 재시작, UP까지 약 90초). 그래서 "몇 명이 몰리면 죽는가"를 재야 했다 → 3절.

## 3. 동시 사용자 한계 — 어디서 잴까

| 해결안 | 판단 |
|---|---|
| 운영에 반영하고 1~2일 관찰 | 실제 사용자가 설치만 하고 거의 쓰지 않아 신호가 약하다 |
| **운영 사양 복제 환경(로컬 Docker)에서 먼저 (처음 고름)** | 운영 위험 없이 설정을 바꿔 가며 비교할 수 있다 |
| **운영 서버에 직접 부하 (마지막에 고름)** | 사용자가 거의 없는 지금 가장 정확하다 |

복제 환경은 CPU 0.125코어 고정, 메모리 650MiB, 스왑 없음으로 운영을 흉내 냈다. 그 과정의 문제:

- **#12 520MiB에서 10명에 OOM** → 해결안: 650MiB로 다시 / 힙 줄이기 / 스왑 허용 / 기록만. **650MiB로 다시를 골랐다.**
  이유: 운영에서 java가 실제로 쓸 수 있는 메모리(java 429MiB + 남은 189MiB ≈ 620MiB)에 맞추는 것이 먼저였다.
- **#13 650MiB에서 60명에 OOM** → 해결안: Tomcat 스레드 상한 / 503 빠른 거절 / 스왑 일부 허용 / 기록만. **스레드 상한을 골랐다.**
  이유: CPU는 40명에서 이미 다 썼으므로 스레드를 200개까지 늘려도 빨라지지 않고 메모리만 쓴다고 봤다.
- **#14 스레드 30개로도 80~100명에서 OOM** → 해결안: 힙 256MiB+`MALLOC_ARENA_MAX=2` / 힙 밖 상한 / 스왑 허용 / 스레드만. **힙 축소+할당기 제한을 골랐다.**
  이유: 실제 살아 있는 힙은 60~70MiB인데 힙 최대 384MiB + 힙 밖 약 270MiB가 650MiB를 넘었다. 복제 환경 두 번 모두 100명까지 생존했다.
- **#15 새 설정에서 예열 뒤 처리량이 절반** → 해결안: 운영에서 직접 비교 / 복제 환경에서 원인 가르기 / 스레드만 / 기록만. **운영 직접 측정을 골랐다.**
  이유: 복제 환경 안에서 원인을 가르는 것보다, 사용자가 거의 없는 지금 운영에서 재는 것이 답에 바로 닿는다.

## 4. 운영 실측 결과와 최종 판단

운영 서버, 지금 설정(G1·384MiB·스왑 금지·스레드 기본 200), 테스트 계정 50명(끝나고 삭제):

| 동시 사용자 | p95 | 오류 | java |
|---|---|---|---|
| 60명 | 0.85초 | 0% | 정상 |
| 100명 | 1.1초 | 0% | 정상 |
| 200명 | 5.3초 | 0.3% | 정상 |
| 300명 | 10초(시간 초과) | 33% | **정상(죽지 않음)** |
| 50명 15분 지속 | 0.57초 | 0% | 정상 |

**최종 판단: 운영 설정을 바꾸지 않는다** (#13~#15의 해결책을 운영에 넣지 않음).

이유:
1. 복제 환경에서 OOM이 난 60명이 운영에서는 오류 0%였다. 운영 java는 CPU를 0.35~0.57코어까지 써서(버스트) 요청이 쌓이지 않았고, 메모리가 509~551MiB에 머물렀다.
   복제 환경은 CPU를 0.125코어로 고정해 운영보다 3~4배 비관적이었다.
2. 운영의 한계는 메모리가 아니라 CPU(무료 서버 몫, steal 0.6~1.1코어)였다. 스레드 상한이나 힙 축소는 CPU 한계를 풀지 못한다.
3. 새 설정은 복제 환경에서 예열 뒤 처리량을 낮출 수 있다는 신호(#15)가 있었다. 이득이 확인되지 않은 변경을 넣지 않는다.
4. 지금 실제 사용자는 12명이라 동시 60명(1초에 한 번씩 계속 누르는 사람 기준)까지 여유가 크다.

## 다시 검토할 때

- 영상 분석(파이썬·Gemini)과 조회 부하가 겹칠 때 남은 메모리가 76MiB(300명 때 최소) 아래로 내려가면 → 스레드 상한·힙 축소를 다시 꺼낸다(측정 도구 `monitoring/limit/run.py --threads --xmx --malloc-arenas`).
- 장시간(몇 시간) 지속 부하에서 steal이 커져 느려지면 → CPU 한계 대응(캐시, 서버 이전)을 검토한다.
- 서버를 옮기면(A1 등) 같은 운영 측정(`monitoring/limit/prod_run.py`)을 다시 한다. 이 서버 IP는 safeKor 수집기 정부 API 허용 IP이기도 하다.
- 복제 환경으로 버스트형 서버를 흉내 낼 때 CPU를 고정 상한으로 두면 한계를 크게 낮게 본다. 설정 비교에만 쓰고 절대 숫자는 운영에서 확인한다.
