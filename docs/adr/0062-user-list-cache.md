# 0062. 사용자별 목록 응답을 단일 JVM에서 20초간 재사용한다

2026-11-28 · 확정 · #563

## 결정

장소·북마크·여행 목록은 인증과 사용자 존재 확인을 마친 뒤 사용자 ID와 목록 종류로 응답 DTO를 찾는다. 기존 조회와 변환 함수가 반환한 목록을 보관하므로 권한·필드·정렬 규칙은 한 곳에서 관리한다. 같은 키로 동시에 들어온 조회는 Caffeine 로더 한 번을 공유한다.

목록 종류마다 최대 512행을 보관하며 빈 목록도 1행으로 센다. TTL은 생성 후 20초다. 캐시 미스 처리 중인 요청은 세 목록 합계 32개까지 허용하고 초과분은 HTTP 429로 반환한다. 이 상한에는 같은 키의 결과를 기다리는 요청도 포함된다. 이미 보관된 결과는 슬롯을 쓰지 않는다.

## 쓰기와 공유 권한

Spring 쓰기 가능 트랜잭션이 성공적으로 커밋되면 현재 캐시 세 개를 함께 교체한다. 다른 사용자의 여행 멤버십 변경, 장소 카탈로그 수정, 비동기 작업 완료에도 다음 요청이 최신 값을 읽는다. 교체 전에 시작한 조회는 이전 캐시에만 결과를 넣는다. 트랜잭션 안에서 목록을 요청한 호출자는 자기 트랜잭션에서 직접 읽는다.

쓰기 범위를 넓게 잡았으므로, 관련 없는 쓰기가 잦으면 캐시 적중률이 내려간다. 이 방식의 즉시 무효화 범위는 같은 JVM의 Spring 트랜잭션이다. 여러 애플리케이션 인스턴스나 외부 DB 쓰기를 도입하면 배포 전에 인스턴스 간 무효화 방식을 마련해야 한다.

## 운영

기본값은 별도 설정 없이 적용된다. 캐시 미스 상한은 `app.list-reads.max-concurrent-misses`에서 조정할 수 있다. 재측정에서는 성공 응답의 지연, 429, 5xx, 클라이언트 타임아웃을 함께 비교한다.
