# 0059 선택 분석 동의, 분석 식별자 분리와 삭제 대기열
- 상태: 확정 · 날짜: 2026-11-26 · 근거: 이슈 #547, 사용자 선택 동의 확정, 앱 #284 계약 및 코디네이터 답변

## 결정

- 필수 약관 동의와 분리한 `analytics_consents`를 사용한다. 두 선택 동의가 모두 true일 때만 무작위 UUID v4를 발급한다. 사용자 번호와 해시는 사용하지 않는다. 같은 동의 세대에서는 모든 기기가 같은 UUID를 받고 철회 후에는 새 UUID를 발급한다.
- `APP_ANALYTICS_NOTICE_READY`는 기본 false다. 실제 고지·방침·보관 기간·삭제 절차 검토와 게시 완료 전에는 켜지 않는다. false에서 하나라도 true인 PUT은 409다. 분석 동의를 거절해도 다른 기능은 사용할 수 있다.
- 사용자 행의 DB 쓰기 잠금을 PUT·DELETE·탈퇴에서 공유한다. CAS는 현재 revision 또는 마지막 변경의 동일 요청 재시도만 허용한다. DELETE에는 revision 조건이 없다. 응답은 no-store이고 UUID는 전용 인증 API에만 포함한다.
- 철회(부분 동의로 변경 포함)·탈퇴는 이전 UUID를 `analytics_deletion_jobs`에 등록한 뒤 연결을 지운다. 두 변경은 같은 트랜잭션으로 커밋/롤백한다. 삭제 큐에는 사용자 번호/FK를 넣지 않아 탈퇴 후에도 삭제 대상을 보존한다. 연결 테이블은 사용자 번호를 PK로 사용하며 삭제 생명주기는 UserAccountService가 관리한다.
- 이번 구현은 **삭제 큐 기록만** 한다. HTTP 클라이언트·자동 실행 작업자를 만들지 않는다. `POSTHOG_PERSONAL_API_KEY` 이름만 정의하고 키 값은 넣지 않는다. 키가 없거나 추가되더라도 자동 삭제 호출은 없고 PENDING을 유지한다. 완료로 꾸미거나 무조건 큐를 비우지 않는다.
- 실제 삭제 API·운영 재시도/알림·백업 만료 검증은 수집 활성화 전 별도 작업이다. PENDING은 외부 삭제 완료를 뜻하지 않는다. 삭제 완료 후에는 큐의 식별자도 운영 보관 정책에 따라 파기해야 한다.
- 신규 공유 링크/멤버를 만드는 트랜잭션에 UUID v4 이벤트 ID를 저장한다. 기존 링크/멤버 반환은 신규 false이며 이벤트 ID는 null이다. 기존 행은 backfill하지 않는다.
- signup은 이번 가입 흐름이 확인되지 않으면 계약대로 생략한다. 현 인증에는 가입 흐름 증거가 없다. 생성 시각이나 계정별 짧은 플래그만 쓰면 이후 로그인·다른 기기와 혼동할 수 있다. 확실한 결합에는 OAuth 사용자 생성, 로그인 성공/교환, JWT 발급/파싱/인증 토큰 전달을 함께 바꿔야 하므로 코디네이터가 정한 JWT 구조·만료·세션 정책 유지 및 인증 변경 범위 조건에 따라 생략한다. 신규 활성화 퍼널의 signup 단계는 아직 수집할 수 없다.

## 이유

선택 동의를 기본 거절로 유지하고, 여러 기기의 지연된 동의 요청이 최근 철회를 덮어쓰지 못하게 한다. 개인정보 연결을 지운 뒤 삭제 식별자를 잃거나 계정 탈퇴와 외부 서비스 장애를 결합하지 않는다. 기존 필수 동의 enum과 DB 검사 제약을 변경하지 않는다(ADR 0049).

## 비교한 대안

- 사용자 번호 해시: 번호 대입으로 연결할 수 있어 제외했다.
- 기기별 ID: 다른 기기와 삭제 대상을 안정적으로 연결할 수 없어 제외했다.
- HTTP 삭제를 동의 요청에서 실행: 외부 장애가 철회·탈퇴를 막고 이번 실제 호출 금지 범위를 벗어나 제외했다.
- 신규 가입 시각으로 판정: 기존 로그인과 늦은 동의를 구분하지 못해 제외했다.

## 다시 볼 조건

수집 활성화 전 실제 고지와 삭제 운영을 검증할 때, 가입 흐름에 인증된 일회성 증거를 전달하는 별도 계약을 도입할 때, 동의 버전을 변경할 때 재검토한다.
