# ADR 0055: 대안 찾기의 실내외 태그를 30일 재사용

- 상태: 채택
- 날짜: 2026-11-25
- 이슈: #537

## 배경과 결정

같은 장소의 대안 찾기·대화 요청에서 Gemini 실내외 태깅을 반복했다. `PlaceCatalogService.upsertAll`은 장소를 먼저 저장/조회하지만, `AlternativeFinderService.filterIndoor`는 그 뒤 `applySpaceTag`만 호출했다. 요청 전체를 감싸는 트랜잭션이 없고 카탈로그 조회가 반환한 엔티티는 영속 상태가 아니므로 변경 감지가 저장해 주지 않았다. 다음 요청에서 `space=null`을 다시 읽어 태깅했다. 별도 추천 경로는 `applyTags` 뒤 명시 저장하므로 기존 태그가 있는 경우와 없는 경우가 섞였다.

사용자 합의에 따라 성공한 공간 태그는 `places.space`와 nullable `space_tagged_at`에 함께 저장하고 30일 미만 동안 재사용한다. 정확히 30일이 되면 다음 실내 필터 요청에서 갱신한다. `INDOOR`뿐 아니라 `OUTDOOR`·`MIXED`도 재사용하되, 기존 응답 계약대로 실내 필터에는 `INDOOR`만 통과시킨다. 전체 태그를 설정하는 기존 `applyTags` 경로도 공간 태그의 생성 시각을 기록한다.

기존 태그의 생성 시각을 추측해 채우지 않는다. 시각이 null이면 다음 실내 필터 요청에서 다시 태깅한다. 무료 티어 429·프로세스 실패·응답 누락·빈 태그는 성공으로 저장하지 않고 다음 요청에서 재시도한다. 만료 태그의 갱신 실패 시 기존 태그와 시각은 유지하고, 기존 화면 오류 방지 처리를 유지한다.

## 저장과 관측

외부 호출 동안 트랜잭션을 열지 않는다. 태깅 성공 뒤 리포지토리의 짧은 갱신 트랜잭션으로 공간 태그 두 컬럼만 업데이트해 다른 요청의 리뷰·전화 갱신을 덮지 않는다. 여러 요청의 동시 최초 태깅을 합치는 기능은 포함하지 않는다.

이 레포에는 Flyway가 없고 Hibernate `ddl-auto: update`를 쓴다. 엔티티에 nullable 컬럼을 추가하며 동일한 참고 DDL을 [space_tagged_at.sql](../../db/supabase/space_tagged_at.sql)에 둔다. 기존 데이터 backfill·인덱스·운영 DB 변경은 없다.

단계 로그는 `실내태그=0ms(재사용 18·신규 0)`처럼 재사용 수와 새로 저장한 수를 기록한다. `trova.alternatives.space_tagging.calls` 카운터는 러너를 부를 때 증가하며 실패 시도도 포함한다. 사용자·장소 라벨은 쓰지 않는다. 30일 내 같은 후보의 재요청에서 외부 태깅 호출과 대기를 없애는 것이 기대 효과이며, 실제 운영 지연 개선은 배포 후 측정해야 한다.

## 검증

트랜잭션을 열지 않는 통합 테스트에서 실제 DB 재조회로 대안 찾기 및 대화 도구의 두 번 요청을 검증한다. 기존/신규 후보, 실외 태그 재사용, 30일 경계, 시각 없는 기존 데이터, 실패·누락·빈 태그의 재시도를 확인한다. 저장 삭제와 만료 비교 반전 변형이 테스트에 잡히는지도 확인한다.
