# 0040. 운영 java 힙 상한을 384MiB에서 144MiB로 낮춘다 (ADR 0037의 "힙 384MiB 그대로"를 바꿈)

- 날짜: 2026-11-11
- 상태: 확정 — 운영 측정 r19·r20·r21 뒤 사용자 결정("1", 2026-11-11). 운영 반영은 측정용 설정을 지우면서 `gc.conf`의 `-Xmx`만 바꾼다.
- 관련: #370, #368, #355, ADR 0037(힙 축소 기각 — 이번에 그 부분만 바꿈), 문제 기록 `docs/monitoring/2026-11-04-capacity-issue-log.md` #370 절

## 문제

ADR 0037은 "힙 축소는 넣지 않는다"고 정했고, 다시 검토할 조건으로 "영상 분석과 조회 부하가 겹칠 때 남은 메모리가 76MiB 아래로 내려가면"을 두었다.
2026-11-10~11 운영 측정(조회 50명 + 릴스 5개, 매번 새로 켠 서버)에서 그 조건이 반복해서 나왔다: 남은 메모리 최저 43~66MiB, 조회 오류 38.4~55.3%.

처음에는 서버 예열을 원인으로 봤지만, 예열을 끈 r18도 55.3%로 무너져 틀린 결론이었다(#370에서 정정).
메모리 추적(NMT)과 GC 로그로 보면 무너진 회차는 측정 중에 G1이 힙을 키웠다(잡아 둔 크기 120MiB → 180~244MiB). GC 직후 실제 사용량은 최대 115MiB였다.
956MiB 서버에서 늘어난 50~100MiB가 스왑·페이지 캐시 부족으로 이어져 GC가 더 느려지는 악순환으로 본다(추정).

## 해결안

| 해결안 | 판단 |
|---|---|
| A. 384MiB 그대로, 원인만 더 관찰 | 7번 중 4번 무너졌다. 실사용자가 영상을 공유하는 중에 조회가 멈출 수 있다 |
| **B. 힙 상한 144MiB (고름)** | 부하 중 GC 직후 최대 사용량(115MiB)보다 조금 크고, 무너진 회차의 힙(180~244MiB)보다 작다 |
| C. `-Xms=-Xmx`로 힙 고정(예: 160MiB) | B보다 시작부터 메모리를 더 잡는다. B로 충분하면 필요 없다 |
| D. 서버 사양 올리기·A1 이전 | 무료 원칙. A1은 아직 확보 못 함 |

## 근거 (운영 서버, 조회 50 + 릴스 5, 각 약 20분)

| 회차 | 힙 상한 | 예열 | 조회 오류 | 힙 잡아 둔 크기 최대 | 남은 메모리 최저 |
|---|---|---|---|---|---|
| r13·r14 | 384MiB | 끔 | 4.0%·2.3% | 120MiB(r14) | 118~119MiB |
| r15~r18 | 384MiB | 켬·끔 | 38.4~55.3% | 180~244MiB | 43~66MiB |
| r19·r20 | **144MiB** | 끔 | 15.2%·8.2% | 133·122MiB | 98·102MiB |
| r21 | **144MiB** | 켬 | **4.6%** | 117MiB | 114MiB |

- 144MiB 3번 모두 힙 부족 종료(`ExitOnOutOfMemoryError`) 0번, 재시작 0번, Full GC 0번. 0.5초 넘는 GC 멈춤은 회차당 3~11번(최대 1.1초).
- 원본: `docs/monitoring/2026-11-08-prod-analysis/r13-*`~`r21-*`(r17~r21은 `nmt.txt` 포함).

## 고른 이유

1. 384MiB에서는 같은 조건에서도 결과가 둘로 갈렸고(2~4% / 38~55%), 갈림이 힙 확장과 같이 움직였다. 144MiB 3번은 모두 무너진 쪽보다 낮았다.
2. 되돌리기 쉽다: systemd drop-in(`gc.conf`) 한 줄.
3. 비용 0, 다른 프로세스·서비스 추가 없음.

## 대가와 조심할 점

- 힙이 정말 모자라면 java가 종료된다(5초 뒤 자동 재시작, UP까지 약 2분). 지금까지 GC 직후 최대 115MiB라 여유는 약 29MiB뿐이다.
  사용자·데이터가 늘면 먼저 여기서 막힌다 → Grafana "Trova 필수 모니터링"의 힙 패널과 GC 멈춤을 본다.
- 144MiB에서 조회만 많은 경우 → 2026-11-11 재확인(#382, 아래 "재확인").
- 측정은 회차마다 흔들림이 크다(조건당 1~3번). "항상 좋아진다"가 아니라 "7번 측정에서 힙 상한 쪽이 일관되게 좋았다"까지가 근거다.

## 재확인 (2026-11-11, #382, 운영 서버)

힙을 줄인 뒤 아직 재지 않은 "조회만" 부하를 384MiB 때 측정과 같은 조건으로 다시 쟀다. 자세한 표는 `docs/monitoring/2026-11-04-capacity-issue-log.md` #382 절.

| 비교 | 384MiB | 144MiB | 판단 |
|---|---|---|---|
| 조회 50명, 평평해진 뒤(15~25분) 서버 p95 | 0.44초(r12) | 0.55초(r24) | 약 +0.1초. GC 분당 12 → 16~19회, 같은 시간 steal도 30 → 52라 힙 몫은 일부 |
| 인원 40 → 200명 p95 | 0.88 / 1.13 / 3.32 / 5.33초 (40·100·150·200명, 11-08) | 0.49 / 1.07 / 2.94 / 6.52초 (r25) | 비슷. 처리량 상한 둘 다 초당 약 75 |
| 200명에서 앱 종료 | 없음 | 없음(힙 committed 최대 135MiB, Full GC 0) | 힙이 작아도 몰릴 때 꺼지지 않음 |

결론: 결정 유지. 대가는 조회 지속 부하에서 p95 약 0.1초. 25~60분 구간은 아직 144MiB로 재지 못했다(측정 도구 기본 25분에 끝남).

## 다시 검토할 때

- GC 직후 힙 사용량이 120MiB를 넘는 날이 생기거나, 힙 부족 종료가 한 번이라도 나면 → 160~192MiB로 올리고 같은 측정을 한다.
- 서버를 옮기면(A1 등) 이 값은 다시 정한다.
