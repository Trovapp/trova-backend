# 0049 사용자 명시 동의와 버전 기록
- 상태: 확정 · 날짜: 2026-11-17 · 근거: 이슈 #456, 사용자 제공 백엔드·앱 API 계약

## 결정

- 간주 동의 대신 로그인한 사용자가 명시적으로 확인한 약관·개인정보처리방침 버전과 만 14세 이상 확인을 `user_consents`에 기록한다. 사용자 FK, 종류, 버전, 동의 시각을 저장한다.
- `ConsentType`은 최초 배포부터 `TERMS`, `PRIVACY`, `AGE_OVER_14` 세 값을 모두 `@Enumerated(STRING)`으로 정의한다. 운영 DB에서 Hibernate가 만든 enum 검사 제약은 `ddl-auto: update`로 갱신되지 않는다. 이후 값을 추가할 때는 운영 DB 검사 제약을 수동 변경해야 한다.
- `GET /api/me/consents`는 현재 약관·방침 버전 기록과 연령 확인 기록 중 하나라도 없으면 `needed=true`를 반환한다. `POST`는 현재 두 버전과 `ageOver14=true`만 받고 세 종류의 기록을 한 트랜잭션으로 저장한다. 같은 사용자·종류·버전은 중복 저장하지 않으며 최초 동의 시각을 보존한다. DB에도 해당 조합의 유일 제약을 둔다.
- 연령 확인의 version은 기준 연령인 `14`로 저장한다. 연령 확인 존재 여부는 버전과 무관하게 판단하므로 약관·방침이 개정되어도 연령 확인 행을 새로 쌓지 않는다. 기존 약관·방침 동의 이력은 보존한다.
- 현재 버전은 `app.consent.terms-version`, `app.consent.privacy-version`으로 관리한다(각각 기본 `2026-10-14`). 환경변수 `APP_CONSENT_TERMS_VERSION`, `APP_CONSENT_PRIVACY_VERSION`으로 실제 게시된 약관·방침 개정일에 맞춰 변경한다.
- 두 API는 로그인해야 한다. 사용자 엔티티가 필요하므로 `CurrentUserService.resolve`를 쓴다(ADR 0036의 ID 전용 조회 경로와 구분).
- 서버는 미동의 사용자의 다른 API를 차단하지 않는다. 앱이 `needed`를 보고 동의 화면을 표시한다. 인증 필터와 iOS 단축어 공유 키 경로에는 동의 검사를 추가하지 않는다.
- 탈퇴 시 모든 버전의 동의 기록을 사용자보다 먼저 같은 트랜잭션에서 삭제한다. 기존 사용자 캐시 제거 시점은 탈퇴 커밋 뒤로 유지한다.

## 이유

- 사용자가 어떤 문서 버전에 언제 동의했는지 서버에서 확인하고, 개정 시 재동의를 요청할 수 있어야 한다. 앱 설치·재설치나 기기 변경에 관계없이 기록을 유지한다.
- 서버 차단을 추가하면 기존 앱과 화면을 띄울 수 없는 iOS 단축어 공유가 영향을 받는다. 사용자 계약대로 화면 제어는 앱이 맡고 서버는 동의 상태·검증·기록을 제공한다.
- 사용자 삭제 전에 FK 참조 기록을 지워 탈퇴 실패와 동의 정보 잔존을 막는다.

## 비교한 대안

- 서버에서 미동의 요청 차단: 강제력이 있지만 기존 클라이언트·단축어 경로가 깨지고 API마다 예외 정책이 필요해 제외했다.
- 앱 로컬 저장만 사용: 구현은 작지만 재설치·다른 기기에서 기록이 사라지고 서버에서 버전·시각을 확인할 수 없어 제외했다.
- 외부 동의 서비스: 현재 세 종류의 기록에는 비용과 연동·운영 부담이 커서 제외했다.

## 다시 볼 조건

- 마케팅·맞춤형 광고 같은 선택 동의를 추가할 때 필수·선택 구분, 철회·보존 정책, 버전과 연령 확인 기준을 함께 재검토한다. enum 값을 늘릴 때 운영 DB 검사 제약 변경도 배포 작업에 포함한다.
