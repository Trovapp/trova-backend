# ADR 0052: 대안 장소 추천 이유는 규칙 문장으로 만든다

- 상태: 채택
- 날짜: 2026-11-20

## 배경

대안 장소 요청은 상위 두 후보의 Gemini 추천 이유를 순차로 기다렸다. 2026-11-19 운영 타이머 표본에서 추천 이유는 회당 약 9초였고, 사용자는 2026-11-20 짧은 규칙 문장을 선택했다. 개인화 순위에는 이미 계산한 점수를 쓰며, 화면은 `recommendationReason` 문자열이 있을 때만 표시한다.

## 결정

대안 경로만 기본적으로 Gemini 이유 생성을 중단한다. 상위 두 후보에 기존 좌표로 계산한 원래 장소와의 **직선 거리**, 일치하는 종류, 양수인 유한 개인화 점수, 유효한 평점, 양수 리뷰 수 순서로 최대 두 근거를 표시한다. 없는 값은 생략하고 아무 근거도 없으면 null을 반환한다. 거리 단위는 반올림 후 1,000m 미만이면 m, 나머지는 소수 한 자리까지 km다. 반올림한 거리가 0m이면 거리 근거를 생략한다. 거리는 원래 일정 장소 기준이며 현재 사용자 위치나 실제 이동 거리가 아니다. 거리순으로 후보를 재정렬하지 않는다.

작은 양수 점수가 종류 근거를 항상 밀어내지 않도록 종류 일치를 취향보다 우선한다. 종류 문구는 `같은 종류의 카페예요`처럼 동일 가게가 아닌 분류 일치임을 명시한다.

개인화 문구는 `취향과 비슷해요`로 통일한다. 점수 0은 조회 실패/신호 없음도 포함하므로 쓰지 않고, 음수·NaN·무한대도 제외한다(ADR 0051). 신호에는 찜 외 일정 추가도 있으므로 `찜한 곳`이라고 단정하지 않는다. 종류 비교는 한글 별칭과 음식점 하위 유형만 정규화하며, 검색용 넓은 분류로 박물관과 공원을 같다고 하지 않는다. `intaeng/ux-writing-ko`의 짧은 해요체·숫자 단위 규칙을 따른다.

기본 모드는 P7의 `personalizationScores`/`findCandidateSimilarities`를 그대로 재사용한다. 후보별 top-5, 유한값 제외, 평균 순서와 후보 정렬 규칙을 유지한다. 채팅의 Gemini 생성기와 다른 추천 경로는 변경하지 않는다.

`app.alternatives.gemini-explanation-enabled`(운영 환경 변수 `ALTERNATIVES_GEMINI_EXPLANATION_ENABLED`) 기본값은 false다. true로 설정하고 재시작하면 기존 후보별 신호 조회와 상위 두 개 Gemini 이유 생성으로 복구한다. 이는 개인화 N+1과 외부 지연도 복구하는 비상 옵션이다.

여행 전체 장소 조회에는 이미 필요한 EAGER 연관을 entity graph로 함께 읽는다. 신규 장소 INSERT 묶기는 공유 카탈로그의 동시 저장/충돌 처리에 영향을 주므로 이번에 변경하지 않는다.

## 결과와 검증

JSON 필드/후보 순서/필터는 그대로이고 이유 문자열의 내용만 바뀐다. 상위 두 곳 밖의 이유는 계속 null이다. Google 검색·임베딩 생성 횟수는 늘리지 않는다. 문구는 모델이 만드는 개별 맥락보다 단순하지만 응답 지연과 생성 비용이 줄고 근거를 재현할 수 있다.

실제 pgvector에서 기존 모드와 이유 외 응답 전체를 비교하고, 신호 있는 사용자 API에서 Gemini 0회와 후보 수 무관 SQL을 검증한다. 로컬 수치와 운영 예측은 [2단계 분석](../monitoring/2026-11-20-alternatives/analysis.md)에 기록한다. 운영 지연 개선은 배포 뒤 별도 확인하며 로컬 밀리초를 운영 개선량으로 단정하지 않는다.
