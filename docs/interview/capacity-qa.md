# 면접 노트 — 부하 테스트·병목 해결 (질문-답)

근거 문서와 숫자는 각 답 끝에. 숫자에는 항상 환경(운영/격리)과 조건을 붙여 말한다.

## Q. 성능 병목을 찾아서 개선한 경험이 있나요?
격리 환경에서 운영 사양을 흉내 내 장소 목록 API에 동시 사용자를 늘려 보니, 40명에서 p95가 2~3초로 늘고 DB CPU가 97%였습니다.
실행 계획을 보니 사용자별 조회가 테이블 전체를 훑고 있어서 `(user_id, created_at, id)` 인덱스를 추가했고,
같은 JVM·데이터에서 인덱스만 빼고 넣는 순서(ABBA)로 반복 측정해 p95 49~64ms, DB CPU 16%를 확인했습니다.
운영에 반영한 뒤에는 같은 방식으로 운영에서도 전후를 쟀는데, 운영 테이블이 277행이라 차이가 없었습니다.
그래서 “데이터가 늘었을 때를 위한 선제 조치”로 정리했고, 운영 응답 시간은 DB 밖에 있다는 걸 분해해서 확인했습니다.
(격리: `docs/monitoring/2026-11-02-index-abba.md`, 운영: `docs/monitoring/2026-11-04-prod-index.md`)

## Q. 왜 운영에서 바로 극한 부하 테스트를 하지 않았나요?
운영 서버가 메모리 1GB짜리 무료 인스턴스라 실제 사용자 장애 위험이 있고, DB가 Supabase 무료 티어라 서버 한계보다 DB 한도에 먼저 걸려
“서비스 한계”가 아니라 “무료 티어 한계”를 재게 됩니다. 그래서 극한은 운영 사양을 흉내 낸 복제 환경에서, 운영에는 분당 150건 정도의 약한 고정 부하만 걸고
응답 1건 2초·오류 1%·서버 메모리 기준을 넘으면 자동으로 멈추게 했습니다.

## Q. 운영에서 개선 효과가 없었다면, 그 작업은 의미가 없었던 건가요?
쿼리 시간이 0.26ms라 응답 270ms 중 비중이 거의 0이었습니다. 응답 시간을 분해해 보니 앱 내부 약 165ms, 서버→DB 왕복 31ms, 클라이언트→서버 왕복 40ms였습니다.
인덱스는 데이터가 늘면 격리 실험처럼 효과가 커지는 선제 조치이고, 이 분해 덕분에 다음에 고칠 곳(앱 내부 처리, DB 왕복 횟수)이 분명해졌습니다.
효과가 없다는 결과도 같은 조건에서 인덱스를 지웠다 다시 만들어 확인했습니다.

## Q. 처음 보는 장애나 멈춤을 겪은 적이 있나요?
운영 약한 부하 측정 중 평소 p95 400ms 정도인 API에서 요청 1건이 3초 시간 초과가 났습니다.
같은 시각 Prometheus를 보니 `jvm_gc_pause_seconds_max`의 major GC가 4.97초였고, DB 연결 5개가 모두 묶여 있었습니다.
JVM 옵션을 확인하니 GC를 지정하지 않아 작은 메모리 서버에서 Serial GC가 자동 선택돼 있었고, Full GC 동안 앱 전체가 멈춘(Stop-the-world) 것이었습니다.
힙 사용량은 90MiB뿐이라 CPU 한도(1/8 OCPU)나 스왑이 청소를 느리게 했다고 보고, GC 로그로 빈도를 확인한 뒤 Serial과 G1을 같은 부하로 비교할 계획입니다.
(진행 후 결과 추가)

## Q. 그럼 GC 없는 언어(예: Rust)로 바꾸면 되지 않나요?
GC 멈춤만 보면 맞지만, 백엔드 전체 재작성 비용이 크고 원인이 “GC 종류를 안 정한 설정”이라 JVM 설정으로 먼저 해결하는 게 비용 대비 맞다고 판단했습니다.
실제로 미디어 처리 일부를 Rust로 비교했을 때도 단독은 빨랐지만 Python에 붙이면 통신 비용으로 오히려 느려져(0.477→1.711ms) 기존 언어를 유지했습니다.

## Q. p95를 왜 보나요? 평균이면 안 되나요?
평균은 느린 요청 몇 개가 묻힙니다. 실제로 GC 멈춤이 있던 측정에서 평균은 291ms로 멀쩡했지만 최대는 3초였습니다.
p95는 “요청 100개 중 95개가 이 시간 안에 끝난다”는 뜻이라 대부분의 사용자가 겪는 최악을 보여 줍니다.

## Q. 측정 결과를 어떻게 믿을 수 있게 만들었나요?
- 같은 조건(같은 JAR·계정·부하·시간대)에서 한 가지만 바꿈. 운영에서는 배포 전에 인덱스만 바꿔 측정.
- 전/후를 번갈아 반복(ABBA, 있음→없음).
- 원본(k6 JSON, Prometheus 5초 간격 JSON, EXPLAIN)과 재현 스크립트를 커밋.
- 측정이 조기 중단되면 사유를 기록하고, 감시 기준을 고친 뒤 3분 완주로 다시 측정.

## Q. 응답이 느린 API를 어떻게 개선했나요?
앞에서 응답을 분해해 보니 다음에 고칠 곳이 DB 왕복 횟수였고, 운영에서 낮은 부하로 약 11분 조회했을 때 여행 상세가 p95 353ms로 주요 화면 API 중 가장 느렸습니다.
코드를 보니 일차마다 장소를 따로 조회하는 N+1이 있어서, 1단계에서 일차 1·3·5·7일 기준 SQL 6·10·14·18회를 일차 수와 상관없이 5회로 고정했습니다(로컬 H2).
그래도 남은 5회를 하나씩 뜯어보니 매 요청 사용자 행을 다시 읽고, 일차를 읽을 때 EAGER 연관 때문에 같은 여행을 한 번 더 읽고 있었습니다.
그래서 사용자 확인은 메모리 확인으로 돌리고, "여행 머리+소유자 확인 1회 + 일차 left join 장소 1회"의 scalar 조회로 바꿔 2회로 줄였습니다.
운영에서 같은 조건으로 재 보니 여행 상세 평균 267→105ms(-61%)였습니다. 초안 상세도 저장 장소 엔티티를 전부 불러오던 것(저장 장소 100개면 엔티티 204개)을 필요한 번호·주소 두 칸만 읽게 바꿔 평균 438→199ms가 됐습니다.
(1단계: `docs/monitoring/2026-11-18-perf-phase1/README.md`, 분석·개선: `trip-detail-analysis.md`, 운영 결과: `docs/monitoring/2026-11-19-p4-metrics/README.md`)

## Q. 왜 캐시나 서버 증설이 아니라 쿼리 횟수를 줄였나요?
응답 분해에서 쿼리 실행은 0.26ms인데 서버→DB 왕복이 31ms라, 비용은 SQL "시간"이 아니라 "횟수"에 있었습니다.
캐시는 적중하면 빠르지만 그 데이터를 바꾸는 쓰기 경로마다 무효화를 맞춰야 하고, 144MiB 힙에 상주 데이터도 늘어서 비슷한 목록 API에서 검토 후 보류했습니다. 더 큰 서버로 옮기는 건 작업 자체가 크고 왕복 횟수는 그대로입니다.
엔티티 매핑(EAGER→LAZY)을 바꾸면 다른 API까지 영향을 받아서, 이 조회 경로만 필요한 칸을 읽는 scalar 조회로 바꿨습니다.
대안도 비교했습니다. 사용자 확인만 바꾸는 A안은 5→4회로 가장 작지만 중복 조회가 남고, 한 쿼리로 합치는 5→1회는 일차 없는 여행 처리가 복잡해져 2회 안을 골랐습니다.
(`docs/monitoring/2026-11-04-prod-index.md`, `trip-detail-analysis.md`의 개선안 비교, PR #477)

## Q. 응답이 바뀌지 않았다는 걸 어떻게 보장했나요?
고치기 전에 이전 응답 조립을 테스트로 옮겨 두고, 새 경로의 실제 JSON 출력과 바이트 단위로 같은지 비교하는 테스트를 먼저 만들었습니다(빈 일차, 날짜 미정, 장소 0개, 일차 0개, 30일 약 300장소 등).
쿼리 수는 1/3/5/7/30일 모두 2회로 고정하는 테스트를 두었고, 구현 전에는 이 테스트가 실패하는 걸 먼저 확인했습니다.
테스트가 진짜 잡아내는지 보려고 일부러 방문 순서를 뒤집으면 2건, inner join으로 바꿔 빈 일차를 빼면 4건이 실패하는 것을 확인한 뒤 원복했습니다.
남의 여행·없는 여행 404, 인증 없음·탈퇴 사용자 401도 그대로 고정했고, 요청당 SQL 측정 코드는 구현한 것과 다른 AI 모델로 교차 리뷰했습니다.
(PR #477·#478·#474, `trip-detail-analysis.md`의 P5·P6 결과)

## Q. 로컬에서는 왜 차이가 거의 없었나요?
로컬 테스트 DB(H2)는 같은 프로세스 메모리에 있어 왕복 비용이 거의 0이라, 여행 상세 1일 기준 0.784→0.656ms 정도만 줄었습니다.
운영은 서버(Oracle 도쿄)↔Supabase 왕복이 SQL마다 붙어서, 3회를 줄이자 평균 162ms(회당 약 54ms)가 줄었습니다.
같은 변경이 로컬과 운영에서 이렇게 다르게 나온 게 "이 서버의 병목은 CPU가 아니라 DB 왕복 횟수"라는 근거가 됐습니다.
그래서 로컬 측정에서는 쿼리 "횟수"만 믿고, "시간"은 운영에서 따로 잽니다.
(`docs/monitoring/2026-11-19-p4-metrics/README.md`의 로컬 vs 운영)

## Q. 실사용자가 거의 없는데 운영 효과를 어떻게 쟀나요?
처음에는 배포 전후 야간 50분씩을 비교했는데 대상 API 요청이 0건이라 아무것도 판단할 수 없었습니다.
그래서 Android 에뮬레이터와 iOS 시뮬레이터로 같은 화면 흐름을 사람 속도로 약 20분씩 동시에 쓰면서 조회만 해, 배포 직전 기준선과 재시작 31분 뒤 표본을 같은 방식으로 만들었습니다. 부하 시험이 아니라 평소 사용 수준이라 운영 측정 규칙 안에서 했습니다.
손대지 않은 목록·장소 API는 전후 평균이 거의 같아서(예: 여행 목록 133→132ms) 비교 구간이 공정하다는 것도 확인했습니다.
요청당 SQL 수 지표를 먼저 배포해 두어서, 운영에서도 여행 상세 2회·초안 상세 3회로 실제로 줄었는지 함께 봤습니다.
(`docs/monitoring/2026-11-18-perf-phase1/README.md`의 배포 전/후 비교, `docs/monitoring/2026-11-19-p4-metrics/README.md`의 운영 전후 비교)

## Q. 측정에서 실수한 적은 없나요?
1단계 배포 뒤 첫 표본이 여행 상세 약 7.7건뿐이었는데, 평균 352→355ms를 보고 "여행 상세는 변화가 없다"고 판단했습니다.
표본을 30건으로 다시 재 보니 352→259ms(-26%)로 실제로는 개선돼 있었고, 그 뒤로 경로당 30건 정도를 목표로 하고 표본 수를 결과와 항상 같이 적습니다.
같은 첫 표본에서 p95는 1,082ms였는데, 건수가 적으면 p95가 히스토그램 버킷 경계와 몇 안 되는 느린 요청에 크게 흔들려 믿기 어렵다는 것도 배웠습니다.
(`docs/monitoring/2026-11-18-perf-phase1/README.md`의 배포 후 표본 비교·표본2)

## Q. 예측과 실측이 달랐던 적은 있나요?
여행 상세는 기존 왕복 31.5ms 기준으로 "3회 줄이면 평균 약 165ms"로 예측했는데, 실측은 105ms로 60ms 더 줄었습니다.
회당 약 54ms로, SQL 수에 보이지 않는 읽기 트랜잭션 종료 같은 왕복도 함께 줄었을 수 있다고 보지만 이번에 분해하지는 않았습니다.
초안 상세도 예측(약 63ms 절감)보다 큰 239ms가 줄었는데, 저장 장소 엔티티 로딩 제거 효과가 함께 들어 있다고 구분해 적었습니다.
(`trip-detail-analysis.md`의 운영 결과)

## Q. 요청당 쿼리 수 지표로 무엇을 찾았나요?
응답 시간만 보면 빈 시간 장소 추천 API가 느린 이유가 외부 검색(Google)인지 DB인지 구분이 안 됐는데, 요청당 SQL 수를 경로별로 남기자 평균 20.15회(운영 35건)로 다른 API(1~4회)보다 훨씬 많다는 게 보였습니다.
코드를 따라가 보니 추천 후보 장소마다 개인화 점수를 내려고 DB를 두 번씩 오가는 N+1이었고, 후보별 상위 5개 유사 신호를 한 번에 구하는 묶음 SQL과 일차·장소 한 번 읽기로 바꿨습니다.
운영에서 같은 방식으로 다시 재 보니 요청당 3.48회(-83%)였고, 평균 874→393ms(-55%), p95 2,104→873ms(-59%)였습니다. 다른 API의 SQL 수는 그대로였고 5xx는 0건이었습니다.
(`docs/monitoring/2026-11-19-p4-metrics/gap-recommendations-analysis.md`의 운영 전후 비교, PR #483)

## Q. H2 테스트만으로 부족했던 경험이 있나요?
빈 시간 추천의 개인화 SQL을 묶음으로 바꾸면서 응답 비교 테스트와 쿼리 수 테스트를 H2로 먼저 만들었고 모두 통과했습니다.
그런데 다른 AI 모델로 교차 리뷰를 하니, H2에는 벡터 칸이 없어 이전·새 경로가 둘 다 "점수 0"으로 폴백하므로 새 SQL이 틀려도 테스트가 통과한다는 지적이 나왔습니다.
그래서 Testcontainers로 운영과 같은 PostgreSQL 17 + pgvector 컨테이너를 띄워 사용자 5명 × 후보 14개 = 70쌍의 점수와 최종 추천 순서가 이전 경로와 같은지 실제로 비교했습니다. 동점 거리·0 벡터·임베딩 없음 같은 경계도 넣었고, 일부러 `LIMIT 5`를 6으로 바꾸면 실패하는 것도 확인했습니다.
그 과정에서 0 벡터가 NaN 점수를 내는 기존 결함도 찾았는데, 이번 변경 범위가 아니라 별도 과제로 남겼습니다.
(`gap-recommendations-analysis.md`의 pgvector 실제 동일성, PR #483)

## Q. 개선했는데 중앙값(p50)이 오히려 늘었다면 어떻게 설명하나요?
빈 시간 추천 API는 운영 전후 평균 874→393ms, p95 2,104→873ms로 줄었는데 p50은 342→492ms로 늘었습니다.
이 API는 "빈 시간 없음"으로 바로 끝나는 빠른 응답과 외부 장소 검색이 들어가는 느린 응답이 섞여 있고, 개선 후 표본은 추천 목록이 실제로 열린 비율이 높았던 것으로 보입니다. 느린 종류의 비율이 늘면 SQL이 줄어도 중앙값은 올라갈 수 있습니다.
다만 개선 전 표본의 응답 종류 비율은 기록하지 않아 확정할 수 없어서, 결과는 평균·p95·요청당 SQL과 함께 보고하고 p50 증가는 한계로 그대로 적었습니다. 다음에는 응답 종류별로 나눠 잴 계획입니다.
