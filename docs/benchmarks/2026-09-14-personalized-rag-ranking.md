# 개인화 추천(RAG) 실측 (2026-09-14)

실제 배포 브랜치(main, PR #3 머지 후)를 로컬에서 기동하고, 시뮬레이터 앱으로 실제
클릭하며 만든 데이터 + Postgres 직접 조회 + 실제 HTTP 호출로 관측한 수치(감으로
정한 값 아님).

## 배포 중 발견하고 고친 버그 2건

실측하지 않았으면 발견 못 했을 버그들 — 둘 다 "공식 문서와 실제 API 응답이 다름"
케이스였다.

1. **임베딩 API 응답 파싱 실패**: 코드는 `{"embeddings": [{"values": [...]}]}`(복수,
   배열)를 기대했는데, 실제 Gemini `gemini-embedding-001:embedContent` 응답은
   `{"embedding": {"values": [...]}}`(단수, 객체)였다. 배포 직후 `api_call_logs`를
   조회해서 발견 — 임베딩 호출 40건 전부 성공(HTTP 200)인데 파싱은 100% 실패하고
   있었다. 기존 테스트도 잘못된(가짜) 응답 형태를 검증하고 있어서 못 잡았다(커밋
   `8fec61e`).
2. **신호가 기록돼도 임베딩이 안 되는 경로 존재**: 임베딩은 "대안 찾기/빈 시간
   추천/추천" 3곳에서 후보로 뜰 때만 생성되는데, 신호는 "여행에 담기"처럼 그 3곳을
   안 거치는 경로에서도 기록됨. 실측해보니 신호 5개 중 4개가 임베딩 없는 장소를
   가리켜서 개인화 계산에서 무시되고 있었다. 신호 기록 5곳 전부에 즉시 임베딩
   호출을 추가해서 해결(커밋 `4087fcf`).

## 임베딩 파이프라인 실측

기존 카탈로그 352개 장소를 전부 백필(신설한 `/api/admin/backfill-embeddings`)했다.

| 항목 | 값 |
|---|---|
| 총 장소 수 | 352 |
| 임베딩 성공(최종) | 352 (100%) |
| 1차 시도 성공/실패 | 247 / 145 |
| 2차 재시도(1차 실패분만) | 105 시도 → 105 성공 |
| 성공 호출 평균/최대 지연시간 | 432ms / 1,068ms |
| 실패 호출 평균/최대 지연시간 | 218ms / 674ms |

- 1차 시도에서 145건(41%)이 실패했다가 재시도로 전부 성공 — 332건을 순차 동기
  호출로 몰아서 보냈을 때의 일시적 레이트리밋으로 추정된다(Gemini 임베딩 자체는
  무료 티어 한도가 넉넉하다고 알려져 있지만, 실측상 짧은 시간에 수백 건을 몰아
  보내면 일부는 실패함 — 재시도로 복구 가능하다는 것까지 확인).
- `PlaceEmbeddingService.ensureEmbeddings`가 실패한 건을 조용히 건너뛰고 계속
  진행한다는 설계(부가 기능 실패해도 본 기능 안 죽음)가 실제로 동작함을 확인 —
  145건 실패에도 나머지 207건은 정상 처리됐다.

## RAG 검색(Retrieval) 실측 — pgvector 코사인 유사도

가장 최근 신호(`ALTERNATIVE_REPLACED`, "Cafe Onion Anguk", 카페)의 임베딩과 카탈로그
전체를 pgvector `<=>` 연산자로 직접 비교:

```
종로왕만두              (dumpling_restaurant)  유사도 0.8990
아티스트베이커리 안국   (cafe)                 유사도 0.8879
카페 레이어드 북촌      (cafe)                 유사도 0.8805
커피한약방              (cafe)                 유사도 0.8802
도토리가든 안국점       (coffee_shop)          유사도 0.8782
```

상위 5개 중 4개가 실제로 카페/커피숍 — 임베딩이 카테고리 단위 의미 유사도를 실제로
포착하고 있음을 확인. (1위가 만두집인 건 의외인데, 이름이 만두집이지 상세 카테고리가
`dumpling_restaurant`라 결과물 그대로 남겨둔다 — 리뷰요약/분위기 텍스트가 임베딩에
같이 들어가서 카테고리 텍스트만으로는 설명 안 되는 유사도가 나올 수 있다는 뜻으로
해석.)

## 전체 파이프라인(Retrieval+Generation) 실측 — 실제 HTTP 호출

`GET /api/trip-places/34/alternatives` (해당 장소 = "Cafe Onion Anguk" 자신, 신호
5개가 이미 있는 상태)를 실제로 호출:

- 후보 19개 반환, 상위 2개에만 `recommendationReason`이 채워지고 3위부터는 정확히
  `null` — `EXPLANATION_TOP_N = 2` 설계대로 동작.
- 생성 호출(`recommendation-explanation`) 실측 지연시간: 927ms, 1,000ms (2건, 1건당).
- 실제 생성된 문구(호출마다 문구가 달라짐 — Gemini 생성이라 결정적이지 않음, 정상):
  - "Gyeongbokgung Palace — 광화문광장과 인접하여 선호하는 역사 문화 탐방에
    완벽합니다."
  - "북촌 한옥마을 — 광화문·안국 인근의 고즈넉한 한옥 감성을 즐기기 좋습니다."

## 발견한 한계 — 개인화 부스트가 인기도에 묻힘

이번 실측에서 나온 19개 후보는 카페뿐 아니라 궁궐/한옥마을/호텔까지 섞여 있었다
(카테고리 필터를 안 걸고 호출함). 결과적으로 상위 2개는 전부 유명 랜드마크
(리뷰 46,809개짜리 경복궁 등)였고, 코사인 유사도가 가장 높았던 카페들
("아티스트베이커리 안국" 등, 위 표 참고)은 후보 19개 중 17위 근처로 밀려났다.

원인은 랭킹 공식(`baseScore + personalizationScore * 0.5`)에서 `baseScore =
rating * ln(reviewCount+1)`의 스케일이 개인화 부스트보다 훨씬 크기 때문이다 —
경복궁 baseScore ≈ 4.6 * ln(46809) ≈ 49.5, 반면 개인화 부스트는 최대
1.0(완전 유사) * 0.5 = 0.5. 리뷰 수 차이가 큰 카테고리 혼합 검색에서는 개인화가
사실상 순위에 영향을 못 준다는 뜻 — 카테고리 필터를 걸고 검색하면(예: "카페"만)
이 문제가 덜할 것으로 예상되지만 실측은 안 함.

**개선 방향(제안, 아직 미적용)**: `PERSONALIZATION_BOOST_WEIGHT`를 고정값 0.5 대신
`baseScore`에 비례한 값으로 만들거나(예: `baseScore` 최댓값 대비 비율), 아예 두
점수를 정규화한 뒤 합치는 방식으로 재검토가 필요해 보인다. 지금 값은 실사용
데이터 없이 `RecommendationService`의 기존 상수를 그대로 가져온 것이었는데,
실측해보니 카테고리 혼합 검색에서는 사실상 무의미한 수준이라는 게 이번에 새로
확인된 사실이다.

## 가중치 수정 후 재검증 (같은 날, 곱셈 부스트 배포 후)

`PERSONALIZATION_BOOST_WEIGHT`를 덧셈(0.5)에서 `baseScore * (1 + score * 0.6)`
곱셈 방식으로 바꾼 뒤(커밋 `a631554`), 같은 장소로 재검증.

- 카테고리 필터 없이(궁궐/호텔/카페 혼합): 순위 그대로 — 경복궁(리뷰 46,809개)과
  동네 카페의 인기도 격차가 워낙 커서 곱셈 부스트로도 못 넘음. 의도한 대로다(인기도
  격차가 극단적으로 큰 카테고리 혼합 검색까지 개인화가 뒤집어버리는 건 오히려
  부자연스럽다).
- **카테고리를 "카페"로 필터링하면 실제로 순위가 뒤바뀜을 확인**: "이도림"(평점 4.8,
  리뷰 1,280개)이 "청수당 베이커리"(평점 4.4, 리뷰 1,855개 — 리뷰 수가 더 많음)보다
  위로 올라옴. 두 baseScore가 원래 비슷한 범위(34.3 vs 33.1)였던 걸 개인화가
  뒤집은 것 — 비슷한 인기도 안에서는 개인화가 실제로 순위에 영향을 준다는 걸
  확인했다.
- 두 후보 모두 실제 생성된 추천 이유가 붙음: "안국과 명동의 아늑한 감성을
  좋아하셔서요"(커피한약방), "아늑한 분위기와 맛을 모두 갖춘 한옥 카페입니다"(이도림).

## 비용 관점 요약

- 임베딩(`gemini-embedding-001`): 무료 티어, 352건 백필 + 이후 신규 5건 = 357건
  누적, 관측된 실패(레이트리밋 추정)는 재시도로 전부 복구됨 — 운영 시 배치 백필은
  한 번에 몰아서 하지 말고 간격을 두는 게 안전해 보임.
- 생성(`gemini-3.5-flash-lite`): 무료 티어, 요청당 최대 2건으로 설계대로 제한됨
  (실측 2건, 927ms/1,000ms).
