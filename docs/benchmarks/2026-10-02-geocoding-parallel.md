# 장소별 카카오 검색을 동시에 보내기 (#7)

## 문제
- 영상 하나에서 뽑은 장소를 카카오 지오코딩할 때 장소마다 하나씩 차례로 호출했다(`PlaceExtractionService` 반복문).
- 같은 변경이 PR #8(커밋 `42703bd`)에 있었지만, 그 뒤 main에 주소 우선 지오코딩(#62)이 들어오면서 `geocode(...)` 형태가 바뀌어 그대로 합칠 수 없었다. PR #8은 닫고 지금 구조에 맞게 다시 옮겼다.

## 바꾼 것
- `KakaoGeocodingService.geocode(...)`를 둘로 나눴다(기존 `geocode`는 둘을 이어 부르므로 동작 같음).
  - `searchCandidates(이름 후보, 지역, 주소, jobId)`: 주소 → 이름 후보 순 검색. 다른 장소 결과를 보지 않으므로 동시에 불러도 안전.
  - `resolveRegionFallback(이름 후보, 지역, 이미 쓴 좌표, jobId)`: 지역 중심 좌표 폴백. 앞 장소들의 좌표와 겹치면 버리므로 장소 순서대로 하나씩.
- `PlaceExtractionService`: 후보 검색은 모든 장소를 동시에 보내고, 결과를 장소 순서대로 받으며 필요한 장소만 폴백한다.
- `AsyncConfig.geocodingTaskExecutor`: 8개 고정(core=max, 쉬면 스레드 정리). PR #8의 core 4·max 8은 큐(100)가 차기 전엔 4개까지만 동시에 나가서 바꿨다.
- 처리 로그에 `ProcessingJob {id} 지오코딩 {n}곳: {ms}ms`를 추가했다(측정에 사용).

## 측정 (로컬, 2026-10-02)
- 환경: Mac 로컬, 개발 DB. 수정 전 JAR(main + 시간 로그만)과 수정 후 JAR을 8090·8091에 동시에 띄우고, 같은 유튜브 쇼츠를 번갈아 제출(순서도 번갈아). 영상 5개 × 2회.
- 파이프라인 스크립트는 양쪽 모두 로컬 서버 폴더(`92ba6ee`, #92 공항·역 규칙 이전)의 것을 썼다 — 지오코딩 비교에는 영향 없음.

- 결과 동일성: 같은 영상의 수정 전·후 두 쪽에 모두 나온 장소는 좌표가 전부 같았다. 장소 목록 자체가 다른 쌍은 Gemini가 매번 조금 다른 장소를 뽑은 것(예: 묵호 9곳 vs 11곳).

- 영상 전체 처리 시간(6~29초) 중 Gemini가 대부분이라, 이번 단축(장소 7~10곳 기준 약 0.3~0.6초)은 전체에서 작은 몫이다.

## 운영 측정 (2026-10-02 배포 후, 테스트 계정, 측정 뒤 데이터 삭제)
- 운영 서버(E2.1.Micro, 1/8 OCPU)에 `dd2aeba` 반영 후 김해·묵호 쇼츠를 3번씩 분석(작업 61~66).
- 수정 후 지오코딩 구간(로그 줄): 1389ms(6곳, 재시작 직후 첫 작업), 570ms(7곳), 523ms(6곳), 652ms(8곳), 373ms(8곳), 673ms(8곳).
  재시작 직후를 뺀 5건 중앙값 570ms, 장소당 약 75ms.
- 수정 전 운영에는 이 로그 줄이 없어서 `api_call_logs`의 카카오 호출 기록으로 비교했다(추정치):
  작업 51~60(9/30~10/2, 순차 호출)에서 첫 호출 기록~마지막 호출 기록 간격은 장소당 116~136ms.
  마지막 호출 자체의 시간이 빠진 값이라 실제 구간보다 약간 짧다.
- 운영에서는 동시에 보낸 호출 하나하나가 느려졌다. 작업 62는 카카오 호출 7회 시간 합이 2063ms로, 순차였던 작업 59의 1026ms(7회)의 두 배다.
  CPU가 작아서 동시 요청끼리 시간을 나눠 쓰는 것으로 보인다(원인 확인은 안 함). 그래서 운영 단축 폭(장소당 약 125ms → 75ms)은 로컬(94 → 35ms)보다 작다.
- 재시작 직후 첫 작업은 호출 6개가 각각 약 1.2초 걸려 수정 전보다 느렸다(1회만 관찰).

## 확인하지 않은 것
- 카카오 API의 동시 요청 제한: 공식 문서에서 초당 제한 수치를 확인하지 못했다. 이번 측정(한 영상 최대 11곳, 동시 8개)에서 카카오 호출 실패 로그는 없었다.
