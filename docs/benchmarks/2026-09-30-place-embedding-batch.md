# 새 장소 임베딩 묶음 요청 (#73, PR #74)

## 문제
처음 보는 지역에서 AI 대화로 장소를 찾으면, 새 장소 임베딩을 `embedContent`로 하나씩 순서대로 만들었다(한 번 만든 임베딩은 DB에 저장돼 다시 만들지 않는다).

## 측정
| 환경 | 측정 | 결과 |
|---|---|---|
| 로컬(Mac), Gemini 직접 | 같은 장소 문장 19개 | 하나씩 19번 **9.92초** / `batchEmbedContents` 1번 **1.34초**, 벡터 동일(코사인 유사도 1.0) |
| 운영 서버(Oracle), 수정 전 | 전주 영상, 첫 대화 "근처 카페 추천해줘" | 첫 대화 **16.9초**, 새 임베딩 16개 하나씩 약 8.4초 |
| 로컬(Mac, 개발 DB), 수정 후 | 전주 영상, 같은 대화 | 첫 대화 8.5초, 새 임베딩 20개 묶음 1번 1.33초 |
| 운영 서버(Oracle), 수정 후 | 강릉 영상(운영에 임베딩 없던 지역), 같은 대화 | 첫 대화 **13.9초**, 새 임베딩 16개 묶음 1번 **1.23초** |

무료 한도는 묶음 안의 문장 수로 센다(분당 100, 하루 1,000). 묶어도 사용량은 같다.

## 운영 수정 후 시간 분해 (강릉, `api_call_logs` 시각)
| 구간 | 시간 |
|---|---|
| 대화 1차 호출 + 장소 검색 | 약 1초 |
| 태그 붙이기(Python 파이프라인, Gemini 2.1초 포함) | 약 3.9초 |
| 임베딩 묶음 요청 | 1.2초 |
| 묶음 요청 끝 → 검색어 임베딩 시작 | **약 4.3초(원인 미확인)** |
| 정렬, 대화 2차 호출 | 약 1.5초 |

- 임베딩 생성 자체는 8.4초 → 1.2초로 줄었지만, 첫 대화 전체는 16.9초 → 13.9초(3.0초)만 줄었다.
- 4.3초 구간은 수정 전(전주)에도 1.6초 있었다. 늘어난 몫은 장소마다 한 번씩 하는 임베딩 DB 저장(16번, 운영에서 Supabase까지 왕복)으로 추정한다. 수정 전에는 이 저장 시간이 하나씩 만드는 8.4초 안에 섞여 있었다. 측정으로 확인하지는 않았다.
- 수정 전후는 지역이 다르다(전주/강릉). 새 임베딩 수(16개)와 질문은 같다.
