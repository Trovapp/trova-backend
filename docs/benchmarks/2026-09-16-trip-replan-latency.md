# 전체 일정 재구성(TripReplanGraph) 응답시간 실측 (2026-09-16)

이 워크트리(`feat/trip-replan`, Task 1~4 전부 구현·리뷰 완료된 상태)의 실제
백엔드를 로컬에서 실제 Supabase DB에 연결해 띄우고, 실제 사용자 계정으로 발급한
JWT로 실제 운영 데이터에 있는 여행에 `POST /api/trips/{tripId}/replan`을 2회
실제 호출해서 관측한 수치(감으로 정한 값 아님). Task 4 구현 서브에이전트는
샌드박스 제약으로 실제 시크릿에 접근하지 못해 이 실측을 못 했고("숫자 지어내지
말고 왜 못 했는지 남기라"는 지침에 따라 벤치마크 문서를 건너뜀), 컨트롤러 세션이
직접 이어서 측정했다.

## 테스트 대상

실제 운영 DB에서 가장 후보군이 풍부한 여행을 골랐다 — `trips.id=8`, 장소 8개 중
6개가 `space='OUTDOOR'`(재구성 대상), `indoorOnly=true` 요청.

## 실측 응답시간

| 시도 | HTTP 상태 | 응답시간(wall-clock) | 결과 |
|---|---|---|---|
| 1회차 | 200 | **44.36초** | replaced 3건, failed 3건 |
| 2회차 | 200 | **47.14초** | replaced 3건, failed 3건 |

두 번 다 같은 여행에 같은 조건으로 호출했는데 결과(3건 성공/3건 실패)가 완전히
동일하게 나왔다 — 그래프 로직 자체는 결정적이고 안정적으로 동작함을 확인했다
(응답시간만 변동, 판정 결과는 안 변함).

**결론: 계획 문서가 우려했던 "최악의 경우 수십 초"가 실제로 맞았다.** 6개
타겟짜리 실제 여행에서 44~47초는 어떤 모바일 클라이언트의 동기 HTTP 요청
기준으로도 감당하기 어려운 수준이다.

## 원인 — `api_call_logs`로 실제 호출 내역 확인

같은 시간대의 `api_call_logs`를 조회해서 시간이 어디서 소모되는지 직접 확인했다.
타겟(재구성 대상 장소) 하나를 처리할 때마다 `AlternativeFinderService.findAlternatives`
내부에서 실제로 이런 외부 호출들이 순차적으로 일어난다:

| 호출 종류 | 실측 지연시간 | 발생 조건 |
|---|---|---|
| `google-places / nearby-search-alternative` | 95~450ms | 타겟마다 1회(항상) |
| `gemini / tag_places`(실내외 온디맨드 태깅) | 1.7~2.6초, 이상치 1건 **18.08초** | 후보 중 `space` 미태깅 장소가 있을 때(`AlternativeFinderService.filterIndoor`) |
| `gemini / place-embedding` | 350~510ms | 후보 중 임베딩 없는(katalog에 처음 잡힌) 장소마다 — 한 타겟에서 최대 13건 몰림 |
| `gemini / recommendation-explanation` | 800~1230ms | 상위 2개 후보에 대해 타겟마다 최대 2회(`EXPLANATION_TOP_N`) |

한 타겟 처리에 순서대로 태깅(최대 ~2.5초, 가끔 훨씬 김) + 임베딩 버스트(새 후보가
많으면 최대 10건×~450ms ≈ 4.5초) + 설명 생성 2회(~2초)가 쌓이면 **타겟 하나에도
5~10초가 걸리는 게 이상하지 않다** — 이걸 6개 타겟에 대해 **완전히 순차적으로**
반복하니 40초를 넘긴다.

`TripReplanGraph`의 그래프 구조(`identify_targets → route_next → fetch_candidates
→ check_conflict → ...`) 자체가 **타겟을 하나씩 순서대로만** 처리하도록 설계돼
있어서(백트래킹도 같은 타겟 안에서만 순환, 타겟 간 병렬 처리는 전혀 없음), 이
비용이 타겟 수에 그대로 선형으로 쌓인다 — 이번 실측으로 새로 발견한 사실이다.

## 비용 관점에서는 문제 없음

무료 티어 한도 차원에서는 이번 실측 중 어떤 호출도 실패(429 등)하지 않았다 —
`api_call_logs`에 잡힌 모든 행이 `success=true`(설명 생성 2건만 `false`, 일반적인
개인화 콜드스타트/근거 없음 폴백으로 추정, 기존에도 있던 동작). 문제는 비용이
아니라 **순차 처리 구조로 인한 응답시간**이다.

## 결론 및 다음 단계

계획 문서(`docs/superpowers/plans/2026-09-16-trip-replan.md`)의 "이 계획 이후"
절에 이미 명시된 조건("v1 실측 결과 응답 시간이 너무 길면, 비동기 처리로 전환하는
별도 계획을 검토한다")이 실측으로 확인됐다 — **44~47초는 너무 길다.** 동기 응답을
그대로 유지하는 건 이 규모(타겟 6개)에서도 이미 무리이고, 선형으로 늘어나는
구조(타겟마다 처리 시간이 그대로 더해짐)를 그대로 6→10으로 외삽하면
`MAX_TARGETS=10`(실제 배포되는 상한)에서는 **약 75~80초**로 늘어날 것으로
추정된다(이번엔 6개까지만 실측, 10개 실측은 안 함 — 추정치이지 실측치 아님을
명시).

**이 수치가 이 브랜치의 머지를 막지는 않는다** — 이 API는 읽기 전용 미리보기이고
(확정은 여전히 기존 `replacePlace`를 사용자가 직접 눌러야 함), 아직 이 엔드포인트를
호출하는 클라이언트(앱 UI)가 전혀 없다. 하지만 **다음 두 가지 중 하나라도
진행되기 전에는 반드시 비동기 처리 전환이 선행돼야 한다**: (1) 앱 쪽에서 이
엔드포인트를 호출하는 UI를 붙이는 것, (2) 이 엔드포인트를 실제 배포 환경에
노출하는 것 — 75~80초는 대부분의 인그레스/모바일 HTTP 클라이언트 기본 타임아웃
(보통 60초)을 넘어서서, 그 자체 설정값 안에서도 504로 끊길 가능성이 높다.

다음 세션에서 비동기 처리(기존 `ProcessingJob` 패턴 — 작업 생성 후 폴링) 전환을
위한 별도 브레인스토밍/스펙을 진행할 것 — 위 게이트 조건과, Gemini 무료 티어
RPM(분당 요청) 버스트 한도를 타겟별로 어떻게 제어할지(타겟 하나당 태깅+임베딩+
설명생성 호출이 몰려서, 10타겟 동시 처리 시 15 RPM 한도를 넘을 수 있음 — 이번
실측에서는 6타겟이라 429가 안 났을 뿐, 10타겟이나 동시 사용자 2명 이상에서는
발생할 수 있음)를 그 스펙에 반드시 포함시킬 것.
