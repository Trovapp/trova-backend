# 운영 서버(Oracle E2.1.Micro) 부하 테스트 실측 (2026-09-21)

trova-app이 실제로 쓰고 있는 라이브 백엔드(`https://193-123-161-217.sslip.io`,
Oracle Cloud Always Free `VM.Standard.E2.1.Micro`, 1/8 OCPU · RAM 956MB, JVM
힙 `-Xmx384m`으로 제한)에 k6로 직접 부하를 걸어서 관측한 수치(감으로 정한 값
아님). 테스트 대상 엔드포인트는 `GET /actuator/health`(인증 불필요, 순수
서버/인프라 처리량을 보기 위해 선택 — 실제 비즈니스 API는 OAuth 토큰이 필요해
스크립팅이 복잡해짐).

## 테스트 환경

- 서버: Oracle Cloud `buildlog-backend-e2`, Ubuntu 22.04, Java 21(Temurin),
  Spring Boot 앱을 `trova` 계정으로 직접 실행(k3s/컨테이너 없이 `java -jar`),
  Caddy가 리버스 프록시 + 자동 HTTPS
- 부하 발생: k6(로컬 macOS에서 원격 서버로 HTTPS 요청)
- 베이스라인(무부하 단건 요청): 250ms(TLS 핸드셰이크 포함)

## 1. 스트레스 테스트 — 점진적 증가

**방법**: VU(가상 사용자) 수를 0 → 200까지 30초 단위로 단계적으로 늘림
(0→10→30→60→100→150→200), 총 3분 20초.

| 지표 | 값 |
|---|---|
| 총 요청 수 | 33,579건 |
| 처리량 | 167.9 req/s |
| 에러율 | **0%** (33,579건 전부 200 OK) |
| 응답시간 평균 | 459.8ms |
| 응답시간 p90 | 907.4ms |
| 응답시간 p95 | **1.21초** |
| 응답시간 최댓값 | 9.78초 |
| 서버 메모리 peak | 664MB / 956MB (69%) |
| 서버 loadavg(1분) peak | 0.72 |

**결론**: 200 동시접속까지도 에러 없이 전부 응답은 했지만, 응답시간이
베이스라인(250ms) 대비 최대 39배까지 늘어났다. 메모리는 664MB로 전체의
69%까지만 썼고 OOM은 없었다 — **병목은 메모리가 아니라 CPU(1/8 OCPU)였다.**
Tomcat 스레드풀이 요청을 큐에 쌓아두고 처리하느라 지연이 누적된 것으로 보인다.

## 2. 스파이크 테스트 — 급격한 증가

**방법**: 평소 수준(5 VU)을 15초 유지하다가, 5초 만에 300 VU로 급격히
올리고 20초 유지 후 다시 5초 만에 5 VU로 급락. 총 1분 5초.

| 지표 | 값 |
|---|---|
| 총 요청 수 | 8,289건 |
| 처리량 | 127.4 req/s |
| 에러율 | **0%** (8,289건 전부 200 OK) |
| 응답시간 평균 | 934.2ms |
| 응답시간 p90 | 2.08초 |
| 응답시간 p95 | **2.59초** |
| 응답시간 최댓값 | 5.8초 |
| 서버 loadavg(1분) peak | **1.87** (스파이크 발생 5초 만에 0.15 → 1.87) |

**결론**: 같은 서버인데도 "급격한 300 VU 스파이크"가 "점진적인 200 VU
증가"보다 오히려 더 나쁜 지연을 만들었다(p95 2.59초 vs 1.21초) — 최대
동시접속 수는 스파이크 쪽이 더 많았으니 당연한 결과이긴 하지만, **부하가
급격히 튀면 loadavg가 순식간에(5초 만에) 12배 뛰는 것**을 실측으로 확인했다.
이 구간에서도 에러는 0건이었다 — 느려지기만 했지 죽지는 않았다.

## 종합 결론

- 이 스펙(1/8 OCPU, RAM 1GB)의 서버는 **300 동시접속까지도 에러 없이 버텼다**
  — 단, 응답시간은 심각하게 늘어난다(정상 250ms → 최대 9.78초).
- 병목은 메모리가 아니라 CPU다. 메모리는 테스트 내내 여유(peak 69%)가 있었다.
- 트래픽이 서서히 느는 것보다 갑자기 튀는 게 같은 최대치 기준으로 더 가혹하다
  — 오토스케일링이나 큐잉/백프레셔 없이 스레드풀만으로 버티는 구조라 스파이크에
  특히 취약하다.
- 에러율 0%인 건 긍정적이지만, 이건 "죽지 않았다"는 것이지 "정상 응답 속도를
  유지했다"는 뜻은 아니다 — 실제 서비스라면 p95가 1초를 넘는 순간부터 이미
  사용자 경험은 나빠진 상태다.

## 재현 방법

```bash
k6 run stress-test.js   # 점진적 스트레스 테스트
k6 run spike-test.js    # 급격한 스파이크 테스트
```
