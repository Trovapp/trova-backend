# Gemini 재시도 대기 시간에 상한 두기 (#7)

## 문제
- `pipeline-test/extract_places.py`의 `call_gemini`(장소 추출·선택·검증·일정·태그·리뷰 요약 스크립트가 함께 씀)는 429/5xx에서 최대 5번 시도하며,
  재시도 전 대기를 5→10→20→40초로 늘리고 `Retry-After` 헤더가 있으면 그 값을 상한 없이 따랐다.
- 서버는 파이프라인 전체를 5분(`PipelineRunner.TIMEOUT_MINUTES`)에 끊는다. 대기만으로 이 시간을 크게 잡아먹을 수 있었다.
- 운영 기록(운영 DB `api_call_logs`, 읽기만): 2026-09-05 작업 18의 장소 수집 호출이 503 "high demand"로 5번 실패하며 132초 걸렸다.
  같은 날 작업 17은 파이프라인 시간 초과로 끝났다(그때는 영상 다운로드 흐름).
- PR #8(커밋 `1e51460`)에 같은 상한(30초)이 있었지만 그 PR은 9월 22일 기준이라 따로 옮겼다.

## 바꾼 것
- `MAX_RETRY_DELAY = 30.0`: 지수 증가 대기와 `Retry-After` 헤더 대기를 30초로 자른다.
- 분당 한도 안내(`retryDelay`, 기존 60초 이하만 따름)는 그대로 둔다 — 분당 한도는 1분 안에 풀리므로 30초로 자르면 다시 걸릴 가능성이 크다.
- PR #8에 있던 나머지는 옮기지 않았다.
  - 요청당 대기 120→30초: 9월 30일(유튜브 링크를 Gemini에 바로 넘기기 시작) 이후 운영 성공 호출 42건이 중앙값 2.9초·최대 10.2초였지만,
    긴 영상(쇼츠가 아닌 것)을 바로 넘길 때 걸리는 시간은 기록이 없어 줄이지 않았다.
  - 시도 6번·서버 제한 8분: 상한만으로 최악 대기가 줄어서 늘리지 않았다.

## 확인 (로컬, 실제 API 호출 없음)
`docs/benchmarks/scripts/gemini_retry_delay_check.py` — 응답을 가짜 503/429로 바꿔 쉬는 시간만 기록.

| 상황 | 수정 전 대기 | 수정 후 대기 |
|---|---|---|
| 503 계속 | 5, 10, 20, 40 (합 75초) | 5, 10, 20, 30 (합 65초) |
| 503 + `Retry-After: 120` | 120 × 4 (합 480초, 5분 초과) | 30 × 4 (합 120초) |
| 429 분당 한도 `retryDelay 45s` | 45 × 4 (합 180초) | 그대로 |

- 파이프라인 스크립트 전부 `py_compile`·import 확인. 정상 응답 경로는 바뀌지 않았다.

## 확인하지 않은 것
- Gemini가 실제로 `Retry-After` 헤더를 보내는지(응답 헤더는 기록하지 않아 알 수 없음). 헤더가 숫자가 아닌 날짜 형식이면 `float()`에서 실패하는 기존 문제도 그대로 있다.
- 요청 하나가 응답 없이 120초를 다 채우는 경우는 여전히 최악 5 × 120초 + 대기 65초로 5분을 넘을 수 있다.
