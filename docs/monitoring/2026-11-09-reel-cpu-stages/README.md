# 릴스 분석 단계별 CPU와 줄이기 (#350, 2026-11-09)

배경: 문제 기록 #16 — 릴스(서버 내려받기·프레임 추출) 처리 CPU가 조회 응답을 무너뜨렸다. 무료 서버 CPU 몫은 고정이라 릴스 한 건의 CPU를 줄인다.

## 1. 운영 서버 단계·명령별 CPU (조회 부하 없음, Gemini·DB 미사용)

도구: `monitoring/limit/reel_cpu_stages.py` — 운영 스크립트(`/opt/trova-backend/pipeline-test`, main과 해시 같음)로 내려받기→오디오→프레임만 실행.
측정 전 확인: 다른 작업(alloy 수집기 조정)이 01:08~01:11 UTC에 있었고, 조용해진 뒤(부하 평균 0.57) 쟀다. 원본 `result.json`.

| 릴스 | 영상 | yt-dlp | 오디오(ffprobe+ffmpeg) | 프레임 | 합계 |
|---|---|---|---|---|---|
| DQRNtv2kvpJ | vp9 720×1280, 17초 | 5.9초 | 1.5초 | **15.1초**(전체 디코딩 14.7초) | 23.6초 |
| DeBanBWpxgq | vp9 720×1280, 32초 | 7.7초 | 1.7초 | **10.5초**(지점 이동 4회 9.9초) | 19.8초 |
| DTum25dgZEX | 인스타 429로 막힘 | 4.1초 | – | – | 4.1초 |

- 가장 무거운 단계는 프레임(53~64%), 다음이 yt-dlp(25~39%). yt-dlp는 켜는 데만 CPU 약 1.8초(`yt-dlp --version`, 압축 실행 파일).
- 측정 중 steal 틱이 서버가 일한 틱의 약 3배였다(쉬는 상태에서도 CPU 몫이 작음).
- 3번째 릴스가 429로 막혀 다시 시도하지 않았다(운영 IP가 막히면 실제 사용자 분석도 막힘).

## 2. 줄일 후보 확인 (로컬 Mac, ffmpeg 9.0.1 — 비율만 사용)

| 확인 | 결과 |
|---|---|
| 해상도 540 vs 720(같은 vp9 릴스, 디코딩 CPU) | 0.33초 vs 0.56초(−41%) |
| 전체 디코딩 스레드 기본 vs 1개 | 0.65초 vs 0.56초(−14%), 걸린 시간은 0.32→0.55초 |
| 짧은 영상에도 지점 이동 | 효과 없음: 인스타 키프레임 5초 간격이라 17초 영상은 전체 디코딩보다 더 푼다 |
| `res:480`/`res:540` 정렬 | 540이 없는 릴스에서 360×640을 받거나(프레임을 키움) 크기 정보 없는 형식을 골랐다 |
| `res~620`(620에 가장 가까운 것) | 540 있으면 540, 없으면 720 — 의도대로 |

적용(사용자 선택 1, 정정 후 1): 내려받기 `res:720` → `res~620`, 전체 디코딩 `-threads 1`.

## 3. 장소 정확도 전후 (로컬 Mac + Gemini 무료 티어, 평가 세트 릴스 8개, 각 1회)

도구: `eval/extraction/reel_ab.py`(ABBA 순서, 정답 `answers.csv`와 이름 포함 비교). 원본 `accuracy-ab.json`.

| | 정답 맞힘 | 프레임 CPU 합(로컬) |
|---|---|---|
| 전(res:720, 스레드 기본) | 12/13 | 5,775ms |
| 후(res~620, 스레드 1) | 12/13 | 4,326ms(−25%) |

- 장소 목록은 8개 중 6개가 같았다. 24번은 후에 2곳을 더 찾았고, 25번은 둘 다 정답을 못 맞혔다(전 "해운대 바다김밥", 후 "해운대") — Gemini 응답 차이로 본다(1회씩이라 단정 못 함).
- 영상별: 540이 있는 릴스(22·23) 프레임 CPU −43%, 짧아서 전체 디코딩하는 h264 720(19·21) −35~38%, 지점 이동을 쓰는 긴 영상·720만 있는 영상(24·25·26)과 360만 있는 영상(20)은 변화 없음.
- Gemini 사용: 18회(키 오류로 거절된 16회는 사용량 아님으로 추정).
