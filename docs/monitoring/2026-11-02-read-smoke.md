# 운영 저부하 조회 실험과 그래프 해석

2026-11-02 KST, 사용자 요청으로 헬스체크 → 테스트 계정 장소 목록 순서로 실행했다.
모두 동시 1명, 최대 30건, 요청 사이 1초 대기, 최대 60초로 제한했다.
영상/AI 요청, 사용자 데이터 변경, 운영 설정 변경, 백엔드 배포는 하지 않았다.

## 실행별 결과 — 중단된 실행도 보존

| 실행 | 요청 수 | 결과 | 중단/완료 이유 |
|---|---:|---|---|
| 최초 health | 1 | 중단 | 스왑 읽기 35페이지 증가, 초기 기준 v1 |
| 같은 기준 health 재시도 | 6 | 중단 | 스왑 읽기 3페이지 증가, 초기 기준 v1 |
| health, 기준 v2 | 30 | 완료 | HTTP·응답 형태 검사 통과, 자원 중단 조건 없음 |
| places, 기준 v2 | 18 | 중단 | 새 스왑 쓰기 1페이지(4KiB), 계획한 30건 미완료 |

네 실행을 합쳐 성공한 30건처럼 집계하거나 중단 실행을 삭제하지 않았다.

v1은 스왑 읽기/쓰기 누적치가 조금이라도 증가하면 중단하는 초기 기준이었다.
요청 없는 30초 관찰에서도 스왑 읽기 3페이지가 증가했다. 메모리 여유는 약 278MiB,
별도 확인한 memory PSI some/full avg10은 0이고 vmstat 간격 표본의 si/so도 0이었다.
소량의 page-in만으로 현재 메모리 고갈을 단정할 수 없어, 이후 실행 전에 기준 v2를 명시했다.

v2: 여유 메모리 100MiB 미만 / 새 swap-out / swap-in 속도 초당 1MiB 이상 /
memory PSI some avg10 1% 이상 / 수집 실패면 중단. HTTP 오류·단일 응답 2초·p95 1초 기준은 유지했다.
수치는 서비스 SLO나 입증된 안전 용량이 아닌 이번 관찰의 임시 운영 기준이다.
PSI는 자원 부족 때문에 작업이 지연된 시간을 나타내며 swap-in/out과 다른 지표다.
[Linux PSI 문서](https://www.kernel.org/doc/html/v6.6/accounting/psi.html),
[vmstat 설명](https://man7.org/linux/man-pages/man8/vmstat.8.html).

places에서 새 swap-out이 관찰된 뒤에는 기준을 다시 바꾸거나 재실행하지 않았다.

[Grafana 시간 구간](http://localhost:3300/d/trova-read-smoke?from=1793545613535&to=1793545692772)
· [저장된 그래프](2026-11-02-health-v2.png)

그래프의 파란 배경은 실제 테스트 시간이다. 그래프 번호 순서로 읽는다.

1. **클라이언트 응답 시간:** 대부분 약 100~150ms, 간헐적으로 175~232ms까지 올라갔다.
   시간이 갈수록 계속 느려지는 패턴은 이 짧은 표본에서 확인되지 않았다. 30건의 p95는 장기 SLO가 아니다.
2. **요청/초:** 계단처럼 올라가고 테스트가 끝난 직후에도 남는다. 15초 간격 수집값을 1분 이동 구간으로
   계산하기 때문이다. 새로운 요청이 계속 들어온다는 뜻은 아니다. k6의 실제 평균 0.885건/초와
   그래프 값이 같아야 하는 것도 아니다. health에는 다른 운영 확인 요청이 섞일 수 있다.
3. **서버 평균 시간:** 관측 테스트 구간 약 65~67ms. k6는 HTTP 전송·응답 대기·수신을 포함하는 다른
   측정 경계라 더 길 수 있다. 차이를 전부 네트워크 문제로 단정하지 않는다. `http_req_duration`은
   초기 DNS/TCP/TLS 연결 시간을 포함하지 않으며 이들은 별도 지표다.
4. **Java CPU:** 관측 최대 약 1.27%. 이번 낮은 부하 표본에서 큰 상승은 보이지 않았다.
   이를 서버 전체 CPU 여유나 최대 동시 처리 능력으로 바꿔 표현하지 않는다.
5. **메모리:** Java 힙 약 79.7~90.3MiB, SSH 관찰 기준 서버 여유 약 259~279MiB.
   힙 사용량과 서버 전체 여유는 서로 다른 범위다. 30초 동안의 완만한 증가만으로 메모리 누수를 판단할 수 없다.
6. **DB 연결:** 활성/대기 연결은 수집 표본에서 모두 0이었다. 15초 사이에 짧은 DB 확인이 끝날 수 있으므로
   DB를 전혀 사용하지 않았다는 뜻이 아니다. 연결 부족으로 기다린 증거를 이번 표본에서 찾지 못했다는 의미다.

기존 「Trova 모니터링 시작하기」의 API 요청 패널은 actuator를 제외한다. 이번 health 요청이 보이지 않는 것은
설정상 정상이며, 새 「Trova 저부하 테스트」 대시보드에서 `/actuator/health`를 명시적으로 포함했다.
차트 조회 간격 5초는 원본 15초 표본을 더 자주 표시할 뿐 해상도를 높여 주지 않는다.

## 3. 병목 개선 여부

이번 자료로 특정 코드의 병목은 확정하지 못했다. 목록은 이미 EntityGraph로 작업·사용자를 함께 읽으며,
과거 N+1을 고친 기록이 있다. 새 SQL 횟수/구간별 DB 지연/할당량을 측정하지 않은 상태에서 캐시나 DB 설정을
바꾸면 원인과 개선 효과를 설명할 수 없어 앱 성능 수정과 개선 후 재측정은 진행하지 않았다.

이번에 개선·검증한 것은 **관찰 도구**다: 헬스체크를 누락하던 그래프에 전용 화면을 추가하고,
스왑 읽기 1페이지에도 반응하던 임시 중단 기준을 자원 압력 지표와 구분했다. 이를 앱 성능 향상으로 쓰지 않는다.
다음 단계는 운영에서 부하를 높이는 것이 아니라 격리 환경에서 같은 크기 데이터의 SQL 횟수·DB 구간·메모리 할당을
측정하고, 실제 병목이 재현되면 그 부분만 고친 뒤 같은 조건으로 비교하는 것이다.

## 검증과 증거

- [원본 집계·요청별 시간·Prometheus 시계열·자원 표본](2026-11-02-read-smoke-results.json).
- 로컬 fixture 9개 테스트 메서드 통과: 정상·응답 오류·리다이렉트·지연·상한·토큰 누락·읽기 응답 형태.
- 자원 중단 기준의 정상/작은 page-in/낮은 메모리/swap-out/높은 swap-in/PSI 경계 검사 통과.
- 최종 운영 UP, 진행 작업 0, 마지막 작업 127 유지. 새 영상/AI 작업 및 사용자 결과 삭제 없음.
- 그래프는 저장된 JSON만으로 `docs/monitoring/scripts/plot_read_smoke.py`에서 재생성한다(matplotlib 필요).
- 실행 도구 `monitoring/run_observed_smoke.py`는 자격 증명을 발급하지 않는다. 기존 테스트 계정의
  단기 토큰 파일과 명시적인 운영 실행 옵션을 받아 제한된 GET만 실행한다.
