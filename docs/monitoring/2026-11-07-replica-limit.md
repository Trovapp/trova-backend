# 운영 사양 복제 환경 동시 사용자 한계 (2단계, #342)

- 환경: **로컬 Docker 복제 환경**(운영 아님). 앱 CPU 0.125, G1, 힙 384MiB, CPU 2개로 인식, 스왑 없음(운영 `MemorySwapMax=0`).
  DB는 같은 Docker의 Postgres 17(운영 Supabase보다 왕복이 짧다 → 운영보다 낙관적).
- 데이터: "서비스가 커졌을 때" 가정 — 사용자 50명 × 저장 장소 40·찜 10(폴더 2)·여행 2(3일 × 4곳)·안 읽은 알림 3. 운영(11-05)은 사용자 12명, 장소 283.
- 부하: `monitoring/limit/load.js` — 앱 조회 화면 9종(장소·여행 목록·여행 상세·찜·폴더·알림·분석 대기·내 정보)을 섞어 부르고 응답 뒤 1초 쉰다.
  VU = 앱을 계속 쓰는 사용자 한 명. 각 VU 첫 15초 제외. 기준 p95 ≤ 1초, 오류 ≤ 1%(실험 목표, 운영 SLO 아님). 영상 분석(Gemini)은 제외.
- 원본: `2026-11-07-replica-limit/`(단계별 `runs.json`, GC 로그, 예열 뒤 k6 요약, 시뮬레이터 화면).

## 1. 메모리 520MiB (2026-11-07 13:17)

1명 p95 298ms, 5명 492ms(CPU 포화), **10명에서 컨테이너 OOM 강제 종료**. 문제 기록 #12. 운영 java가 실제로 쓸 수 있는 양(RSS 약 430MiB + 가용 약 200MiB)보다 빡빡해 650MiB로 다시 쟀다(사용자 선택 1).

- 예열된 서버는 **40명까지 기준 안**(p95 0.9초, 초당 약 30요청)이고 CPU 0.125를 다 쓴다. 이 근처가 응답 속도 한계다.
- **60명에서 메모리 한도(650MiB)를 넘어 커널이 java를 죽였다**(`OOMKilled=true`, 종료 코드 137). 힙이 아니라 동시 요청이 늘며 커지는 힙 밖 메모리(스레드 등) 때문이다. 문제 기록 #13.

같은 조건으로 두 번. 원본 `run6a-x256-*`, `run6b-x256-*`.

|---|---|---|

| 20명 | 2.8초 / 0% / 511MiB | 3.7초 / 0% / 520MiB |

- **두 번 모두 100명까지 앱이 죽지 않았다.** 최고 메모리 545·560MiB로 한도까지 90MiB 이상 남는다. Full GC 0회.
- 넘치는 요청은 줄을 서다 클라이언트 시간 초과(10초)로 실패한다(오류 3~9%). 부하가 빠지면 바로 회복한다.
- 응답 속도는 CPU 0.125가 정한다(새 JVM은 10명부터 p95 1초 초과, 예열된 상태는 3절). 최대 GC 멈춤 1.3초(2차 100명, CPU 제한 아래 Young GC).
- 확인 못 한 것: 이 설정에서 예열된 JVM의 속도(3절의 40명 p95 0.9초가 유지되는지), 기동 시간(한 번 277초 걸려 측정 도구 대기를 10분으로 늘림).

## 결론과 다음

- 응답 속도 한계: 예열된 상태 약 40명(초당 약 30요청), 재시작 직후는 약 10~20명. 병목은 CPU 0.125.
- 더 급한 위험은 메모리다. 스왑을 막은 지금은 동시 요청이 몰리면 느려지는 대신 **죽는다**(문제 기록 #13·#14).
- 스레드 상한 30 + 힙 256MiB + `MALLOC_ARENA_MAX=2`면 100명에서도 죽지 않고 느려지거나 일부 시간 초과로 끝난다(6절). 운영 반영은 사용자 결정.
