값은 `/actuator/prometheus`의 `http_server_requests_seconds_{count,sum}`을 앱 열기 전(15:13:36)·후에 저장해 뺀 것(요청 1건의 서버 처리 시간).
원본: `prometheus-before-open.txt`, `prometheus-after-open.txt`.

- 예열 후(11-10): 배포 427d727(#357 예열 + #359 지표 직접 전송) 재시작 15:08, UP 135초, 예열 2회 뒤(15:10:31) 약 3분 지나 첫 열기.

- DB 연결 풀은 원인이 아니다: 10개 모두 미리 열려 있었고(새로 만든 연결 0), 연결을 받기까지 가장 오래 걸린 것이 0.09초.
  남은 차이는 홈 API 5개가 동시에 와서 CPU(1/8 OCPU)를 나눠 쓰는 몫과, 예열 2회로 다 데워지지 않은 코드 경로로 추정한다(미검증).

- 사용자 체감: "엄청 빨라졌네"(예열 전 재시작 직후 약 10초, 평소 4초, #125 뒤 약 2초).

## 2차: 예열 5회·홈 API 동시 (#362, 배포 3587659, 재시작 16:53)

예열 로그(운영): 1회차 4.9초 → 5회차 0.59초. 5회차의 홈 API 5개(동시) 0.18~0.30초 = 데워진 서버 수준.

| API (요청 1건) | 1차 예열 뒤 첫 열기 (15:14) | **2차 예열 뒤 첫 열기 (16:58)** | 2차 두 번째 열기 (17:13) |
|---|---|---|---|
| `/api/auth/me` | 0.14초 | 0.19초 | 0.12초 |
| 홈 API 5개 | 0.49~1.18초 | **0.56~1.18초** | 0.13~0.24초 |
| `POST /api/push/subscriptions` | 2.1초 | 1.4초 | 0.28초 |

- **효과 없음.** 예열 자체는 데워진 수준까지 내려갔지만, 몇 분 뒤 실제 첫 열기의 홈 API는 1차와 같았다.
- 같은 앱 요청(동시 10개 이상)인 두 번째 열기(15분 뒤)는 0.13~0.24초 → 원인은 동시 요청 수가 아니다.
- 남은 후보(미확인): 1/8 OCPU에서 JIT 컴파일이 밀려 재시작 뒤 몇 분 동안 덜 최적화된 코드가 돈다, 예열이 지나지 않는 경로(다른 사용자 데이터, 브라우저 CORS 사전 요청 등).
  두 번째 열기 구간의 요청 수(`me` 5건 등)에는 다른 사용자 요청이 섞였을 수 있다.
- 판단: 해가 없어(시작 때 약 8초 CPU) 5회·동시를 그대로 둔다. 재시작 직후 첫 몇 분만의 문제라 더 파지 않는다.
