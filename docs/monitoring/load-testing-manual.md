# 부하 테스트 매뉴얼 — 모니터링 → 병목 발견 → 개선 → 재측정

Trova 백엔드에서 실제로 해 본 순서를 일반화한 매뉴얼이다. 다른 서비스에도 그대로 쓸 수 있게 “왜 하는지”와 “무엇을 확인하는지”를 같이 적는다.
실제 사례 링크는 각 단계 끝에 둔다. (작성 2026-11-04, 진행하면서 갱신)

---

## 0. 한 장 요약

```
목표 정하기 → 기준 정하기 → 환경 정하기(운영/격리) → 관측 준비(Prometheus·Grafana)
→ 안전장치 넣은 측정 도구 → 사전 확인 → 기준 측정(전) → 변경 → 같은 조건 재측정(후)
→ 무너지면: 멈추고 → 원인 찾기 → 기록 → 해결안 비교 → 선택 → 다시 측정
→ 보고서(조건·숫자·캡처·한계)
```

가장 중요한 원칙 세 가지
1. **같은 조건으로 전/후를 비교한다.** 조건이 다르면 숫자 비교가 무의미하다.
2. **숫자 옆에는 항상 조건을 붙인다.** “어디서(로컬/운영), 몇 명, 얼마 동안, 어떤 데이터”.
3. **운영은 지키고, 극한은 격리 환경에서.** 운영에는 약한 부하만, 무너뜨리는 실험은 운영 사양을 흉내 낸 복제 환경에서.

## 1. 용어 풀이

| 용어 | 뜻 | 예시 |
|---|---|---|
| VU (가상 사용자) | k6가 흉내 내는 사용자 1명. 요청 → 대기 → 요청을 반복 | 5 VU = 5명이 동시에 사용 |
| think time | 요청 사이에 쉬는 시간. 실제 사람은 화면을 보느라 쉰다 | 요청 뒤 2초 대기 |
| RPS | 초당 요청 수 | 5 VU × (1요청/약 2.3초) ≈ 2.2 RPS |
| p95 | 요청 100개 중 느린 쪽 5개를 뺀 가장 느린 응답 시간. “대부분의 사용자가 겪는 최악” | p95 425ms |
| 평균 vs p95 | 평균은 느린 요청이 묻힌다. 사용자 체감은 p95가 더 정확 | 평균 291ms인데 1건은 3초 |
| 오류율 | 실패한 요청 비율 | 1% 미만이면 통과 |
| 처리량 포화 | VU를 늘려도 RPS가 더 안 늘어나는 지점. 이후엔 대기만 길어짐 | |
| 병목 | 전체 속도를 붙잡는 가장 느린 한 곳 | DB CPU, 커넥션 풀, GC |
| 커넥션 풀 (HikariCP) | 앱이 DB 연결을 미리 만들어 두고 빌려 쓰는 통. 다 빌려가면 대기(pending) | pending 21 = 21개 요청이 줄 섬 |
| 인덱스 | DB의 책 목차. 없으면 전체를 훑는다(Seq Scan) | |
| EXPLAIN ANALYZE | DB가 쿼리를 실제로 어떻게 실행했는지와 걸린 시간 | Seq Scan, 0.264ms |
| JVM | Java 프로그램을 실행하고 메모리를 대신 관리하는 프로그램 | Spring Boot가 이 위에서 돎 |
| GC | JVM이 안 쓰는 메모리(쓰레기)를 자동으로 치우는 것 | |
| Minor GC / Full GC | 새 물건만 빨리 치움 / 전체 대청소 | 3~8ms / 4,970ms |
| Stop-the-world | GC 동안 앱 전체가 멈추는 것 | 5초 동안 모든 요청 대기 |
| Serial GC / G1 GC | 청소부 1명이 전부 멈추고 청소 / 나눠서 조금씩 청소해 멈춤을 짧게 | 메모리가 작은 서버는 JVM이 Serial을 자동 선택 |
| RTT | 네트워크 왕복 시간 | 운영 서버→DB 31.5ms |
| 토큰 (JWT) | 로그인한 사용자임을 증명하는 출입증. 요청마다 붙인다 | k6는 OAuth 로그인을 못 해서 미리 받은 토큰 사용 |
| ABBA | 전(A)·후(B)·후(B)·전(A) 순서로 번갈아 재는 방법. 시간에 따른 변화(예열 등)를 상쇄 | |

## 2. 목표와 기준 정하기

**목표를 먼저 한 문장으로.** 예: “면접에서 말할 병목 해결 경험 + 서비스가 몇 명까지 버티는지”.

**“버틴다”의 기준을 숫자로.** 사람의 체감 기준(Nielsen): 0.1초 즉시, 1초 흐름 유지, 10초 이탈.
서버 응답에는 모바일 네트워크·화면 그리기가 더해지므로 서버 기준은 더 엄격하게.

| 단계 | p95 | 오류율 |
|---|---|---|
| 쾌적 | ≤ 0.2초 | < 1% |
| 양호 | ≤ 0.5초 | < 1% |
| 한계 | ≤ 1.0초 | < 1% |

**“명”의 정의도 정한다.** k6 VU는 쉬지 않고 요청하면 실제 사람보다 훨씬 무겁다.
“실제 앱 사용자처럼(화면 체류·폴링 간격)” 행동하게 만들어야 “동시 사용자 N명”이라고 말할 수 있다.

## 3. 환경 정하기 — 운영 vs 격리(복제)

| | 운영 서버 | 격리 복제 환경(로컬 Docker) |
|---|---|---|
| 장점 | 진짜 숫자 | 무너뜨려도 됨, 데이터 마음대로 |
| 위험 | 실제 사용자 장애, 무료 DB 한도 | 사양이 다르면 엉뚱한 병목 |
| 용도 | 약한 부하로 전/후 확인 | 한계 찾기, 원인 재현, 해결 비교 |

복제 환경을 운영과 비슷하게 만드는 법
- 앱 컨테이너에 운영과 같은 메모리·JVM 옵션.
- CPU 제한은 **운영에서 같은 약한 부하로 잰 지연과 비슷해지도록 보정**.
- DB까지의 네트워크 지연도 운영에서 재서 똑같이 넣는다(없으면 커넥션 풀 병목이 CPU 병목으로 보이는 등 원인이 바뀐다).
- 외부 유료/한도 API(AI 등)는 가짜 구현으로 대체.
- 부하를 거는 맥 자체가 먼저 한계인지(k6 CPU, 보내지 못한 요청 수) 항상 확인.

## 4. 관측 준비 — Prometheus + Grafana

- **Prometheus**: 서버의 지표를 주기적으로 긁어 와 저장. 운영 서버는 SSH 터널(`localhost:18080 → 운영 8080`)로 수집.
  시작 전 `up{job="..."} == 1` 확인. 0이면 터널부터 다시 연다.
- **Grafana**: Prometheus 데이터를 그래프로. 캡처할 때 시간대(KST/UTC)를 적는다.
- 꼭 볼 지표

| 지표 | Prometheus 이름(Spring Boot) | 알 수 있는 것 |
|---|---|---|
| 요청 수·평균 시간 | `http_server_requests_seconds_count/sum` | 처리량, 서버 내부 처리 시간 |
| 최대 응답 시간 | `http_server_requests_seconds_max` | 튀는 요청 |
| DB 연결 사용/대기 | `hikaricp_connections_active/pending` | DB가 밀리는지 |
| GC 멈춤 | `jvm_gc_pause_seconds_max` | Stop-the-world |
| 힙 사용 | `jvm_memory_used_bytes{area="heap"}` | 메모리 압박 |
| CPU | `process_cpu_usage`, `system_cpu_usage` | CPU 병목 |

- 기본 설정에선 서버 쪽 p95가 안 나온다(평균만). 필요하면 HTTP 지연 히스토그램을 켠다.
- 관리형 DB(Supabase 등)의 DB CPU는 앱 Prometheus에 없다 → DB 대시보드 캡처로 보완.

## 5. 안전장치가 들어간 측정 도구

운영에 거는 k6 스크립트에는 반드시
- **부하 크기를 코드에 고정**(명령어로 VU·시간을 못 바꾸게, setup에서 검사).
- **즉시 중단 조건**: 응답 1건 ≥ 2초, 오류율 ≥ 1%, p95 ≥ 1초, 401(토큰 문제)은 서버 오류와 구분.
- **서버 자원 감시**를 같이 돌려 여유 메모리·스왑·메모리 압박이 기준을 넘으면 중단.
- **요청 제한(rate limit) 아래로**: 예) 5 VU × 2초 대기 ≈ 150/분 < 운영 IP 제한 300/분.
- 토큰은 파일 경로로만 넘기고 출력·커밋하지 않는다. 측정 후 정리.
- 로컬 가짜 서버(fixture)로 위 조건을 테스트한 뒤 운영에 쓴다.

Trova: `monitoring/places-load.js`, `monitoring/run_observed_smoke.py --mode places-load`, 테스트 `monitoring/test_places_load.py`.

## 6. 사전 확인(측정 전에 반드시)

1. 관측 연결: Prometheus `up == 1`.
2. 대상 확인: 운영 DB가 맞는지(테스트 계정·행 수로 확인), 실행 중인 JAR 해시.
3. 데이터 규모: 테이블 행 수·크기. **작은 테이블에선 인덱스 효과가 안 보인다.**
4. 쿼리 실행 계획(EXPLAIN ANALYZE) 저장.
5. 네트워크 왕복: 앱 서버→DB, 내 PC→앱 서버(TCP 연결 시간으로 자격증명 없이 잴 수 있음).
6. 응답 시간 분해: 서버 내부 시간(Prometheus) vs 쿼리 시간(EXPLAIN) vs 네트워크. 가장 큰 덩어리가 진짜 병목 후보.

Trova 실측(운영, 2026-11-04): 장소 277행·184kB, 쿼리 0.264ms, 서버→DB 31.5ms, PC→서버 40.4ms.
→ 응답 시간의 대부분은 쿼리 밖에서 생김. 인덱스 효과는 운영 규모에선 거의 안 보일 것으로 예상.

## 7. 측정 → 변경 → 같은 조건 재측정

1. **전 측정**: 같은 시간대, 같은 계정, 같은 부하. k6 원본 + Prometheus 원본(JSON) + 캡처 저장.
2. **변경 하나만**: 한 번에 하나만 바꿔야 원인을 말할 수 있다.
   - DB 인덱스는 운영에서 `CREATE INDEX CONCURRENTLY`(테이블을 잠그지 않음, 트랜잭션 밖에서) → `indisvalid` 확인 → 앱 배포.
3. **후 측정**: 배포 후 예열 시간을 두고 전과 같은 조건.
4. **비교**: p95·평균·RPS·DB 대기·CPU·GC. 실사용 요청이 섞였으면 그 수도 적는다.
5. 격리 환경에서는 **ABBA**로 반복해 우연을 줄이고, 응답 내용이 같은지(해시)도 확인.

## 8. 무너졌을 때 — 원인 찾기 순서

1. **멈춘다.** 도구가 자동 중단하게 만들어 두면 운영 피해가 작다.
2. **시간을 맞춘다.** 이상한 요청이 난 시각(k6 원본)과 같은 시각의 Prometheus 지표를 나란히 본다.
3. **용의자 체크리스트**

| 증상 | 의심 | 확인할 지표/도구 |
|---|---|---|
| 특정 순간 모든 요청이 동시에 수 초 멈춤 | GC Stop-the-world | `jvm_gc_pause_seconds_max`, GC 로그 |
| VU를 늘릴수록 지연이 선형으로 증가, DB CPU 100% | 쿼리/인덱스 | DB CPU, EXPLAIN |
| `Connection is not available` 오류, pending 증가 | 커넥션 풀 고갈 | `hikaricp_connections_pending` |
| 요청이 큐에 쌓이다 타임아웃 | 톰캣 스레드 고갈 | `tomcat_threads_busy_threads` |
| 프로세스가 갑자기 죽음 | 메모리 부족(OOM) | 컨테이너 OOMKilled, 힙, 스왑 |
| `too many open files` | 파일·소켓 한도 | `ulimit -n` |
| k6 쪽 `dial timeout`, dropped iterations | 부하 발생기 한계 | k6 CPU, 맥 상태 |

4. **기록한다**(문제 기록 파일): 현상(원문), 확인한 것, 원인 추정과 근거, 해결안 2~4개(권장 표시), 선택, 결과.
5. **해결안을 비교 실험**한 뒤 고른다. 언어·구조 교체 같은 큰 변경보다 설정·쿼리 같은 작은 변경을 먼저.

### 실제 사례: 운영에서 처음 본 5초 멈춤 (2026-11-04)
- 현상: 5 VU 장소 목록 359건 중 1건이 3초 시간 초과, 나머지는 p95 425ms.
- 같은 시각 Prometheus: `jvm_gc_pause_seconds_max{action="end of major GC", gc="MarkSweepCompact"}` = 4.973초,
  DB 연결 active 5(평소 0~1). 평소 CPU 2.5%로 여유.
- 원인 추정: GC 종류를 지정하지 않아 메모리가 작은 서버에서 Serial GC가 자동 선택 → Full GC 동안 전체 정지,
  1/8 OCPU 한도로 청소가 느림(추정).
- 다음: GC 로그로 빈도 확인 → 복제 환경에서 Serial vs G1 비교 → 운영 반영 여부 선택. (결과는 진행 후 추가)
- 판단: “Rust로 바꾸면 GC가 없다”는 맞지만 전체 재작성 비용이 너무 크고, JVM 설정으로 해결 가능성이 높아 설정 먼저.

## 9. 보고서에 넣을 것

- 조건: 환경(로컬/운영), 사양, 데이터 규모, VU·think time·시간, 측정 시각(KST/UTC).
- 전/후 표: p95·평균·RPS·오류·DB 대기·CPU·GC.
- 캡처: Grafana/Prometheus 그래프(값이 보이게, 캡처가 의도한 화면인지 열어서 확인 — 다른 화면으로 덮어써진 적 있음).
- 해석: 왜 이런 숫자가 나왔는지, 운영과 격리 결과를 섞지 않기.
- 한계: 측정하지 않은 것(장시간 안정성, 최대 인원 등).
- 원본: k6 JSON, Prometheus JSON, EXPLAIN, 재현 스크립트를 커밋.

### 면접용 문장 틀
“운영 지표에서 ○○를 보고, 같은 사양의 격리 환경에서 재현해 원인이 △△임을 확인했습니다.
□□로 고친 뒤 같은 조건에서 반복 측정해 p95가 A → B가 됐고, 운영 반영 후 운영 지표로도 확인했습니다.”

## 10. 실제로 겪은 함정

- **도구 권한 문제**: Orca 터미널에서 다운로드 폴더 접근이 막혀 git이 안 됨 → 오래 떠 있던 터미널 호스트가 권한 변경을 반영 못 함. 호스트 재시작으로 해결.
- **토큰 발급은 자동화 도구가 막는다**: 운영 자격증명을 다루는 일은 사람이 직접 하고, 도구에는 파일 경로만 넘긴다.
- **읽기 전용 옵션이 연결 풀러에서 무시됨**: Supabase 풀러는 접속 옵션(`default_transaction_read_only`)을 무시 → 쿼리를 `BEGIN READ ONLY; … ROLLBACK;`으로 감싼다.
- **캡처 파일이 엉뚱한 화면으로 덮어써짐**: 남아 있던 headless Chrome이 로그인 화면을 저장. 캡처 후 반드시 열어 확인.
- **작은 운영 데이터**: 격리에서 98% 줄인 인덱스도 운영(277행)에서는 효과가 안 보인다. 그대로 기록하고 “데이터가 늘면 커진다”를 격리 근거로 설명.
