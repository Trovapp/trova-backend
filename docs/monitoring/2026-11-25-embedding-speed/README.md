# 대안 임베딩 호출 수 검증과 독립 작업 중첩

2026-11-25 · 이슈 #543 · 기준 `origin/main` `0b35d6c` · 운영 변경·배포 없음.

**대안 요청은 이미 묶음 1회였다. 이번 변경은 혼잡도 조회가 있는 요청에서만 그 대기를 임베딩 HTTP와 겹친다. 기존 새 장소 30건처럼 혼잡도가 0ms인 조건의 1.4초 임베딩 자체를 단축한 결과는 아니다.** 순위·개인화·추천 이유를 바꾸는 응답 지연 생성/B1·B2·B3, 텍스트 축약은 사용하지 않았다.

## 59묶음 / 30대안의 원인

- `AlternativeFinderService`는 검색·보충의 Google ID 중복을 제거한 뒤 `ensureEmbeddings`를 한 번 호출했다. Google 검색의 `MAX_RESULT_COUNT=20`, 보충 최대 1회이므로 최대 40후보이며 `PlaceEmbeddingService.MAX_BATCH_SIZE=100` 안에 든다. 누락 벡터가 있으면 1회, 없으면 0회다. `PlaceCatalogService.upsertAll`에는 Gemini 호출이 없다. 저장 전·후로 임베딩을 두 번 하지 않는다.
- [원본 journal](../2026-11-25-v11-recheck-followup/server-alternatives/journal.log)의 30개 대안 단계행 각각에 **같은 스레드의 가장 가까운 이전 묶음 1개**가 0.539초 이내에 대응한다. 나머지 **29묶음은 모두 1곳**이다. [재분석 JSON](journal-analysis.json)에 대응 행 번호·시간차가 있다.
- 준비 과정에서 장소를 여행에 추가하는 `TripService.addPlaceToDay`도 긍정 선호 신호 저장 뒤 `ensureEmbeddings(List.of(place))`를 호출한다. 이런 단일 장소 묶음을 포함한 창 전체의 59줄을 30대안 요청으로 나누어 대안당 약 2회라고 볼 수 없다. 요청 ID가 없는 로그이므로 29묶음의 개별 HTTP 경로까지 단정하지 않는다.
- 이와 같은 모집단 주의는 [앞선 임베딩 지연 평가](../2026-11-25-embedding-defer-eval/README.md)의 데이터 출처 절에도 명시돼 있다. 합칠 중복 호출을 발견하지 못했으며, 호출 합치기로 1.2초를 절약했다는 주장은 하지 않는다.

## 변경과 결과 보존

1. 기존과 같은 좌표·거리·이동시간 계산으로 응답 대상 `LocatedCandidate`를 먼저 만든다. **임베딩과 개인화 입력 후보 목록은 그대로 유지한다.** 거리로 탈락하는 후보도 `user_preference_signals.place_id`에 연결돼 있을 수 있어, 벡터 생성이 다른 후보의 top-5 선호 신호를 바꿀 수 있기 때문이다. 좌표 없는 후보도 기존과 같이 임베딩한다.
2. 임베딩 존재 조회와 입력 텍스트 구성은 요청 스레드에서 끝낸다. 불변 문자열 목록을 전달한 가상 스레드는 Gemini HTTP만 실행한다. 요청 스레드는 응답에 남는 장소의 혼잡도를 원래 후보 순서로 조회한다. Gemini 묶음끼리는 순차 처리하며 요청당 동시에 1개만 실행한다.
3. HTTP 완료를 기다린 뒤 API 호출 기록과 벡터 저장을 요청 스레드에서 처리하고, **저장 후에 개인화 SQL을 그대로 실행**한다. 카탈로그는 후보 ID·기존 mood/reviewSummary를 결정하고, 실내 태깅도 입력을 바꿀 수 있어 그 전에 임베딩을 만들지 않는다. 개인화 조회도 후보·선호 신호의 새 벡터에 의존하므로 병렬화하지 않는다.
4. DB 작업·엔티티 접근은 추가 스레드로 보내지 않는다. 대안 서비스는 자체 트랜잭션이 없고 카탈로그의 `@Transactional` 호출은 이미 끝난 상태다. 커넥션 풀의 추가 연결을 점유하지 않는다. 새 `synchronized` 블록 안에서 HTTP/대기/DB를 실행하지 않으며 executor 종료까지 기다려 응답 후 작업을 남기지 않는다.
5. 혼잡도 대상이 없거나 기존 `ensureEmbeddings` 호출자는 요청 스레드의 기존 동기 경로를 유지한다. `filterIndoor`·태그 저장·`conversation/*` 서비스 코드는 변경하지 않았다. 새 메서드를 모킹하는 두 컨트롤러 테스트는 반환값과 독립 작업 실행을 보완했다.
6. 단계 로그는 `임베딩=…ms(묶음 1회·N곳)`처럼 HTTP 시도 수·입력 장소 수를 추가한다. 임베딩 벽시계에는 동시에 수행한 혼잡도 작업이 포함되므로 **두 시간을 더하면 안 된다.** `recordBatch`의 기존 문장별 계수는 그대로이며 실제 HTTP 횟수와 구분한다. 429 재시도나 동시 Gemini 호출 수 증가는 없다.

## 같은 조건의 전후 측정

[reproduce.py](reproduce.py)는 기준 커밋의 두 서비스 원문을 `git show`로 읽어 이름만 바꾼 테스트 클래스로 컴파일한다. 변경 전·후 모두 실제 임베딩 서비스, 개인화 서비스의 평균 계산, 대안 정렬·추천 이유 코드를 실행하고 I/O만 가짜로 제공한다. 벤치마크 경계는 `findAlternatives` 진입~반환이다. HTTP 컨트롤러/실제 네트워크 측정은 아니다.

고정 입력: 카페 4후보(기존 벡터 1곳·신규 3곳), 거리 탈락 선호 신호 1곳·좌표 없음 1곳 포함. 같은 필터·사용자·가짜 벡터·신호 행을 사용한다. 가짜 Gemini 묶음 1회 1,200ms, 개인화 SQL 300ms, 혼잡도 대상이 있으면 조회 300ms다. 검색·카탈로그 저장 등 나머지 I/O는 지연 없는 mock이며, 각 조건을 3번 반복한다.

## 검증과 변형 검사

- `EmbeddingSpeedTest`: 원본 main과 변경 후의 전체 후보 응답 레코드(순서·이유·혼잡도 포함), 개인화 점수 맵, 저장 벡터 맵, 요청 텍스트 목록을 `assertEquals`로 비교한다. 시간 측정 6쌍과 기본/이유 복구 모드 2쌍을 검증했다. 일반 테스트에서는 고정 기대 순위·점수·이유·묶음 1회를 검증한다. mood·리뷰 요약도 그대로 전달됨을 확인한다.
- 래치 테스트로 Gemini가 대기하는 동안 독립 작업이 실행됨을 확인하고, HTTP가 가상 스레드에 있는 동안 DB 작업은 요청 스레드에 남는지 확인한다.
- `PlaceEmbeddingServiceTest`: 기존 성공·실패·100개 분할 경계에 더해 빈 후보/기존 벡터만 존재/존재 조회 실패에도 독립 작업을 정확히 한 번 실행하는지, 기존 호출의 동기 실행을 확인한다. 기존 대안 서비스 테스트와 두 컨트롤러의 실제 대안 경로 테스트도 유지한다.
- **변형 2개 검출:** `MAX_BATCH_SIZE=1`로 쪼개면 묶음 1회 불변식이 깨져 실패한다. 독립 작업을 HTTP 완료 뒤로 돌리면 래치 테스트가 실패한다. 실제로 원문을 바꿔 각각 실패를 확인하고 finally에서 복구한 뒤 관련 테스트를 다시 통과시켰다. 이미 묶음 1회였으므로 ‘새 합치기를 되돌린 검사’라고 부르지는 않는다. [변형 결과](mutations.json) · [분할 로그](묶음_분할.log) · [순차 복원 로그](순차_복원.log) · [복구 로그](restored.log).
