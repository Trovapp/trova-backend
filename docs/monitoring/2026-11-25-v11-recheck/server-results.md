# 서버 집계·단계 분해

입력은 Mac이 제공한 16개 .prom.gz와 journal이다. 모든 시간 단위는 초, SQL은 계측된 문장 수다. 집계 스크립트는 네트워크 요청을 하지 않는다. 재현 순서는 summarize_v11_prom.py → report_v11_results.py → plot_v11_recheck.py → pdf_v11_recheck.py다.

## 집계 범위와 검증

모든 창의 process_start_time_seconds가 같고 선택한 누적 count·sum·bucket·total의 감소가 없다. 시작 스냅샷에 없는 시리즈는 같은 프로세스의 신규 등록으로 가정해 0에서 차감했으며 목록을 server-deltas.json에 남겼다. 11-20 원자료 재계산으로 대안 12건·평균 2.049378383초·버킷 p95 4.080218930초·SQL 26.666667을 재현했다.

HTTP는 method/uri/status로 분리한다. SQL에는 status 라벨이 없어 성공·실패가 섞인 URI는 성공 요청당 SQL로 해석하지 않는다. HTTP 완료 시점 기준이므로 SSE 수명과 창 밖에 시작한 요청이 포함될 수 있다. 비동기 분석 SQL·명시 훅 없는 JDBC는 빠진다. 외부 타이머는 호출 계측 횟수이며 실제 네트워크 재시도 횟수와 같다고 보장하지 않는다. place-embedding-batch는 문장별로 같은 배치 시간을 기록하므로 합산 시간을 실대기로 쓰지 않는다.

상세 자체는 평균 123ms·SQL 2지만 진입 때 추천·목록·멤버 등 다른 요청이 동반된다. 반복 진입 중 SSE 429 24건이 관찰됐다. 메모 평균 343ms, 순서 784ms이며 SQL은 4와 6.13으로 다르다. 수정 창 자동 추천은 성공 28건·429 2건, Places 검색 43회로 쓰기 외 비용이 더해졌다. 메모가 추천 입력을 바꾸지 않아도 재요청한다면 무효화 범위를 줄일 여지가 있다.

## 오류·연결 해석

401 2건은 HTTP uri=UNKNOWN으로 기록되고 404 2건은 /api/public/trips/{token}으로 기록된다. 네 traceId가 journal의 상태와 일치한다. 경로 템플릿의 {token}은 실제 공유 비밀값이 아니다. 전체 제공 창에서 HTTP 5xx 증분은 0이다. journal의 웹 푸시 외부 400은 별도 외부 응답으로 HTTP 5xx와 혼동하지 않는다.

SSE 429 총 51건과 추천 429 19건은 정상 UI 사용 중 발생했다. TripStreams의 사용자별 동시 연결 기본 3개 제한과 DailyQuotaService의 일일 장소 호출 기본 100회 제한은 조사할 코드 경로이나 이 로그만으로 원인을 확정할 수 없다. 연결 해제 지연·재연결 중복·추천 재조회 조건을 같은 요청 흐름에서 후속 검증해야 한다. 상한을 무조건 늘리는 해결은 제안하지 않는다.

모든 경계의 Kafka lag·deferred size는 0, deferred discard 차분도 0이다. fallback 카운터와 SSE 활성 gauge가 없으므로 미측정으로 남긴다. SSE 200 완료 요청은 상세 창 26건 평균 119.034초, 빈 시간 창 24건 평균 51.428초이며 두 창의 p95 rank가 +Inf 버킷 안에 있어 30초 초과만 알 수 있다. Prometheus histogram_quantile은 이 경우 마지막 유한 경계를 반환하므로 Grafana 30초 선은 정확한 p95나 연결 종료 시간이 아니다. 매니저 원자료 README의 “30초 연결 종료” 해석은 이 차분 근거로 정정한다.
