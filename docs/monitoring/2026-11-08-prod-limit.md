# 운영 서버 동시 사용자 한계 실측 (#342, 2026-11-08, 운영 서버)

사용자 요청(2026-11-08): "1~2일 관찰하지 말고 운영서버에 실제 부하를 줘서 봐줘. 지금 사람들이 설치만 하고 사용은 안 해."
복제 환경(로컬 Docker, `2026-11-07-replica-limit.md`)의 숫자가 운영과 같은지 확인하려고 운영 서버에 직접 부하를 줬다.

- 대상: 운영 서버(Oracle E2.1.Micro, 2 vCPU 표시·기본 1/8 OCPU 버스트형, 메모리 956MB), `https://193-123-161-217.sslip.io`(Caddy → java).
  java 설정은 그대로(G1, `-Xmx384m`, `MemorySwapMax=0`, Tomcat 스레드 기본 200). 운영 DB는 Supabase.
- 부하: 맥(가정 인터넷)에서 k6, 복제 환경과 같은 `monitoring/limit/load.js`(조회 화면 9종, 요청 사이 1초). 영상 분석·Gemini 호출 없음.
- 데이터: 운영 DB에 `provider='loadtest'` 계정 50명(저장 장소 2000, 찜 500(기존 장소 목록 사용), 여행 100(30일 뒤), 알림 150)을 넣고
  끝난 뒤 지웠다(`monitoring/limit/prod_data.py seed|cleanup`, 남은 계정 0 확인). 토큰은 서버 안에서 만들고 비밀 값은 서버 밖으로 나가지 않았다.
- 측정 중에만 IP 요청 제한을 껐다(systemd drop-in `loadtest.conf`, 끝난 뒤 삭제·재시작).
- 운영 DB 쓰기와 서버 재시작은 자동 권한 검사가 막아, 사용자가 직접 실행했다.
- 원본: `2026-11-08-prod-limit/`(단계별 `runs.json`, 구간 GC 로그). 도구: `monitoring/limit/prod_run.py`.

p95 571ms, p99 1,088ms, 오류 0%, 초당 40.7요청, 메모리 최고 563MiB, GC 175회·최대 0.27초, steal 0.33코어.
15분 동안 버스트가 끊겨 느려지는 현상은 이 부하에서는 보이지 않았다.

## 복제 환경과 다른 점

| | 복제 환경(CPU 0.125 고정, 650MiB) | 운영 |
|---|---|---|
| 40명(예열 뒤) p95 | 0.9초 | 0.9초 |
| 60명 | OOM 강제 종료 | p95 0.85초, 오류 0% |
| 100명 | (스레드 30·힙 256MiB로만 생존, p95 10초) | p95 1.1초, 오류 0% |
| 쓴 CPU | 최대 0.125코어 | 0.35~0.57코어 |
| 기동 | 277초 | UP 109초 |

- 운영 java는 CPU를 0.125코어보다 3~4배 더 썼다. 복제 환경은 CPU를 너무 적게 줘서 요청이 쌓였고, 쌓인 요청만큼 스레드·메모리가 늘어 죽었다.
  운영은 처리가 빨라 쌓이지 않아 메모리가 509~551MiB에 머물렀다.
- 그래서 복제 환경의 문제 기록 #13·#14·#15(몰리면 OOM, 새 설정이 느림)는 운영 조건에서는 재현되지 않았다. 운영 설정은 바꾸지 않았다.

## 결론

- 운영 서버 지금 설정으로: 동시 60명까지 p95 0.9초 이하, 80~100명 1.1~1.2초, 150~200명 3~5초(실패 거의 없음), 300명에서 33% 시간 초과. 어느 단계에서도 java는 죽지 않았다.
- 여기서 1명은 1초에 한 번꼴로 계속 누르는 사람이다. 실제 사용자(몇 초~수십 초에 한 번)로는 훨씬 많은 인원에 해당한다(추정).
- 한계는 메모리보다 CPU(무료 서버 몫, steal)다. 남은 메모리는 최소 76MiB였다.
- 확인 못 한 것: 몇 시간 이상 지속 부하에서의 버스트 소진, 영상 분석(파이썬·Gemini)이 같이 돌 때의 메모리.
