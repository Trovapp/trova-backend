# 조회 요청당 DB 왕복 수 분해 (2026-11-05, 로컬 격리)

질문: 운영 장소 목록 응답(약 270ms) 중 앱 내부 처리 약 165ms가 어디서 생기나. 쿼리 자체는 0.3ms, 운영 서버→DB 왕복은 31.5ms다
(`2026-11-04-prod-index.md`). 요청 하나가 DB에 몇 번 다녀오는지 셌다.

## 방법 (로컬 Docker, 운영 DB·설정 미사용)
1. **문장 수** — `monitoring/roundtrips/count.py`: 격리 앱+Postgres(`monitoring/capacity/compose.yml`)에서 `log_statement=all`로
   JDBC 연결이 보낸 문장을 엔드포인트별로 모음(예열 1회 뒤 3회 평균). 결과 `2026-11-05-db-roundtrips/roundtrips.json`, 원본 `db-statements.log`.
2. **실제 왕복 수** — `monitoring/roundtrips/latency.py`: 앱과 DB 사이에 toxiproxy를 두고 DB 응답에 30ms 지연을 넣었다 뺐다(없음→있음→있음→없음),
   엔드포인트별 30회씩 중앙값을 비교. (지연 있을 때 − 없을 때) ÷ 30ms ≈ 요청당 왕복 수. 결과 `latency.json`.
   드라이버가 여러 문장을 한 번에 묶어 보내면 문장 수보다 왕복 수가 적다. 이걸 구분하려고 지연 기울기로 쟀다.

## 결과

|---|---|---|---|---|
| `/api/places` | 4 | 3.1ms | 109.3ms | 3.54 |
| `/api/places/pending` | 4 | 2.7 | 108.7 | 3.53 |
| `/api/trips` | 6 | 2.2 | 139.8 | 4.59 |
| `/api/bookmarks` | 4 | 2.0 | 107.8 | 3.53 |
| `/api/bookmarks/folders` | 4 | 1.8 | 106.1 | 3.48 |
| `/api/notifications` | 4 | 1.8 | 106.5 | 3.49 |
| `/api/trip-drafts/auto` | 4 | 2.5 | 108.3 | 3.53 |
| `/api/auth/me` | 3 | 1.4 | 72.7 | 2.37 |
| `/api/users/me` | 3 | 1.6 | 71.7 | 2.34 |

`/api/places` 한 요청의 문장(로그 원문 순서):
1. `BEGIN READ ONLY`
2. `select … from users where id=?` ← `CurrentUserService.resolve()` → `userRepository.findById()` (Spring Data 기본 읽기 전용 트랜잭션)
3. `COMMIT`
4. `select … from saved_places … join processing_jobs …` ← 본 조회(트랜잭션 밖, 자동 커밋)

해석
- **모든 로그인 요청이 본 조회 앞에 “사용자 확인” 트랜잭션을 따로 연다.** `BEGIN`은 첫 조회와 한 번에 묶여 나가서 왕복은
  (BEGIN+사용자 조회) 1 + `COMMIT` 1 = **2번**, 본 조회 1번 → 약 3번. 사용자 확인만 하는 `/api/auth/me`가 약 2번인 것과 맞는다.
- 측정값이 정수보다 0.3~0.5 큰 것은 toxiproxy가 응답을 여러 조각으로 받을 때 조각마다 지연이 붙는 영향으로 추정(미확정).
- 운영으로 옮겨 보면(추정, 운영 실측 아님): 왕복 3~3.5번 × 31.5ms ≈ **95~110ms** → 앱 내부 약 165ms의 약 60~65%가 DB 왕복 대기.
  나머지 약 55~70ms는 1/8 OCPU에서의 JSON 변환·보안 필터 등 CPU 처리로 본다(미분해).
- 그중 **사용자 확인 트랜잭션이 왕복 2번(약 63ms)**을 차지한다. 가장 큰 단일 개선 후보다.

## 개선 선택지 (사용자 선택: B)
| 안 | 내용 | 줄어드는 왕복(추정) | 바뀌는 동작·비용 |
|---|---|---|---|
| A | 사용자 확인 조회를 트랜잭션 없이(자동 커밋) 실행 | 1번(`COMMIT`) ≈ 31ms | 동작 그대로. 리포지토리 메서드에 트랜잭션 전파 설정 추가 |
| B | 사용자 존재 여부를 앱 메모리에 캐시(정지 사용자 목록처럼). 탈퇴·삭제 시 캐시 무효화 | 2번 ≈ 63ms | 단일 JVM 전제(ADR 0025·0027과 같은 범위). 탈퇴 직후 반영 로직 필요 |
| C | 본 조회가 `user_id`만 필요하면 사용자 엔티티를 읽지 않고 토큰의 ID로 바로 조회 | 2번 ≈ 63ms | 탈퇴한 사용자의 토큰이 401 대신 빈 목록을 받게 됨(현재 주석의 의도와 충돌) |

다음: 선택한 안을 구현 → 같은 지연 기울기 측정으로 왕복 수 감소 확인 → 운영 반영 후 운영 지표(장소 목록 서버 평균)로 확인.

## 개선 후 (사용자 선택 2번: 사용자 존재 확인을 메모리에 기억, ADR 0036, 로컬 격리)

|---|---|---|---|

| `/api/places/pending` | 4 → 1 | 3.53 → 1.25 | 108.7 → 39.53ms |
| `/api/trips` | 6 → 1 | 4.59 → 1.25 | 139.78 → 39.06ms |
| `/api/bookmarks` | 4 → 1 | 3.53 → 1.26 | 107.84 → 39.09ms |

| `/api/notifications` | 4 → 1 | 3.49 → 1.29 | 106.52 → 40.08ms |

| `/api/trip-drafts/auto` | 4 → 1 | 3.53 → 1.27 | 108.34 → 40.34ms |

- 자주 불리는 조회 7개는 **왕복 약 3.5 → 약 1.25번**(사용자 확인 2번 제거). `/api/auth/me`·`/api/users/me`는 사용자 정보가 필요해 그대로(대조군).
- 여행 목록은 6 → 1문장: 사용자 확인 트랜잭션에 더해, 사용자 ID 버전 서비스 메서드에 읽기 전용 트랜잭션을 걸지 않아 `BEGIN/COMMIT`도 빠졌다
  (스칼라·튜플만 읽어 지연 로딩이 없음을 확인하고 유지, 코드 주석에 이유 기록). 측정 데이터에 여행이 없어 지역 조회는 실행되지 않았다.
- 30ms 지연을 넣은 조건에서 응답 중앙값이 약 107ms → 약 39ms. **운영으로 옮기면(추정) 장소 목록 등 조회마다 약 63ms 감소**
  (2번 × 31.5ms). 운영 반영 후 운영 지표로 확인 예정.
- 측정값이 1보다 0.25~0.3 큰 것은 개선 전과 같은 toxiproxy 조각 지연 영향으로 추정.
- 전체 `./gradlew build` 1,052개 테스트 실패 0(새 테스트 5개: 단위 4, 통합 1 — 7개 API 호출 뒤 탈퇴하면 401).

원본: `2026-11-05-db-roundtrips/after-count/`, `after-latency/`.

### 이 방법이 최선인가 (검토)

경합 해결 방법 비교
| 방법 | 장점 | 단점 |
|---|---|---|
| **탈퇴 표시 + 잠금 (선택)** | 추가 DB 왕복 0, 단일 JVM에서 순서와 상관없이 막힘 | 표시가 줄지 않음(탈퇴 수만큼, 무시할 크기). 잠금은 첫 기억·탈퇴 때만 경쟁 |
| 기억한 뒤 한 번 더 존재 확인 | 표시 없이 단순 | 사용자마다 처음 한 번 왕복 +1(약 31ms) |
| 세대 번호(탈퇴마다 증가, 확인 전후 비교) | 표시 없음 | 코드가 가장 복잡, 이 규모에 과함 |

전체 방향에 대한 판단
- **이번 범위(사용자 확인 왕복 제거)에서는 이 방법이 맞다고 본다.** 운영 응답 분해에서 가장 큰 단일 덩어리(약 63ms)였고, 동작(탈퇴 401)을 유지하며 코드 변경이 작다.
- **최선은 아니다 — 남은 것**
  1. 데이터가 있으면 `user` EAGER 로딩 때문에 SELECT가 더 남는다. 다음 후보: 조회 API를 DTO 프로젝션으로 바꾸거나 연관을 LAZY로(영향 범위 큼, 별도 측정 필요).
  2. 단일 JVM 전제. 서버를 늘리면 탈퇴 표시를 공유(DB·Redis 등)해야 한다. 지금 구조(서버 1대)에선 불필요.
  3. 운영 효과는 아직 추정. 배포(11-06 G1 확인 뒤) 후 운영 지표(장소 목록 서버 평균)로 확인해야 "최선"을 말할 수 있다.
