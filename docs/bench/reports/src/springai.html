Spring AI 2 도입: 전후 비교와 성능

Trova 백엔드 · 2026-11-11 작성 · 운영 반영 2026-10-31(PR #245, #254) · 결정 기록 ADR 0020
한 줄 결론. Java에서 Gemini를 부르는 텍스트·JSON 클라이언트를 직접 만든 REST에서 Spring AI 2 ChatModel로 옮겼다. 속도는 그대로다(차이가 측정 흔들림 안). 얻은 것은 재시도를 한 곳으로 모은 것과 호출 시간·토큰 지표 자동 수집이다. 기본 재시도를 그대로 뒀다면 한 요청이 Gemini를 최대 15번 불러 무료 한도를 몇 배로 썼을 것이다. 운영에서 HTTP/2 시간 초과(6/6)가 나서 HTTP/1.1로 고정해 해결했다.

2. 왜 도입했나

  • 문제: Gemini 클라이언트 4개가 요청·응답 레코드, 시간 제한, 재시도를 각자 만들었다(567줄). 모델이나 옵션을 바꾸려면 네 곳을 고쳐야 했다.
  • 비용: Spring AI는 Apache 2.0 라이브러리라 무료다. 비용은 지금처럼 Gemini 호출 수로만 생긴다(ADR 0002).
  • 다음 단계 준비: 대화 도구 호출(@Tool)·구조화 출력·임베딩을 직접 만들지 않고 쓸 수 있다.
  • 검토한 다른 방법: REST 유지(의존성은 안 늘지만 도구 호출·지표를 계속 직접 만들어야 함), LangChain4j(레포가 Spring Boot 중심이고 Boot 4 공식 지원·관측 연동은 Spring AI가 더 직접적), 자동 설정 그대로 사용(키 없는 테스트·로컬에서 서버가 안 뜨고 재시도가 두 겹으로 남음).

6. 결정과 한계, 남은 일

Gemini 텍스트·JSON 호출은 Spring AI 2로 유지하고, 재시도는 우리 코드 한 곳에서만 한다(ADR 0020).

  • 한계: 속도 이득은 입증하지 못했다. 이득은 코드·설정·지표 쪽이다.
  • 한계: JAR가 약 25MB, 메모리가 약 16MB 늘었다. 956MB 서버에서 감당할 수 있는 크기로 봤다.
  • 한계: 응답 비교는 로컬 짧은 요청 각 20회다. 운영 호출 실패율은 아직 표본이 적어 제시하지 않는다.
  • 남은 일: 운영 호출이 쌓이면 gen_ai_client_operation_seconds로 중앙값·실패율 기록.
  • 남은 일: 다음 단계(대화 도구 호출 → @Tool, 임베딩·pgvector)는 1단계를 운영에서 본 뒤 정한다.
