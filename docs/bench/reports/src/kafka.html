Kafka 작업 대기열 도입: 전후 비교와 성능

Trova 백엔드 · 2026-11-12 갱신 · 운영 반영 2026-10-30(PR #246), 자동 초안 2026-11-11(PR #391), 실패 작업 토픽·직접 초안·재구성·다시 보내기 2026-11-12(PR #395, #397, #401) · 결정 기록 ADR 0021
한 줄 결론. 영상 분석 시작을 서버 안 대기열(@Async)에서 Aiven 무료 Kafka로 옮기고, 브로커가 안 되면 서버 안 대기열로 자동으로 넘기게 했다. 얻은 것은 속도가 아니라 재시작에 강한 처리다. 같은 구조를 일정 초안·재구성까지 넓혔고, 처리하지 못한 작업은 실패 작업 토픽과 경보로 드러나게 했다. DB 저장과 Kafka 전송 사이에서 작업이 사라지는 틈은 아웃박스 테이블 대신 멈춘 작업 다시 보내기로 막았다. 운영 강제 종료 실험 3번에서 모두 작업이 끝까지 처리됐다(초안 2분 29초, 재구성 2분 23초, Kafka 장애 중 종료 8분 53초). 대가는 운영에서 분석 시작까지 약 0.2초가 더 걸리는 것이다.

이력서용 한 줄: Kafka 대기열 이전과, 재시작해도 작업을 끝까지 처리하는 구조, DB 저장과 전송 사이의 작업 유실 방지를 운영 강제 종료 실험 3번으로 검증했다(추가 비용 0원).
  • 영상 분석·일정 초안·일정 재구성 작업을 교체 가능한 대기열로 모으고 운영을 Aiven 무료 Kafka로 옮겼다. 브로커 장애 때는 5초 안에 서버 안 대기열로 자동 전환된다.
  • 처리가 끝난 뒤 처리 완료를 기록하고, 작업별 잠금과 상태 확인으로 같은 작업은 한 번만 실행되게 했다. 운영에서 처리 중 SIGKILL을 해도 초안은 2분 29초, 재구성은 2분 23초 만에 완료됐고 외부 API 중복 호출은 없었다.
  • DB 저장과 Kafka 전송 사이의 유실은 방법 5가지를 비교한 뒤, 새 테이블 없이 작업 상태를 아웃박스로 쓰는 "멈춘 작업 다시 보내기"로 막았다. Kafka를 끊고 강제 종료하는 운영 실험에서, 예전이면 15분 뒤 실패하던 작업이 8분 53초 만에 완료됐다.
  • 처리에 실패한 작업은 다시 돌리지 않고 실패 작업 토픽 하나에 모은다(Gemini 반복 호출 방지). 처리 대기 지연과 실패 작업 경보를 Grafana에 만들었다.

2. 왜 도입했나

  • 문제: 서버 안 대기열은 메모리에만 있다. 배포·재시작 때 기다리던 영상 분석이 사라지고, 15분 뒤에야 실패로 정리됐다(#43).
  • 비용 0원 원칙(ADR 0002): 유료 관리형 대기열은 쓰지 않는다.
  • 브로커를 운영 서버에 두지 않은 이유: 로컬에서 힙을 256MB로 줄여도 Kafka 컨테이너가 297~327MB를 썼다. 운영 서버는 956MB인데 앱이 이미 약 400MB를 쓴다.
  • Aiven 무료 플랜: 토픽 5개, 토픽당 파티션 2개, 125KiB/s. 이 서비스 규모에 충분하다. 로컬 Docker로 "교체 가능한 구조"만 보이는 대신, 운영에서 실제로 돌려 본 경험을 남기려고 운영에 연결했다.
  • 검토한 다른 방법: DB 테이블 대기열(FOR UPDATE SKIP LOCKED)은 추가 인프라 없이 재시작에 강하지만 Kafka 구조를 보이는 쪽을 골랐다. 브로커를 같은 서버에 띄우려면 서버를 키워야 해서(유료) 기각했다.

3. 전후 구조

분석 시작을 ShareJobQueue.enqueue(jobId) 하나로 모으고, 설정 APP_QUEUE_TYPE 하나로 구현을 고른다.

단계전: 서버 안 대기열(async)후: Kafka(운영)
접수공유 API가 스레드 풀에 바로 넣음토픽 trova.share-jobs(파티션 2, 값 = 작업 id)로 보냄
처리서버 안 pipelineTaskExecutor리스너가 동시 2건, 한 번에 1건씩
끝낼 때기록 없음분석이 끝난 뒤 오프셋 커밋
서버 재시작대기 작업 사라짐커밋 안 된 작업을 다시 받음
중복 방지해당 없음끝났거나 지워진 작업은 건너뜀. 기본 재처리 9회는 끔(Gemini를 다시 부르지 않게)
브로커 장애해당 없음5초 기다린 뒤 서버 안 대기열로 넘김. 1분 동안 Kafka 건너뜀

6. 확장: 자동 일정 초안도 Kafka로 (2026-11-11, #390)

영상 분석이 끝난 뒤 자동으로 일정 초안을 만드는 단계가 아직 서버 안 대기열이라, 재시작하면 초안이 사라지고 15분 뒤 실패로 정리됐다. 같은 대기열 구조로 옮겨 공유 → 분석 → 초안이 끝까지 Kafka를 거친다.

항목내용
토픽·그룹trova.draft-jobs(파티션 2, 무료 토픽 5개 중 2개째), 그룹 trova-draft-jobs, 동시 처리 1
브로커 장애영상 분석과 같은 규칙: 5초 뒤 서버 안 대기열로 넘김, 1분 건너뜀, 지표 trova.queue.draft.fallback
중복 방지다시 받은 초안은 상태를 보고 PENDING·PROCESSING만 만든다. 끝난 초안·답 기다리는 초안은 Gemini를 부르지 않고 건너뜀. 같은 초안은 서버 안에서 한 번에 하나

7. 확장: 실패 작업 토픽·경보, 직접 초안·재구성까지 (2026-11-12, #394·#396)

이제 Kafka를 거치는 일은 영상 분석, 일정 초안(자동·직접), 일정 재구성 세 가지다. 처리하다 실패한 메시지는 한 토픽에 모으고, 쌓이면 경보가 울린다.

항목내용
토픽trova.share-jobs, trova.draft-jobs, trova.replan-jobs, 실패 작업 trova.dead-letters — Aiven 무료 5개 중 4개
실패 작업리스너 예외는 다시 돌리지 않고 실패 토픽으로(원래 토픽·예외는 헤더, 스택 트레이스 제외 — 무료 125KiB/s). 다시 돌리면 Gemini를 또 부르므로 사람이 보고 관리자 재시도
경보(Grafana Cloud)토픽별 처리 못 한 메시지 > 3개가 15분, 실패 작업 > 0. 대시보드 "대기열 — Kafka" 줄. Runbook docs/runbooks/kafka-queue.md
재구성 중복 방지예전엔 상태 확인 없이 다시 돌렸다 → PENDING·PROCESSING만 시작하고 끝난 작업은 건너뜀. 같은 작업은 서버 안에서 하나씩
대가화면에서 기다리는 직접 초안·재구성에 Kafka 전달 약 0.2~0.4초. 브로커 장애 첫 요청은 5초 늦음

8. 저장됐지만 대기열에 없는 작업 다시 보내기 (2026-11-12, #399·#404, ADR 0043)

작업은 "DB에 저장 → Kafka로 보내기" 두 단계로 시작한다. 그 사이에 서버가 죽거나, Kafka 장애로 서버 안 대기열에 넘긴 뒤 죽으면 작업은 어디에도 없고 15분 뒤 실패로 정리됐다. 아웃박스 테이블을 새로 만드는 대신 작업 행의 PENDING·PROCESSING 상태를 그대로 아웃박스로 쓰고, 멈춘 작업을 한 번 다시 보낸다.

9. 결정과 한계, 남은 일

운영은 Kafka를 그대로 쓴다(ADR 0021). 사용자 약 12명 규모에서 처리량 이득은 없다. 얻는 것은 재시작에 강한 처리와, 서버를 늘릴 때 설정만 바꾸면 되는 구조다.

  • 한계: 외부 의존이 하나 늘었다(Aiven). 무료 플랜은 오래 안 쓰면 꺼진다는 기록이 있지만 공식으로 확인하지 못했다. 꺼져도 자동 넘기기로 공유는 막히지 않는다.
  • 한계: 중복 실행 방지는 서버 한 대 안에서만 보장한다.
  • 한계: 저장 뒤 보내기 전에 죽은 작업은 최대 약 9분 늦게 처리된다(다시 보내기 기준 3~8분 + 1분 주기). 다시 보내기·중복 방지는 서버 한 대 기준이다(ADR 0043).
  • 한계: 비교는 낮은 부하에서 영상 3종으로만 했다. 실제 트래픽의 실패율·처리량으로 일반화하지 않는다.
  • 남은 일: 무료 Oracle A1(2 OCPU·12GB)을 확보하면 브로커를 그쪽으로 옮길지 다시 본다.
  • 남은 일: 운영 공유가 쌓이면 경로별 대기 중앙값과 1초 안에 시작한 비율을 기록한다.
