# 동선 최적화: 전체 순서 대입 → 동적 계획법 (#313)

**결과가 같으면서 로컬에서 장소 10개 기준 약 530ms → 0.24ms로 줄었다.** 운영 서버(Oracle E2.1.Micro)에서는 아직 재지 않았다.

## 무엇을 바꿨나

- 대상: `RouteOptimizer`. 사용 위치는 동선 최적화 버튼 API 두 개(`POST /api/places/videos/{jobId}/days/{day}/optimize-route`, `POST /api/trips/{tripId}/days/{day}/optimize-route`)이고, 사용자가 응답을 기다린다.
- 전: 장소가 10개 이하일 때 가능한 순서를 **전부** 만들어 하나씩 거리를 합산했다(10개면 10! = 3,628,800가지, 순서마다 거리 계산 9번).
- 후: **동적 계획법(Held-Karp)**. 쉽게 말하면 "지금까지 들른 장소 묶음 + 마지막 장소"가 같으면 앞에서 어떤 순서로 왔는지는 상관없으므로, 그 상태별로 가장 짧은 거리만 기억한다. 10개면 상태 수가 10 × 2¹⁰ = 10,240개이고, 계산은 약 10만 번이다. 장소 쌍 사이 거리는 처음에 한 번만 계산해 표로 둔다.
- 고정 장소(식당 등)·좌표 없는 장소를 제자리에 두는 `optimizeKeepingFixed`도 같은 방식으로 바꿨다. 빈자리를 앞에서부터 채우고, 고정 장소 구간을 사이에 둔 거리를 그대로 반영한다.
- 그대로인 것: 정확해를 쓰는 상한(10개), 10개 초과 시 가장 가까운 곳 근사, 원래 순서보다 확실히 짧을 때만 바꾸는 규칙, 좌표 없는 장소 처리. 다만 **총거리가 완전히 같은 순서가 여러 개면 어느 쪽을 고르는지는 예전과 다를 수 있다**(거리는 같다).

## 정확성 확인

- `LegacyRouteOptimizer`(테스트 전용, 바꾸기 전 코드 그대로)와 새 코드에 같은 무작위 입력(seed 313)을 넣어 총거리가 1e-9km 이내로 같은지 비교했다. 좌표만 있는 경우(2~10개) 약 150개, 좌표 없는 장소가 섞인 30개, 고정 장소가 섞인 60개, 움직일 장소 10개와 고정 2개 2건, 이미 최단인 경우 모두 통과했다.
- 기존 `RouteOptimizerTest` 7개와 동선 최적화 통합 테스트도 그대로 통과했다.

## 시간 측정 (로컬)

- 환경: **로컬 MacBook(Apple M5, 10코어), Java 21.0.9**. 운영 서버는 CPU가 훨씬 약해서(E2.1.Micro, OCPU 1/8) 값이 다르다.
- 방법: 경우마다 무작위 입력 3개 × 방식별 워밍업 2회 + 측정 5회. 짝수 회차는 예전→새, 홀수 회차는 새→예전 순서로 번갈아 쟀다. 모든 표본은 [원본 JSON](results/route-optimizer-dp-local-20261104.json)에 있다.
- 다시 재기: `ROUTE_BENCH=1 ROUTE_BENCH_ENV=local ROUTE_BENCH_OUT=$PWD/out.json ./gradlew test --tests 'com.trova.backend.service.RouteOptimizerBenchTest' --rerun-tasks` (평소 빌드에서는 돌지 않음)

| 경우 | 움직일 장소 | 전 중앙값 | 후 중앙값 | 전 평균 | 후 평균 |
|---|---:|---:|---:|---:|---:|
| optimize | 6 | 0.284ms | 0.039ms | 0.286ms | 0.043ms |
| optimize | 7 | 0.552ms | 0.025ms | 0.972ms | 0.043ms |
| optimize | 8 | 4.792ms | 0.055ms | 4.792ms | 0.060ms |
| optimize | 9 | 47.954ms | 0.085ms | 49.363ms | 0.092ms |
| optimize | 10 | 529.700ms | 0.236ms | 532.444ms | 0.230ms |
| optimizeKeepingFixed (고정 2개 포함 12곳) | 10 | 813.790ms | 0.251ms | 819.990ms | 0.276ms |

- 해석: 장소가 7개 이하면 원래도 1ms 미만이라 사용자가 느끼는 차이는 없다. 차이는 **9~10개일 때** 크다. 이 값은 동선 계산 자체의 시간이고, API 전체 응답 시간(DB 조회·저장 포함)이 아니다.
- 운영 서버에서 전 값이 몇 초가 될지는 **추정하지 않는다**. 필요하면 배포 전에 같은 측정을 운영 서버에서 따로 돌려 기록한다.
