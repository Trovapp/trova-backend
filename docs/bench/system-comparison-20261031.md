# 기존·Spring AI 2·Kafka 성능 비교 (#260)

## 비교 대상과 적용 범위

실제 도입 순서는 **기존 REST + async → REST + Kafka → Spring AI 2 + Kafka**다. Spring AI 2는 Java 텍스트/JSON 호출만 바꿨으며, Python 영상 장소 추출은 별도다. 대화 도구 호출과 임베딩도 모두 Spring AI로 전환된 것은 아니다.

| 단계 | 코드 기준 | Java AI 호출 | 영상 시작 대기열 | 근거 |
|---|---|---|---|---|
| 최초 기준 | 97fc866 | 기존 RestClient | async | 두 의존성 모두 없음 |
| Kafka 도입 | 1666fee | 기존 RestClient | 설정에 따라 Kafka/async | Kafka만 추가 |
| Spring AI 도입 초기 | 15c1406 | Spring AI 2 | Kafka 사용 가능 | 이미 Kafka 도입 후의 커밋 |
| 운영 HTTP 수정 후 | 2b1b56e 및 후속 main | Spring AI 2, HTTP/1.1 | 운영 Aiven Kafka + async 폴백 | 현재 운영 계열 |

따라서 15c1406이나 0e472f4를 "Spring AI만 있는 빌드"로 간주하면 안 된다. 둘 다 Kafka 의존성을 포함한다. 클라이언트 자체의 비교는 아래 별도 하네스에서 대기열을 실행하지 않고 분리했다.

## 1. Java AI 클라이언트: 동일 요청 신규 측정

2026-10-31 로컬 Mac, Java 21. 현재 앱의 SpringAiConfig(HTTP/1.1·SDK/라이브러리 재시도 비활성화)와 기존 방식의 RestClient를 같은 프로세스에서 사용했다. 전체 서버·DB·Kafka는 시작하지 않았다. Gemini 모델과 temperature 0.1·JSON 형식·프롬프트는 동일하다. 라운드마다 먼저 부르는 클라이언트를 바꾸고 호출 사이 6초를 두었다. 별도 JVM 힙 상한은 주지 않았으므로 과거 -Xmx384m의 자원 측정과 직접 비교하지 않는다. 각 1회 워밍업 뒤 4회 측정, 총 실제 호출 10회.

| 지표 | 기존 REST | Spring AI 2 |
|---|---:|---:|
| 측정 성공 | 4/4 | 4/4 |
| 중앙값 | 3,656.64ms | 3,636.54ms |
| 평균 | 4,030.36ms | 3,593.95ms |

중앙값 차이는 약 20ms(0.55%). **이 표본으로 유의미한 속도 이득을 주장하지 않는다.** 기존 기록의 902→892ms와 절대값이 다른 것은 요청·측정 시점 등이 달라서이며, 두 날의 수치를 이어 개선율로 계산하지 않는다. n=4로 p90/실패율을 일반화하지 않는다.

범위: 정상 단일 요청 지연. 실패·재시도·전체 초안 생성·메모리·JAR 영향은 이 실험에서 재지 않았다. REST는 기존 연결 3초/읽기 20초, Spring AI는 운영의 전체 20초 제한이므로 오류 경로의 타임아웃 의미까지 동일한 실험은 아니다. 새 SDK를 수정하기 전 15회 재시도 가능성은 도입 중 발견한 설정 문제이고, 최초 REST의 상한도 3회였으므로 "기존 대비 호출 15→3 절감"으로 주장하면 안 된다.

원본: `results/client-latency-20261031.json`.

## 2. 대기열: 로컬 동일 메시지 전달 비교

로컬 내장 Kafka 브로커 1개·파티션/소비자 2개와 앱 async 실행기. 입력은 동일한 작업 ID, 저장소와 분석 서비스는 mock이다. 기본/카프카 순서를 교대로 21회씩 실행하고 첫 회는 워밍업으로 제외했다. enqueue 직전부터 분석 메서드 진입까지의 단조 시계 시간을 기록했다. 직렬 전송이며 부하·백로그는 없다.

| 지표 | async 실행기 전달 | Kafka 전달 |
|---|---:|---:|
| 표본 | 20 | 20 |
| 중앙값 | 0.0549ms | 6.6327ms |
| 표본 p90(nearest-rank) | 0.0771ms | 6.7629ms |

이는 **로컬 전달 오버헤드** 비교다. Kafka에 네트워크·브로커 전달 단계가 추가되는 비용이 관측됐다. async는 실행기에 직접 제출하므로 Spring @Async 프록시 전체 비용을 재는 것은 아니다. DB·Gemini·Aiven 원격 TLS·공유 API·재시작 복구를 포함하지 않으며, 운영 대기 시간이나 전체 분석 속도로 해석하지 않는다. 21회씩 해당 경로로 전달됐는지도 검증했다.

원본: `results/local-queue-latency-20261031.json`.

## 3. 운영 실측: 기록 재검증

운영 journal을 다시 읽어 기존 기록을 검증했다. 분석 시작→DONE에는 추출·지오코딩·선별·저장이 포함되며, 공유 응답이나 초안 생성은 포함하지 않는다.

| 작업 | 경로 | 영상 ID | 대기 | 처리 시작→DONE |
|---|---|---|---:|---:|
| 87 | Kafka | H1bCCd1vDCA | 당시 미측정 | 14.511초 |
| 88 | async 폴백 | YS4z0NqKkyw | 당시 미측정 | 14.767초 |
| 91 | Kafka | H1bCCd1vDCA | 3,867ms | 13.698초 |
| 92 | Kafka | YS4z0NqKkyw | 1,192ms | 13.370초 |
| 93 | Kafka | 8vmpPuFwQ94 | 2,076ms | 13.597초 |

**정정:** 과거 87·88을 같은 영상의 전후 비교처럼 설명했으나 실제 URL이 다르다. Kafka 14.5초·async 14.8초는 각각 관측된 결과일 뿐 속도가 같다는 통제 실험이 아니다. 88·92는 동일 영상이지만 실행 시점·빌드·연결 상태가 달라 통제 A/B가 아니다. 정상 async의 운영 대기는 아직 측정하지 않았다. async 폴백은 Kafka 실패 대기를 포함하므로 기존 async 기준선으로 대체하면 안 된다.

현재 운영 프로세스의 Prometheus 읽기 스냅샷에는 Spring AI 성공 1회·합계 4.0111초, Kafka 대기 1회·합계 2.076초, 폴백 0회가 있었다. n=1의 누적 계수이며 운영 중앙값/p90이 아니다. 배포·재시작으로 계수가 초기화되므로 과거 5.1초 성공 기록과 혼합 집계하지 않는다.

원본(필요한 필드만): `results/production-observations-20261031.json`. 운영 설정·서비스·데이터는 변경하지 않았다.

## 4. 자원과 장애 시 동작: 기존 기록의 범위

- 과거 로컬 기록: 기준 JAR 71.2MB, Kafka 도입 기록 83.9MB; Spring AI 작업 기록 95.9MB 및 RSS 평균 +16MB. 상세는 `spring-ai-kafka-performance.md`. 당시 측정 빌드 산출물의 정확한 커밋/원본 자원 로그를 복원하지 않았으므로 Spring AI만의 독립 증가분이나 최종 두 기술의 합산 비용을 새로 입증한 것으로 제시하지 않는다.
- Spring AI 운영 초기에는 6/6 timeout, HTTP/1.1 고정 후 1회 성공 5.1초가 기록되어 있다. 이는 운영 장애 수정의 전후이고 최초 REST 대비 속도 개선률은 아니다. 근본 망 원인까지 독립 재현한 것은 아니다.
- Kafka 프로세스 중단 후 재수신 약 37초·DONE은 과거 로컬 테스트 기록이다. 운영 Aiven 강제 중단의 무손실 보장을 입증한 것이 아니다.
- 과거 운영 Aiven power off/on에서 토픽 끝 오프셋이 초기화됐다는 기록이 있다. 브로커 데이터 보존 정책을 확인하지 않고 "장애에도 무조건 작업 보존"이라고 쓰면 안 된다. DB의 멈춘 작업 실패 정리는 자동 재처리와 다르다.
- Kafka 타임아웃→async 폴백 뒤 늦은 메시지의 두 실행 경로 진입은 후속 로컬 시나리오로 재현했다. 실제 저장 중복은 실행하지 않았고 해결은 #261에서 추적한다.

## 해석과 운영 비교 후속

Spring AI 2의 정상 요청 속도 개선은 현재 입증되지 않았고, 호출 경계·계측·클라이언트 통합이 주된 변화다. Kafka는 전달 비용이 추가되며 작업 전달 경로와 복구 가능성을 바꾼다. Python 추출 정확도·LLM 처리 속도를 두 기술의 효과로 제시하지 않는다.

운영에서 최초 async와 Kafka의 전체 효과를 비교하려면 같은 영상·동일 코드·동일 부하에서 정상 async/Kafka를 교대로 반복하고, 요청 응답·작업 생성→분석 시작·분석 시작→저장 완료·성공률·RSS를 구분해 기록해야 한다. 이후 사용자 승인으로 동일 코드의 Kafka→async→Kafka 운영 비교를 완료했다. 각 경로 n=4의 대기 중앙값은 async 135ms, Kafka 574ms이며 전체 처리 시간의 속도 개선은 입증하지 못했다. 상세 조건·복구·정리는 [운영 비교](production-queue-ab-20261031.md)를 참고한다. 최초 REST 빌드로 되돌린 운영 실험과 포화 부하 시험은 하지 않았다. ACK 지연 중복 진입은 로컬 제어 시나리오로 재현해 #261로 추적한다.

## 재현

- 호출 비교: 사용량 확인 후 `TROVA_BENCH_KEY`를 로컬 비공개 환경에서 주입하고 `./gradlew -I docs/bench/scripts/client-latency.init.gradle clientLatencyBench -q`. 키를 명령 출력이나 결과에 쓰지 않는다. 기본 결과 파일을 덮어쓰므로 필요하면 `-PbenchOutput=<별도.json>`을 준다.
- 큐 비교: `TROVA_RUN_QUEUE_BENCH=1 ./gradlew test --tests '*ShareJobKafkaRoundTripTest.로컬_async와_Kafka_전달_지연을_비교한다'`. 실제 Kafka는 로컬 내장 테스트 브로커뿐이며 Gemini 호출은 없다. 기본 결과 파일을 덮어쓴다.
