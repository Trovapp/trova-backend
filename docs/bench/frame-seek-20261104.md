# 인스타 프레임 뽑기: 영상 전체 디코딩 → 지점 이동 (#323)

**운영 서버에서 51초·46초 영상의 프레임 뽑기가 19.1초 → 10.6초, 18.0초 → 11.1초로 줄었다(각 3회 중앙값). 뽑힌 장면은 예전과 같다.** 19초 영상은 예전 방식을 그대로 써서 2.93초 → 2.99초(차이 없음)다.

## 배경

[운영 기준값(#319)](prod-resource-baseline-20261104.md)에서 인스타 분석 37~41초 중 프레임 뽑기가 19.6~19.7초였다. 예전 방식은 8장을 뽑으려고 ffmpeg로 영상 전체를 디코딩한다(자식 CPU 37~38초, 운영 서버는 1/8 OCPU). ffmpeg는 이미 C 프로그램이라 언어를 바꿀 대상이 아니고, **덜 디코딩하는 방법**을 찾았다.

## 쉬운 용어

- **디코딩**: 압축된 영상을 실제 그림으로 푸는 일. CPU를 가장 많이 쓴다.
- **키프레임**: 앞 장면 없이 혼자 풀 수 있는 장면. 그 사이 장면은 앞 장면과의 차이만 저장돼 있어서, 중간 장면 하나를 보려면 바로 앞 키프레임부터 풀어야 한다. 이 인스타 영상들은 키프레임이 5초마다 하나다.
- **지점 이동(-ss)**: 원하는 시각 바로 앞 키프레임으로 건너뛰어 거기서부터만 푼다.

## 바꾼 것 (`pipeline-test/frames.py`)

1. 예전 방식이 어느 장면을 고르는지 먼저 확인했다. 51초 영상의 전체 1,525장과 대조하니 **8구간 각각의 가운데 직전 마지막 장면**이었다(가장 가까운 장면과의 차이 0.37~0.65, 바로 앞뒤 장면과는 2.1~22.0, 0~255 밝기 기준).
2. 새 방식은 ffprobe로 압축 데이터의 장면 시각·키프레임만 읽고(디코딩 없음, 운영 약 0.3초), 같은 규칙으로 장면을 고른 뒤, 한 번의 ffmpeg 실행에서 8곳으로 각각 이동해 한 장씩 뽑는다.
3. **풀어야 할 장면 수를 미리 계산해서** 지점 이동이 예전의 0.7배 미만일 때만 쓴다. 키프레임이 드물면 지점마다 앞 키프레임부터 풀어야 해서 오히려 느려진다(첫 시도에서 19초 vp9 영상이 3.4초 → 4.5초로 느려졌다).
4. 20초 미만 영상은 시각 읽기도 생략하고 예전 방식을 쓴다(시각 읽기 비용이 이득보다 컸다).
5. 시각을 못 읽거나 지점 이동이 실패하면 예전 방식으로 다시 뽑는다. 예전 방식은 `extract_frames_full_decode`로 남겨 비교에 쓴다.

## 같은 장면인지 확인

- 실제 인스타 영상 3개와 합성 영상 7개(0.4~9초, 시작 시각이 0이 아닌 영상 포함): 장면 수가 모두 같고, 같은 순서 사진끼리의 차이는 0.0~0.25다(인코딩 경로 차이 수준).
- 51초 영상은 새 방식 8장도 전체 장면 대조에서 예전과 **같은 장면 번호**(95, 286, 477, 668, 859, 1050, 1241, 1432)로 나왔다.
- 테스트 `pipeline-test/test_frames.py` 5개(규칙 3개, 키프레임 5초짜리 40초 영상에서 PSNR 35dB 초과, 이전 프레임 정리)는 로컬과 **운영 서버(Python 3.10, ffmpeg 4.4)**에서 통과했다.

## 시간 측정

- 같은 영상에서 예전·새 방식을 번갈아(짝수 회차 예전→새, 홀수 회차 새→예전) 워밍업 1회 + 측정 3회. 운영 서비스·큐·DB는 건드리지 않고 운영 서버의 별도 임시 폴더에서 `nice -n 10`으로 돌렸다. 시작 전 진행 중 작업 0건을 확인했다.
- 도구 [frame_extract_bench.py](scripts/frame_extract_bench.py). 원본은 단계별로 모두 남겼다: [1차 지점 이동만](results/frame-seek-prod-20261104-v1-seek-only.json), [2차 비용 규칙](results/frame-seek-prod-20261104-v2-cost-rule.json), [3차 길이 중복 읽기 제거](results/frame-seek-prod-20261104-v3-no-double-probe.json), [최종](results/frame-seek-prod-20261104-final.json), [로컬(1차 코드)](results/frame-seek-local-20261104.json).

**단계별로 바꿀 때마다 잰 값(운영 중앙값, 예전 → 새)**

| 단계 | 51초 h264 | 46초 h264 | 19초 vp9 |
|---|---|---|---|
| 1차 지점 이동만 | 19.5 → 10.3초 | 18.2 → 11.2초 | 3.4 → **4.5초 (느려짐)** |
| 2차 비용 규칙 추가 | 19.0 → 11.2초 | 19.5 → 11.4초 | 3.2 → 3.7초 |
| 3차 길이 중복 읽기 제거 | 18.6 → 10.8초 | 19.0 → 10.9초 | 3.0 → 3.5초 |
| 최종 20초 미만 생략 | 19.1 → 10.6초 | 18.0 → 11.1초 | 2.9 → 3.0초 |

- 로컬(MacBook M5)에서는 원래도 0.2~0.5초라 차이가 작았다. 이 개선은 CPU가 약한 운영 서버에서 의미가 있다.
- **분석 1건 전체 시간은 재지 않았다.** 프레임 뽑기만 약 8초 줄었으므로 인스타 분석(37~41초)이 그만큼 줄 것으로 **예상**하지만, 다운로드·Gemini 시간이 매번 흔들려서 실제 분석으로 확인해야 한다.
- 키프레임 간격이 5초보다 길거나 짧은 영상은 이득이 다르다. 비용 규칙이 이득 없는 경우를 예전 방식으로 돌리지만, 표본은 3개뿐이다.

## 남은 후보 (하지 않음)

- 각 구간의 **키프레임 자체**를 뽑으면 장면당 한 장만 풀어서 더 빨라진다. 다만 뽑히는 장면이 최대 2.5초 달라져서(화면 자막이 바뀔 수 있음) 평가 세트로 정확도를 확인해야 한다.
