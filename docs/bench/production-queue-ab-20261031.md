# 운영 동일 영상 async/Kafka 비교 및 복구 (#260)

> 최신 종합: [2026-11-01 비교 정리](system-comparison-summary-20261101.md). 원본 재계산과 후속 중복 억제/복구 검증 상태를 포함합니다. 아래 수치는 당시 기록입니다.

## 조건과 원본

2026-10-31 Oracle E2.1.Micro 운영 서버·Aiven Kafka, 현재 운영 JAR/Python, 같은 김해 쇼츠(8vmpPuFwQ94), 계정 1에서 reanalyze=true로 직렬 제출했다. 영상을 매번 실제 재분석하며 캐시로 기존 결과를 재사용하지 않는다. 자동 초안은 원래대로 활성화했고 각 작업과 초안 처리가 안정된 뒤 RSS를 읽었다.

Kafka(K1: 워밍업 1+측정 2) → async(A: 워밍업 1+측정 4) → Kafka(K2: 워밍업 1+측정 2) 순서다. 총 11건, 분석 성공 11/11. 각 블록 첫 실행을 제외하면 경로별 측정 4건이다. 무작위 순서는 아니며 같은 URL 하나의 낮은 부하 조건이다.

원본: `results/production-queue-ab-20261031.json`. JAR SHA-256은 전후 동일함을 검증했다. 실제 경로도 서비스 로그의 kafka/async와 표본별 기대값이 일치함을 확인했다. Python 스크립트나 서비스 JAR을 교체하지 않았다.

## 결과 (워밍업 제외, 각 n=4)

| 항목 | 정상 async | Aiven Kafka |
|---|---:|---:|
| 작업 생성→분석 시작 중앙값 | 135ms | 574ms |
| 공유 HTTP 응답 중앙값 (Mac에서 측정) | 400.332ms | 834.251ms |
| 분석 시작→저장 완료 중앙값 | 22.062초 | 21.451초 |
| 작업 생성→저장 완료 중앙값 | 22.197초 | 21.755초 |

| job에 귀속된 Gemini 논리 호출 | 12 | 12 |
| 해당 호출의 실제 시도 합계 | 14 | 12 |
| 재시도 대기 합계 | 15,000ms | 0ms |

- Kafka는 이 표본에서 대기 중앙값이 439ms 길었다. 이는 같은 코드·같은 영상·운영 원격 브로커 조건에서의 관측이다.
- 전체 처리 중앙값 차이 약 0.44초로 속도 개선을 주장하지 않는다. 두 경로 모두 논리 호출 12회(수집·선별·매칭 각 4회)지만 async에서 추가 전송 시도 2회·15초 대기가 있었다. 모델 응답 시간과 결과 변동, 재시작·연결 상태가 섞여 있다.
- RSS 차이를 Kafka 의존성의 고정 메모리 증가로 단정하지 않는다. 같은 코드의 서로 다른 프로세스/시점 관측이며 힙 사용·GC·캐시를 통제하지 않았다.
- 표본 4건으로 p90이나 운영 전체 실패율·처리량을 일반화하지 않는다. 포화 부하·브로커 장애·프로세스 강제 종료를 운영에서 시험하지 않았다.

## 변경 및 복구

- 전환 전 전역 진행 작업/초안 0건 확인.
- 영구 `/opt/trova-backend/.env`는 수정하지 않음. `/run/systemd/system/trova-backend.service.d/90-codex-ab-260.conf`가 임시 `/run/trova-ab-260.env`를 마지막 EnvironmentFile로 읽게 해 `APP_QUEUE_TYPE=async`만 일시 덮어씀.
- async 전환 기동 후 UP 대기 94.207초. 원래 Kafka 복구 후 120.181초. 각 1회 관측이며 대기열별 기동 성능으로 일반화하지 않는다.
- 측정 종료 후 임시 파일 두 개 제거, daemon-reload·재시작 완료. 서비스 active·헬스 UP, DropInPaths 비어 있음 확인. 복구한 Kafka 경로로 K2 3건까지 성공.
- 이 실행이 만든 장소 66개·자동 초안 1개만 식별해 로컬 비공개 0600 JSON 백업 후 삭제. 해당 job ID의 장소·초안 잔여 0건을 확인했다. DONE 작업 기록과 API 호출 기록은 측정 증거로 유지했다.
- 정리 대상 작업: 94~104. 기존 사용자 장소/초안은 삭제하지 않았다. 생성된 작업 기록은 계정의 오늘 공유 사용량에 포함된다.

## 해석

Spring AI 2 클라이언트 자체는 별도 로컬 동일 요청 비교에서 평가했다. 이 운영 실험은 **Spring AI 2를 사용하는 동일 코드에서 대기열만 바꾸는 비교**다. 최초 REST 시절 빌드를 운영에 되돌려 측정한 실험은 아니다. 과거 단계별 수치와 이 결과를 혼합해 두 기술을 합친 개선율을 만들지 않는다.
