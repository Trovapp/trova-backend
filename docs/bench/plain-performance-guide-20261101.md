# Spring AI와 Kafka 성능을 읽는 방법

Spring AI와 Kafka를 넣었다는 이유만으로 전체 분석이 빨라졌다고 말할 수는 없습니다. 이전 운영 비교에서는 Kafka 경로가 더 오래 걸렸습니다. 중복 조회와 저장 방식을 보완한 뒤 실제 운영에서 같은 영상을 한 번씩 확인한 결과도 11.884→16.745초로 길어졌습니다. 속도 이득은 확인하지 못했습니다. 다만 변경 후가 재시작 뒤 첫 분석이라 지속적인 성능 저하로 단정할 수도 없습니다.

## 도구의 역할

| 말 | 쉬운 설명 | 이 서비스에서 쓰는 곳 |
|---|---|---|
| Spring AI 2 | Java에서 Gemini를 부르는 공통 연결 도구 | 일정 요청 해석·일정 초안 생성, 추천 문구 생성 |
| Kafka | 작업을 전달하고, 중단됐을 때 다시 받을 수 있게 하는 대기열 | 공유한 영상의 분석 작업 전달 |
| 비동기(async) | 요청을 받은 뒤 분석은 뒤에서 진행하는 방식 | 내부 전달 방식과 Kafka 모두 해당 |
| DB | 작업과 장소를 보관하는 데이터베이스 | 작업 상태 확인·장소 저장 |
| 프롬프트 | AI에게 주는 지시문 | 후보 수집·추출·일정 생성 |
| 중앙값 | 시간을 순서대로 놓았을 때 가운데 값 | 작은 표본의 대표 시간. 일반적인 속도 보장은 아님 |
| 재시도 | 실패한 외부 요청을 다시 보내는 것 | 무료 한도 보호를 위해 횟수·기다린 시간 기록 |

영상의 장소 추출뿐 아니라 **장소 선택·검증도 Python이 Gemini를 직접 호출**합니다. Spring AI는 주로 일정 생성 쪽입니다. 영상 분석 시간에 Spring AI가 직접 호출되는 것으로 가정해 속도 효과를 계산하면 잘못된 결론이 됩니다.

실제 도입은 `직접 AI 호출 + 내부 전달 → 직접 AI 호출 + Kafka → Spring AI + Kafka` 순서였습니다. Spring AI만 도입한 중간 운영 단계는 없습니다. 따라서 세 버전을 완전히 같은 조건에서 비교한 결과는 아직 없습니다.

## 이전 비교에서 알 수 있는 것

운영에서 같은 영상 3개를 각 2번, 각 방식 6건씩 분석한 결과입니다. 자동 일정 초안 완료 시간은 포함하지 않습니다.

| 가운데 값 | 내부 전달 | Kafka |
|---|---:|---:|
| 분석 시작 전 대기 | 0.2345초 | 0.440초 |
| 작업 생성→장소 저장 완료 | 11.919초 | 12.761초 |

이 낮은 부하에서는 Kafka 전달 비용이 추가됐습니다. 전체 분석은 0.842초 길었지만 Gemini 응답과 추가 검증 횟수도 달라졌으므로 증가분 전부를 Kafka 탓으로 확정하지 않습니다. 처리량(같은 시간에 완료하는 작업 수)이나 실제 장애 시 성공률을 입증한 비교도 아닙니다.

Spring AI의 짧은 요청 각20회 비교는 **로컬 Mac** 결과입니다. 직접 호출 중앙값0.913초, Spring AI0.719초였지만 변동 범위를 고려하면 확실한 속도 우위는 입증하지 못했습니다. 운영 성능이나 전체 영상 분석 속도로 바꿔 표현하지 않습니다.

## 이번 보완의 목적

- Kafka 시작 시 같은 작업 정보를 다시 읽던 조회 두 곳을 없앴습니다. 끝난 작업을 건너뛰는 검사는 서비스 안에 유지합니다.
- 장소를 한 개씩 별도로 저장하던 것을 장소 전체와 완료 표시가 함께 저장되도록 바꿨습니다. 중간 실패 시 일부만 남지 않도록 하는 안전성 보완이기도 합니다.
- 같은 영업시간 조회가 동시에 겹치면 진행 중 요청만 공유합니다. 이 동시성 동작은 가짜 외부 클라이언트로 검사했으며 운영 Google 호출 절감률은 아직 측정하지 않았습니다.
- Java AI의 시도 횟수와 실제 재시도 대기를 기록합니다. 로그 저장 실패를 이유로 이미 성공한 AI를 다시 부르던 경로도 제거했습니다.
- 장소명 프롬프트 후보는 사람 정답10개와 비교해 더 나빠져 채택하지 않았습니다. 대신 넓은 지역명/차량 내부 표기만 좁게 점검합니다. 업종/주소 근거가 있는 동명 가게와 구체 장소는 보존합니다.

새 코드의 실패·복구 검사는 격리된 자동 검사 환경에서 수행합니다. 실제 운영에서는 강제 장애를 만들지 않고 정상 배포와 영상 분석을 확인합니다. 전체 build1028중1025통과·실패/오류0·기존 선택 실행3건 제외, 실제 Kafka/별도 JVM 복구1건 추가통과, Python54·배포 도구11검사 통과했습니다. 통합 중 기존 HTTP 검사1건이 헤더 전 연결 종료로 실패했지만 코드 변경 없는 집중·전체 재실행은 통과했고 실패 기록도 보존했습니다.

## 이번 운영 변경 전후 결과

두 번 모두 Spring AI/Kafka를 쓰는 구성입니다. 최초 도입 비교가 아니라, 현재 구성의 중복 조회 제거와 저장 보완 전후입니다.

| 항목 | 변경 전 job123 | 변경 후 job124 |
|---|---:|---:|
| 공유 요청 응답 | 1.320초 | 4.082초 |
| 분석 시작 전 대기 | 0.894초 | 2.637초 |
| 작업 생성→장소 저장 완료 | 11.884초 | 16.745초 |
| 영상 분석 Gemini 호출 기록 | 3개 | 3개 |
| 위 AI 기록의 시간 합 | 7.904초 | 10.460초 |
| 저장 장소 | 6개 | 같은 이름 6개 |
| 분석 / 자동 일정 초안 | DONE / READY | DONE / READY |

전체는4.862초, 시작 전 대기는1.743초 길어졌습니다. AI 기록의 시간 합도2.556초 늘었습니다. 이 합은 네트워크 요청 수나 전체 파이프라인 시간과 같은 뜻이 아닙니다. 카카오 조회도 병렬이므로 각 호출 시간을 더해 전체 지연으로 쓰지 않습니다. DB 저장 단계만의 별도 운영 시간은 없어 저장 최적화의 독립 효과도 계산할 수 없습니다.

운영 일정 AI의 측정 시간대 기록은4.021→5.406초(각1회), 전후 모두 Spring AI라 도입 효과 비교가 아닙니다. 변경 후에는 실제 시도1/재시도 대기0이 기록됐습니다. 해당 로그는 개별 영상과 직접 연결되지 않으므로 시간대 기록으로만 제시합니다. 초안 생성→마지막 갱신 시간은6.527→7.122초이나 마지막 갱신은 전용 완료 시각이 아니어서 참고값입니다.

- 배포: PR295/298/297/299/301 순차 반영, main `fff19cd`. 빌드 기준 `92c94c9`와 런타임 소스가 같은 것을 확인했습니다. JAR과 extract_places.py를 함께 백업·교체했습니다. 환경/스키마/큐 변경 없음. 정상 상태까지102.697초, 전용 배포 도구 전체156.195초(빌드·전후 분석 제외)입니다. devflow deploy.sh를 쓴 시간과 섞지 않습니다.
- 새 JAR SHA-256: `394ba70011cb7f5a1612c5f293aeb63890352babbe3f88c1ebce9fd9b760f88a`. 변경 없는 나머지 Python6개도 해시를 대조했습니다.
- 최종 active/UP/Kafka·진행 작업0·관찰 구간 실제 WARN/ERROR 레벨0. 인증 없는 API401·세션 쿠키 없음. 테스트 장소12개와 자동초안2개만 각 비공개 백업 후 정리했고, 작업/호출 로그는 유지했습니다. 테스트 계정 오늘19/20,1건 예비 보존.
