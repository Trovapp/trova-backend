# Trova 영상 분석의 Rust 부분 도입 검토와 전후 기록 (#309)

**현재 기록만으로 Rust가 몇 초 줄일지는 알 수 없다.** 운영에서 모은 Python 분석12건을 다시 계산했고, 작은 부품을 비교하는 실험까지 설계했다. Rust 코드는 아직 실행하지 않았으므로 전후 속도/메모리 개선은 **미측정**이다.

이번에 권장하는 첫 실험은 영상 분석 전체 교체가 아니라 **AI에 보낼 미디어 요청을 준비하는 부분**이다. 정확히 같은 내용을 만들면서 더 빠르거나 메모리를 덜 쓰는지부터 확인한다.

## 쉬운 용어 설명

- **벽시계 시간**: 시작부터 끝까지 실제로 기다린 시간. CPU 계산·인터넷·AI 응답 대기가 모두 들어갈 수 있다.
- **CPU 시간**: 서버가 직접 계산한 시간. 외부 응답을 기다리는 시간과 다르다.
- **작업 프로세스(worker)**: 백엔드가 영상 하나의 처리를 맡겨 실행하는 프로그램.
- **base64**: 오디오/사진의 이진 데이터를 API JSON에 넣을 수 있도록 문자로 바꾸는 방식.
- **RSS**: 특정 프로세스가 실제 메모리에 올린 크기. Java 서버 RSS와 Python 작업 RSS는 서로 다른 값이다.
- **중앙값**: 표본을 정렬했을 때 가운데 값. 각 지표의 중앙값끼리 더해 한 작업의 시간이라고 계산하지 않는다.

## 1. 사용한 운영 기록

- 자료: [2026-11-01 확대 비교 원본](results/production-queue-expanded-20261101.json), 소스 `40fe231f146d9b79dcf2b77fb406e6d75452fdf8`. 당시 Oracle E2.1.Micro 운영 서버에서 수집했다. 현재 분석 시점의 소스는 `008e2de`이며 최신 서버 속도라고 부르지 않는다.
- 15건 중 워밍업3건을 제외한12건이다. 공개 유튜브3개를 각 경로에서2회씩 실행했다. Python은 양쪽 모두 같고, Kafka/async 대기열만 달랐다. **두 경로를 Python/Rust 전후라고 해석하지 않는다.**
- 이 코드의 정상 유튜브 경로는 Gemini에 URL을 직접 넘긴다. 따라서 이 자료로 인스타 다운로드·FFmpeg·미디어 base64 처리 성능을 평가할 수 없다. 원본 JSON에는 해당 단계별 timings와 Python 작업 프로세스의 CPU/RSS가 없다. 있는 메모리 값은 Java 서버의 관측 RSS다.
- 기록된 Gemini41행, 알려진 시도41회, 알려진 재시도 대기0ms다. 누락된 시도/대기 행은0이었다. 이는 공급자 청구/잔여 한도나 모든 실제 전송을 입증하는 값은 아니다.
- 원본 SHA-256과 작업별 재계산: [분석 JSON](results/rust-pipeline-feasibility-20261104.json). 새 영상 제출·Gemini/카카오 호출·DB/SSH 접속·배포 없이 파일만 재계산했다.

## 2. 기존 Python의 관측 결과

아래는 **당시 전체 분석의 배경 자료**다. Rust 시험의 준비 함수만 잰 시간이 아니다. 큐 대기는 제외하고 분석 시작→장소 저장 완료를 분모로 사용했다. 자동 여행 초안 완료는 포함하지 않는다.

| 지표 | Kafka + Python,6건 | async + Python,6건 |
|---|---:|---:|
| 분석 시간 평균 | 12.174초 | 11.807초 |
| 분석 시간 중앙값 | 12.060초 | 11.689초 |
| 후보 수집·선별 두 AI 호출 시간 합계의 중앙값 | 7.398초 | 7.511초 |
| 추가 선별·검증 포함 모든 AI 호출 시간 합계의 중앙값 | 8.975초 | 8.648초 |
| 작업별 AI 호출 시간 비중의 중앙값 | 74.685% | 74.550% |
| AI 로그 시간 밖의 나머지 시간 중앙값 | 3.085초 | 3.041초 |

12건에서 기본 두 AI 호출 비중은 약60.0~67.1%, 모든 AI 호출을 포함하면 약73.2~76.9%였다. **호출에 기록된 경과 시간**이므로 외부 통신·Gemini 처리뿐 아니라 일부 로컬 응답 읽기/JSON 해석·재시도 대기도 포함한다. 전부 순수한 외부 대기라고 하지 않는다.

현재와 당시 코드에서 collect→filter→주소 검색→추가 select→verify는 순차 진행된다. 이 검토한 흐름을 전제로 AI 호출 로그를 합산했다. 주소 검색은 병렬 실행될 수 있으므로 **카카오 호출 시간들을 합해 전체 시간에서 빼지 않았다.** 반복/알 수 없는 AI 작업이나 전체 시간보다 큰 합계는 계산기가 거절한다.

**나머지 약3초를 Python 계산 시간이나 Rust로 없앨 수 있는 시간이라고 보면 안 된다.** 여기에 카카오 검색·DB·Java·프로세스 실행·로그 전송 등이 섞여 있다. 기존 Java RSS300MB대 기록도 Python worker의 메모리가 아니므로 Rust 메모리 감소 비교에 쓰지 않았다.

## 3. 전후 비교 상태

| 항목 | Python 전(before) | Rust 후(after) | 판정 |
|---|---|---|---|
| 역사적 운영 전체 분석 | 위 표의6+6건 | 미측정 | Rust 전체 속도 차이 알 수 없음 |
| 같은 고정 파일의 미디어 준비 시간 | 미측정 | 미측정 | 새 대조 실험 필요 |
| 같은 준비 프로세스의 CPU/최대 RSS | 미측정 | 미측정 | 메모리 절감 주장 불가 |
| 요청 parts 내용·미디어 순서 호환성 | 현재 구현이 기준 | 미검증 | Rust 구현 후24개 골든과 비교 |

기계가 읽는 [전후 비교 틀](results/rust-pilot-comparison-template.json)에서도 미측정은 `null`이다. 역사적 전체 분석 시간을 새 준비 함수 실험의 before 값으로 복사하지 않는다. Rust를 실행하지 않은 결과를0초·성공·100% 개선으로 기록하지 않는다.

### 왜 부분 속도 개선이 전체 속도 개선과 다른가

다음은 **설명용 가정이며 실측/예측이 아니다.** Rust로 해당 계산이10배 빨라진다고 가정해도:

| 전체 시간에서 해당 계산이 차지한다고 가정한 비중 | 전체 시간 감소 |
|---|---:|
| 1% | 0.9% |
| 5% | 4.5% |
| 10% | 9.0% |

계산식은 `전체 시간 비율 = (1−계산 비중)+계산 비중/부분 속도 배수`다. 현재 자료에는 그 계산 비중이 없으므로 트루바의 예상 개선율을 넣을 수 없다. Python base64도 내부 네이티브 처리를 이용하므로 Rust의10배 우위를 전제하지 않는다.

## 4. 설계한 작은 시험

[상세 설계](../superpowers/specs/2026-11-04-rust-pipeline-pilot.md)와 [구현 순서](../superpowers/plans/2026-11-04-rust-pipeline-pilot.md)를 작성했다.

1. 기존 `build_parts`를 사용하는 Python 제어 프로그램과 Rust 비교 프로그램에 **동일 로컬 파일/자막/후보/프롬프트**를 넣는다. 요청 parts 생성까지만 수행하며 API는 호출하지 않는다.
2. 유튜브 참조·텍스트·오디오·프레임·혼합·사진 게시물의24개 고정 입력에서 내용/순서/MIME/base64와 실패 동작을 먼저 비교한다. 사진/오디오 자체를 다시 압축하거나 프롬프트를 바꿔 속도를 유리하게 만들지 않는다.
3. 로컬은 호환성 확인용이다. 성능은 사용자가 실행을 선택한 뒤 운영 서버의 별도 폴더/프로세스에서 직렬로 비교하도록 설계했다. 운영 서비스/큐/DB/기존 작업은 바꾸지 않는다.
4. 같은 입력에서 Python→Rust/Rust→Python 순서를 교대한다. 새 프로세스와 지속 프로세스의 결과를 분리하고 평균/중앙값/모든 개별 짝·실패·자원을 보존한다.
5. 별도 CLI가 빠르더라도 현재 Python에 Rust 보조 프로세스를 더하는 실제 경로가 느릴 수 있다. **추가 실행·통신 비용을 포함한 통합 비교**를 별도로 거쳐야 채택 판단에 쓸 수 있다.

외부 서비스·유료 API는 추가하지 않는다. 현재 자료로 전면 이식을 결정하지 않으며 기존 Spring AI·Kafka·Python 운영 구성도 바꾸지 않았다. 인스타 처리가 실제 병목이거나 Python 프로세스 비용이 충분히 크다는 근거가 생기면 해당 부분만 검토하는 순서를 권한다.
