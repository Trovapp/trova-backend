# PR #263 리뷰 (2026-10-31)

## 확인 범위

시작 시 HEAD 912d22f 기준의 변경과 실제 호출자를 읽었다. async process·Kafka listener·lifecycle 트랜잭션, 일정 생성의 markProcessing, 관리자 재시도(새 job 생성), 오류 처리, 프로세스 종료와 오프셋 경계를 점검했다. 신규 JVM의 DB 상태 복구 검사는 통합 테스트이며 실제 Kafka 브로커/서버 강제 재시작을 수행한 것은 아니다.

## 발견·수정

### P1: 시작 상태 조회/커밋 오류가 기존 작업 상태를 FAILED로 바꿀 수 있음

startAnalysis가 분석 예외를 처리하는 try 안에 있어, 완료 여부를 읽는 도중 DB 오류가 나도 markAnalysisFailed가 호출됐다. 늦은 메시지가 이미 완료된 작업을 확인하던 상황이라면 status·오류 메시지·retryCount를 잘못 갱신할 수 있다(이미 기록된 analysisStatus와 저장된 장소가 삭제되는 것은 아님).

시작 상태 조회/커밋과 null 건너뛰기를 분석 실패 처리 밖으로 옮겼다. 시작에 실패한 예외는 호출자에게 전달하고 기존 작업의 분석 실패로 기록하지 않는다. 분석 시작 허용 이후에 발생한 오류는 기존 실패 처리를 유지한다.

회귀 검사: 시작 조회 예외가 그대로 전달되는지, markAnalysisFailed·외부 파이프라인·저장·초안이 호출되지 않는지, 다른 스레드의 후속 수신이 잠금을 얻어 종료 상태를 다시 확인하는지 검사한다. Kafka 기본 오류 재시도 정책은 변경하지 않았다.

## 기존 검증과 결론

- 같은 작업은 선행 처리 완료까지 기다리고, DB 종료 상태를 다시 확인한다. 즉시 중복 성공 반환은 하지 않는다.
- Kafka 먼저/async 먼저 모두 실제 리스너·서비스 경로에서 파이프라인·저장·초안 각 1회, 늦은 경로의 대기를 검사했다. 잠금 제거 negative control에서도 두 순서 모두 실패했다.
- 새로운 프로세스에서 analysisStatus 없는 PROCESSING의 재처리를 허용한다. 분석 완료 뒤 일정 생성 중인 PROCESSING은 다시 추출하지 않는다.
- 관리자 재시도는 새로운 job을 생성하므로 종료 작업 차단과 충돌하지 않는다.
- DB 스키마·외부 API·운영 설정은 변경하지 않았다. 단일 서비스 인스턴스 보장 범위로 평가한다.

## 남은 검증·한계

- 실제 Kafka 오프셋과 프로세스 종료/재시작, max.poll.interval을 포함한 장시간 부하 통합 검증은 미완료다. 메서드 반환 시점 테스트를 실제 브로커 오프셋 검증으로 부르지 않는다.
- 고정 버킷 충돌 시 다른 작업도 기다릴 수 있다. 여러 JVM의 같은 DB 소비, 재시작 전 부분 저장, 외부 API exactly-once는 보장하지 않는다.
- 기존 PipelineRunner의 waitFor 인터럽트 경로에는 실행 중 자식 프로세스를 명시적으로 종료하는 코드가 없다. 이번 PR이 추가한 동작은 아니며 별도 수명주기 검토 대상이다. 이 리뷰에서 수정하거나 운영 장애로 재현하지 않았다.
- 오류 처리 정책(DefaultErrorHandler, 재시도 0회)은 유지했다. 시작 DB 오류를 전달한다고 자동 재시도가 보장되는 것은 아니다.
