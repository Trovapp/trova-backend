# 세 후속 수정 코드·검증 리뷰 (#282)

검토 시작 head는 PR279 `9df6463`, PR280 `c6e3c2e`, PR281 `a035643`이다. 사용자가 변경 검토와 순차 머지·배포를 모두 승인해 리뷰부터 진행했다.

## 발견·수정

Expo 파서는 `details.error`가 없으면 자유 형식 `message`를 오류 코드로 사용했다. 발송 서비스가 문자열 `DeviceNotRegistered`를 받으면 토큰을 삭제하므로, 설명이 우연히 그 문자열이거나 오류 구조가 깨진 응답에서 잘못된 자동 삭제가 가능했다. 설명에는 토큰 등이 포함될 수도 있어 그대로 전달하면 기존 로그 원칙과도 어긋난다.

명시적인 `details.error`의 비어 있지 않은 문자열만 코드로 사용하고, 코드가 없으면 일반 실패 `error`로 처리했다. 설명만으로 기기를 삭제하지 않는다. 정상 코드에 의한 삭제와 티켓 순서 보존은 유지한다.

파서 검사 1개를 추가하고 실제 발송 서비스 + fake client의 혼합 티켓 검사를 확장했다. 이전 코드에서 13개 중 3개 실패·오류0을 확인했고, 수정 후 PR279를 반영한 build는 981개 중978통과·실패/오류0·기존 opt-in3skip이었다. [리뷰 재현 집계](expo-ticket-review-20261101.json). 실제 Expo로 보내거나 운영 기기 토큰을 삭제하지 않았다.

## 나머지 검토

- 장소 상세: 현재 컨트롤러 호출은 외부 호출 전체를 감싸는 트랜잭션이 없다. placeId별 소유 Future의 성공/fallback/예외 전달, 소유자만 항목 제거, 대기자 인터럽트 보존과 소유 작업 비취소, 다른 장소 병렬, 완료 뒤 독립 재시도를 확인했다. 응답은 사용자별 정보가 없는 기존 공용 장소 상세다. 단일 JVM 범위이며 외부 클라이언트의 내부 재시도는 유지한다(ADR0027).
- 진행 로그: LF까지 원본 바이트를 모은 뒤 UTF-8 해석한다. 모든 바이트 분할 위치, 한 바이트씩 쓰기, CRLF·빈/깨진 JSON·미완성 줄을 확인했다. callback 예외를 정상 진행으로 숨기지 않고 기존 PipelineRunner의 실패/프로세스 정리 경로로 전달한다. 추가 차단 문제는 발견하지 않았다.
- 기존 데이터/응답/요청 한도/큐 설정·의존성·Entity/스키마는 바뀌지 않는다. 운영 이전 소스2ebf4b6 대비 런타임 변경은 PlaceReviewService, HttpExpoPushClient, StderrProgressTail 세 파일이다. Python 변경은 없다.
